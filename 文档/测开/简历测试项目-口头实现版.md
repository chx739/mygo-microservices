# §1 测试金字塔分层与覆盖

## 一句话定位

> 把测试分成四层金字塔——底部单元测试覆盖最广跑得最快、往上集成测试验证组件协作、再上并发安全验证、顶部 k6 端到端压测——**每一层用对工具，跑时分开但产出统一**。

## 四层实现流程

### Layer 1 单元测试
- **范围**：单函数、纯逻辑、零外部依赖
- **覆盖对象**：JWT 签发与验证、密码哈希、布隆过滤器、本地缓存读写、消息构造
- **工具**：Go 原生 `testing`，无第三方框架
- **跑时**：套件总跑时 < 5 秒

### Layer 2 集成测试
- **范围**：多组件协作 + 真实依赖
- **覆盖对象**：HTTP handler 全套（register/login/refresh/logout/me）+ middleware（token 校验各种边界）+ Mongo repo（索引强制等真行为）+ Redis 操作（限流 / 锁 / 幂等）
- **工具**：
  - Redis 用 `miniredis`（in-process 实现 Redis 协议，零容器开销）
  - Mongo 用真实实例（mock 测不出索引、CAS 等真行为）
  - HTTP 用 `httptest.NewServer`
  - RabbitMQ 用 channel mock（消息路由逻辑测试）+ E2E 压测兜底
- **跑时**：套件总跑时 < 30 秒

### Layer 3 并发安全验证
- **范围**：**横切关注点**——不是单独一层，是套在前两层上的"开关"
- **机制**：所有测试统一 `-race` 跑（Go 内置数据竞争检测器，基于 ThreadSanitizer）
- **代价**：内存 + CPU 各 2-10 倍，但漏掉的并发 bug 在生产偶发，最难复现

### Layer 4 端到端压测
- **范围**：真实业务路径，跨多个服务、网络、消息队列
- **工具**：k6 + xk6 + Prometheus + Grafana
- **跑时**：smoke 30 秒、完整 concert 17 分钟
- **频率**：smoke 每次发布、完整压测周/月级

## 口头表述（背这段）

> "我把测试体系分成四层金字塔——底层是单元测试，覆盖 JWT、密码哈希、布隆、本地缓存这种纯逻辑函数，套件总跑时不到 5 秒。第二层是集成测试，覆盖 HTTP handler 全套加 middleware 加 Mongo repo，Redis 用 miniredis 起 in-process 实例，Mongo 必须用真实例因为索引和 CAS 行为 mock 不出来。第三层不是独立层而是横切关注点——所有测试统一 -race 跑，验证并发安全，代价是 CPU 慢 2-10 倍但漏掉的并发 bug 在生产偶发最难复现，所以必须开。最顶层是 k6 端到端压测，17 分钟一轮覆盖真实业务路径。**这四层的关键不是数量而是分工——底层快跑频次高，顶层慢但接近真实**。"

## 高频追问

| 问 | 答 |
|---|---|
| **金字塔三层比例？** | 单测最多约 70%、集成 25%、E2E 5%。倒过来变成冰激凌锥是反模式——E2E 多则维护贵跑得慢。 |
| **覆盖率多少？** | 关键路径（鉴权、支付、并发锁）≥ 85%，业务 service ≥ 70%，utility ≥ 60%。100% 覆盖是陷阱，会被琐碎分支充水。 |
| **为什么 Redis 用 miniredis 不用 testcontainers？** | miniredis 在测试 import 里直接 `RunT(t)` 起一个，**比 testcontainers 快几个数量级**，跑完自动销毁。生产行为 95% 一致，5% 不一致的部分（持久化、复制）不在单测覆盖范围。 |

# §2 并发正确性专项断言（四个场景）

## 一句话定位

> 分布式系统最难测的就是并发——N 个 goroutine 同时进来时才暴露的问题。我针对四类典型并发风险**用数字断言而不是"看起来对"**。

## 通用方法论（每个场景都用）

1. **制造并发窗口**：mock 依赖里加 sleep / dbLatency，给 N 个 goroutine 时间堆到同一段
2. **ready chan 起跑线**：所有 goroutine 先 `<-ready` 阻塞，主线程 `close(ready)` 同时放闸
3. **sync.WaitGroup 收尾**：所有 goroutine 跑完再断言，避免主线程提前结束
4. **atomic 计数**：无锁原子计数，不引入额外 mutex 影响时序
5. **跑 `-race`**：验证无 data race

---

## 场景 1：分布式锁互斥（接单锁）

### 实现流程

1. 起一个真实 Redis 实例（miniredis 或 docker）
2. 100 个 goroutine 同时调 `TryAcquireTripAcceptLock(同一 tripID)`
3. 每个 goroutine 用 atomic.Int32 给"成功"加一
4. **断言**：成功数 == 1，失败数 == 99
5. 验证锁的 owner 字段：成功那个 goroutine 持有的 owner == Redis 里的 owner（防止误删别人锁）
6. 跑 `-race` + `-count=10` 多次稳定

### 口头表述

> "我用 100 个 goroutine 模拟 100 个司机同时抢同一个 tripID 的极限场景。每个 goroutine 调 `TryAcquireTripAcceptLock`，用 atomic 计数成功次数。**断言只有 1 个成功，99 个失败**——这就是分布式锁的核心契约。释放锁我用 Lua 脚本做'比较 owner 再删'的原子操作，防止 TTL 到期自动释放后别的 goroutine 抢到新锁、我再 DEL 误删的窗口。-race 跑过、多次 count 跑过，结果完全稳定。"

### 真实数字

- 100% 互斥（100/100 次试验都只有 1 个成功）
- benchmark 单实例 2.4k QPS / 12 核并发 12.9k QPS
- P99 加锁释放 0.8ms

---

## 场景 2：消息幂等收敛

### 实现流程

1. 起 miniredis（消息幂等状态机依赖 Redis）
2. 准备一条 `amqp.Delivery` 带固定 MessageId
3. 100 个 goroutine 同时调 `ClaimMessageForProcessing`，每个传入一个会自增计数的业务回调
4. **断言**：业务回调只被调用 1 次（atomic 计数器 == 1）
5. 单独写一个测试验证：业务失败时 `processing` 状态被 release，下次重试能进入业务（防止"永久卡死"）

### 口头表述

> "消息幂等用的是 `processing → done` 两态机——抢到 SetNX `processing:msg-id` 的那个 goroutine 才执行业务，业务成功后改成 `done`。失败的 goroutine 看到 processing 直接跳过，看到 done 也跳过。我用 100 个 goroutine 拿同一 MessageId 并发调，业务回调里 atomic 加一，**断言计数 == 1**。第二个测试验证业务失败时 processing key 被 release，下一次重试能正常进入业务——**这是防止幂等变永久卡死的关键测试**。"

### 真实数字

- 100% 收敛（100 goroutine 业务函数只执行 1 次）
- benchmark 全流程 2.5k QPS
- 失败 release 路径单独验证

## 场景 3：缓存击穿合并（singleflight）

### 实现流程

1. 起真 Redis，把 tripID 写进布隆过滤器（不然 Bloom 预检会判否、直接返回 404，碰不到 singleflight）
2. mock repo 加 `dbLatency = 50ms`，**这是制造并发窗口的关键**——给所有 goroutine 时间堆到同一个 sfg.Do
3. 50 个 goroutine 用 ready chan 对齐起跑线，同时调 `GetTripByID(同一 tripID)`
4. **断言**：`mockTripRepository.getTripCalls == 1`（50 并发只触发 1 次 DB 调用）
5. 第二个测试验证：warm 后两次顺序读 getTripCalls 仍 == 1，证明 singleflight 不影响热路径性能

### 口头表述

> "缓存击穿是热点 key 在 L1 和 L2 同时过期那一刻，N 个并发请求同时穿透到 DB。singleflight 是 Go 官方的 `golang.org/x/sync/singleflight` 库，把'相同 key 的并发 fn 调用'合并成只跑一次、其他人等结果。我用 50 个 goroutine 同时 GetTripByID 同一个 ID，mock repo 加 50ms 延迟制造并发窗口，**断言 repo.GetTripByID 只被调 1 次**——50:1 合并。我还专门写了第二个测试验证 singleflight 不影响热路径——warm 后顺序读两次，repo 调用仍然只有 1 次，证明 singleflight 只在击穿瞬间介入，不损耗常规性能。"

### 真实数字

- 50 并发合并为 1 次 DB 调用
- 50 个 goroutine 总耗时约 70ms（如果没合并是 50 × 50ms = 2.5s，**10 倍差距是合并的证明**）

---

## 场景 4：限流精确放行

### 实现流程

1. 起真 Redis（限流脚本是 Lua 在 Redis 单线程执行）
2. 200 个 goroutine 在 1 秒内打同一个 limit key（limit=10）
3. 每个 goroutine 调 `SlidingWindowAllow`，用 atomic 分别计 `allowed` 和 `rejected`
4. **断言**：`allowed == 10`，`rejected == 190`——**精确放行 10 个，多 1 少 1 都不行**
5. 跑 `-race` 验证

### 口头表述

> "限流我用 Redis ZSET + Lua 脚本做滑动窗口：删过期 → 计数 → 写入三步在 Lua 里原子执行。测试方法是 200 个 goroutine 同时打同一个 key，limit 设 10。Lua 在 Redis 单线程里跑，N 个并发请求被串行处理，**第 11 个进来时 count 已经是 10，Lua 直接拒绝**。断言**放行精确等于 10、拒绝精确等于 190**——多一个少一个都不行。这种精确性是滑动窗口的关键卖点：固定窗口在边界会双倍放行，滑动窗口不会。"

### 真实数字

- 精确放行 10（200 并发 limit=10）
- benchmark P99 0.90ms / 4.5k QPS

# §3 缓存正确性三模式对照实验

## 一句话定位

> 多级缓存加了 L1 又加了 singleflight，**每一层都得证明它确实有效**，不能凭感觉。所以我搭对照测试床用同一个 workload 跑三遍，定量验证每层的真实贡献。

## 实现流程

1. **共享 workload**：预生成 200 个唯一 tripID + 2000 次访问序列（Zipf 分布 s=1.07，模拟生产偏斜流量）
2. **定种子**：`rand.NewSource(42)` 保证三次运行的访问序列**完全相同**
3. **三模式切换**：通过两个 bool 参数（withRedis / withL1）切换：
   - NoCache（false, false）→ 每次调 mock repo 都 sleep
   - L2Only（true, false）→ Bloom + Redis + 回源
   - L1+L2（true, true）→ 完整三级
4. **每次跑前清空**：FlushDB Redis、重置 mock 计数器，保证公平
5. **记录指标**：每次 GetTripByID 的耗时、累计 db_calls
6. **输出对比表**：P50 / P95 / P99 / max / db_calls

## 口头表述

> "三模式对照本质就是控制变量法——同一个 workload 跑三遍，只改'有没有 L1' 和 '有没有 L2'。Workload 是 2000 次访问、200 个唯一 ID、Zipf 偏斜分布模拟真实热点流量。定种子 42 保证三次跑的访问序列完全相同。**结果分两块看：一是 db_calls 列**——NoCache 是 2000、L2Only 和 L1L2 都是约 200，**缓存把 DB 压力降了 10 倍**；**二是 P50 列**——NoCache 是 10ms（mock sleep），L2Only 约 400µs，L1L2 小于 10µs，**L1 比 L2 又快 40 倍**。**P99 三模式接近**，因为 cold miss 每个 ID 第一次必回源 DB，缓存救不了首次访问——这告诉我们降 P99 要靠预热脚本不是加缓存层。"

## 真实数字

| 模式 | P50 | P95 | P99 | db_calls |
|---|---|---|---|---|
| NoCache | ~10ms | ~10ms | ~11ms | **2000** |
| L2Only | ~400µs | ~3-5ms | ~10ms | **~200** |
| L1L2 | **<10µs** | ~300µs | ~10ms | **~200** |

## 高频追问

| 问 | 答 |
|---|---|
| **dbLatency 10ms 是真 Mongo 吗？** | 不是，mock repo 里 `time.Sleep(10ms)` 合成，**对照实验看相对加速倍数不看绝对值**——机器换了绝对值变，相对加速比稳定。 |
| **为什么 Zipf 不用 uniform？** | uniform 等概率分布所有 ID 都是热点，会高估缓存效果。生产流量都是 Zipf 偏斜，用 Zipf 才符合真实。 |
| **总命中率多少？** | 从 db_calls 反推 ≈ 90%（2000 次访问只 200 次 cold miss）。**没直接打 hit_rate 指标，下一步会启用 ristretto 自带 Metrics() 推到 Prometheus**。 |
| **L1 价值在哪？** | 不是降 DB 压力（这是 L2 的事），是**降 Redis 网络往返**。L1 命中 µs 级（内存读），L2 命中几百 µs（含网络），差 40 倍。 |

# §4 端到端性能压测体系（k6）

## 一句话定位

> k6 是 Go 写的 JS 脚本式压测工具，单进程多 goroutine 支持高并发，原生支持 WS 和多角色场景。我用它打"演唱会散场"模型瞬时大流量。

## 实现流程

### Step 1 选工具
- k6 vs JMeter（XML/GUI 重，CI 不友好）/ Locust（Python GIL 限并发）/ wrk（极快但只能打单 URL）
- **业务流是多步骤 + WS + 多角色**，只有 k6 的 scenarios 模型能表达

### Step 2 多角色 scenarios
- rider：`ramping-vus` 阶梯爬坡（50 → 2000）模拟突发流量
- driver：`constant-vus` 800 个长连接 WS 全程在线
- attacker：`constant-arrival-rate` 200 RPS 恒定打伪造 ID 验证 Bloom 防御

### Step 3 业务流编写
- 每个角色一个 default function
- rider 流程：登录 → **先连 WS 再发 preview/start**（这是踩坑出来的关键顺序）→ 15 秒等 driver_assigned

### Step 4 SLO 编码
- `thresholds.js` 把 SLO 写成断言：`preview p99 < 300ms`、`attacker_blocked_by_bloom > 98%`
- k6 跑完不达标 exit 非 0，可挂 CI 卡口

### Step 5 指标推送
- xk6 编译进 `xk6-output-prometheus-remote` 扩展
- 跑时用 `--out experimental-prometheus-rw=...` push 到 Prometheus
- 服务端 8 个白盒指标走 pull
- Grafana 一张面板对照看黑盒 + 白盒

### Step 6 留底
- 一条命令 `./k6 run --summary-export=...json`
- summary JSON 留底，多轮对照写进 REPORT.md

## 口头表述（必背）

> "k6 我配了三个角色 scenarios——rider 用 ramping-vus 阶梯爬坡 50 到 2000、driver 用 constant-vus 800 个长连接 WS、attacker 用 constant-arrival-rate 200 RPS 打伪造 ID 验证防御层。rider 的业务流是**先 WS 连上 `/ws/riders`、在 open 回调里发 preview → start → 等 15 秒看 driver_assigned**——**这个顺序是踩坑出来的**，必须先 WS 连上再发 start，否则 gateway 还没注册 conn，派单消息推不回来。SLO 写在 thresholds.js 里，比如 preview p99 < 300ms、attacker_blocked_by_bloom > 98%，k6 跑完不达标 exit 非 0，**可以直接挂 CI 门禁**。指标用 xk6 编译进 prometheus remote_write 扩展，跑时 push 给 Prometheus，**和服务端的 pull 指标在同一个 Grafana 面板上对照看**——黑盒和白盒双视角。一条命令跑完 summary JSON 留底做多轮对比。"

## 真实数字

- 17 分钟 / 276K 请求 / 1200 VU 峰值
- preview p99 = 44.55ms（SLO 300ms ✅）
- attacker 拦截 100%

## 找到的瓶颈

| 瓶颈 | 数据 | 类型 |
|---|---|---|
| auth bcrypt | p99 = 15s | CPU 慢哈希（**设计 tradeoff 不调 cost**） |
| 派单容量 | trip_assigned = 0.74% | 架构容量（非脚本 bug） |
| start 写入 | failure rate = 1.95% | Mongo 单实例无副本集 |

**关键金句**："这些丑数字我都如实写进 REPORT 不调阈值掩盖——**压测的价值是暴露真实容量边界，不是表演全绿报告**。"

## 高频追问

| 问 | 答 |
|---|---|
| **VU 和 iteration 区别？** | VU = 虚拟用户并发数；iteration = 一个 VU 跑完一遍 default function。VU 复用，跑完接着跑下一轮。 |
| **threshold 是干嘛的？** | SLO 编码成断言，没达标 k6 进程 exit 非 0，**可直接挂 CI 门禁**——这是 k6 区别于 wrk 的关键。 |
| **遇到最难的坑？** | trip_assigned 永远 0%。最后 curl 单独打 `/ws/riders` 看到 400 不是 101，定位到 **metrics 中间件没实现 http.Hijacker 接口**，gorilla 断言失败直接 400。8 行代码加 Hijack 方法修复。教训：**症状是死值就要怀疑测量装置本身**，不是被测对象。 |

# §5 跨服务可观测性与故障定位

## 一句话定位

> 微服务故障定位最痛的是日志散在多个服务里，靠 grep 30 分钟才能拼一次完整调用链。OpenTelemetry + Jaeger + Prometheus + Grafana 让任意请求的全链路 1 分钟内还原。

## 实现流程

### Trace 链路追踪（OTel + Jaeger）

1. 4 个服务都引入 OTel SDK + Jaeger exporter
2. HTTP 入口、gRPC 调用、RabbitMQ publish/consume 三类边界用 propagator 包装
3. propagator 把 trace_id 写进 HTTP header / gRPC metadata / RabbitMQ message header
4. 下游 service 起新 span 时 parent 自动指向上游 span
5. Jaeger UI 输入 trace_id 还原完整调用链

### Metrics 监控（Prometheus + Grafana）

1. `shared/metrics` 包统一定义 8 个指标，sync.Once 防重复注册
2. HTTP middleware 自动埋点（QPS + 延迟 Histogram）
3. 业务指标在关键路径手动埋点（Bloom / 锁 / 限流 / 幂等）
4. Prometheus 用 K8s ConfigMap 配 static_configs 抓 4 个服务
5. 同时开 `--web.enable-remote-write-receiver` 接 k6 推压测指标
6. Grafana 三个 ConfigMap 分离 datasource + provider + dashboard JSON，启动自动加载

### 真坑剖析（必背）

**症状**：压测 trip_assigned 永远 0%，但 HTTP 全 200。
**排查**：
1. 怀疑司机匹配链路 → RabbitMQ 通的，排除
2. 怀疑 GEO 查不到司机 → 逻辑正确，排除
3. **跳出业务思维**用 curl 单独打 `/ws/riders` → 400 不是 101，锁定在 WS 升级
4. 读 gorilla 源码，发现升级需把 ResponseWriter 断言成 `http.Hijacker`
5. **根因**：metrics 中间件包了一层 statusRecorder 抓 status code，**没实现 Hijacker 接口**
6. 修复 8 行代码加 Hijack 方法透传底层 conn

**方法论**：**症状—装置—被测对象三层归因**——症状是死值（0%/100%）时先怀疑装置（中间件、测试链路、测量工具），不是被测对象。

## 口头表述

> "可观测性分链路追踪和指标监控两块。**追踪**用 OpenTelemetry + Jaeger，4 个服务都引入 SDK，HTTP / gRPC / RabbitMQ 三类边界用 propagator 把 trace_id 跨进程传递，下游 span 自动 parent 指向上游，Jaeger UI 输入 trace_id 就能还原完整调用链。**指标**用 prometheus client_golang 统一定义 8 个 Counter / Histogram / Gauge，分流量层、消息层、并发控制层三块。HTTP 自动埋点走 middleware，业务指标在关键路径手动埋。Prometheus 用 K8s ConfigMap 配 static_configs 抓 4 个服务，同时开 remote-write-receiver 接 k6 推的压测指标，**两种模型按生命周期分工——长期服务 pull、短命压测 push**。Grafana 三个 ConfigMap 分离 datasource、provider 和面板 JSON，启动自动加载零手工配置。"

## 真坑剖析口头版

> "压测里发现 trip_assigned 永远 0%，但 HTTP 接口全 200。我先怀疑业务链路——查 RabbitMQ 消息流通的，查 GEO 撮合逻辑也对，**两轮排查都没结果**。最后用 curl 单独打 /ws/riders 看到 400 不是 101，定位到 WS 升级失败。读 gorilla 源码发现升级需要把 ResponseWriter 断言成 http.Hijacker，**而我的 metrics 中间件包了一层 statusRecorder 抓 status code，没实现这个接口**——gorilla 断言失败直接 400，WS 永远建不起来。8 行代码加个 Hijack 方法透传底层连接修复，重跑 trip_assigned 立刻从 0% 变成真值。**这件事让我固化了一个方法论：症状是死值时先怀疑测量装置本身，不是被测对象**。如果一开始就这么想，能省两轮错误归因。"

# §6 混沌测试与故障演练

## 一句话定位

> 单测和压测都是"按预期工作"，混沌验证"非预期下的退化"。生产事故几乎都是非预期组合——pod 挂、网络抖动、依赖部分不可用，这些只有主动注入才能验证。

## 通用流程（每个场景共用）

1. 写 CRD YAML 定义 kind、action、selector、duration
2. `kubectl apply -f xxx.yaml` 注入故障
3. 同时跑 k6 压测做负载背景
4. Grafana 加 annotation 竖线标记注入点
5. 业务指标跌破 SLO 那一刻打 mark、恢复回去那一刻再打一个，差值 = RTO
6. 跑完 `kubectl delete -f` 清理

## RTO / RPO（必背）

| 缩写 | 含义 | 一句话 |
|---|---|---|
| **RTO** | Recovery **Time** Objective | 故障到业务恢复的时长上限 |
| **RPO** | Recovery **Point** Objective | 故障可容忍的数据丢失量上限 |

## 场景 1：PodKill driver-service

### 流程

1. Chaos Mesh `PodChaos` 用 `pod-kill mode=one selector=app:driver-service`
2. K8s 检测 NotReady，新 pod 拉起（30s 量级）
3. 故障窗口内 rider 拉单的消息**在 RabbitMQ 队列堆积不丢**（persistent + 未 ack）
4. 新 pod 起来，重连 RabbitMQ，开始重投消费
5. 业务指标短暂下探后恢复

### 关键断言

- ✅ `idempotency_dedup_total` 增量 > 0（重投被识别为重复）
- ✅ Mongo trip 表**无重复派单**
- ✅ `trip_assigned_rate` 下探后 1min 内恢复

### 预期 RTO / RPO

- **RTO < 60s**（pod 启动 30s + 消费追平 10-20s）
- **RPO = 0**（消息持久化 + 重投 + 业务幂等三层兜底）

### 口头表述

> "T+0 杀掉 driver-service 一个 pod 后，K8s 检测 NotReady 拉新 pod，**故障 30 秒内 rider 拉单的消息在 RabbitMQ 队列堆积但不丢**——消息是 persistent + 未 ack 状态。新 pod 起来重连 RabbitMQ，重投消息开始消费。**关键断言是 idempotency_dedup_total 有增量**，证明重投消息被我的幂等状态机识别为重复跳过，Mongo trip 表也没出现重复派单。**预期 RTO 小于 60 秒，RPO = 0**——这个场景本质验证消息可靠性加幂等接管，RabbitMQ 当缓冲、幂等保证不重复，两层配合实现故障期间业务无感。"

## 场景 2：NetworkChaos delay redis 50ms

### 流程

1. Chaos Mesh `NetworkChaos` 用 `action=delay latency=50ms jitter=10ms correlation=25`
2. 给 Redis pod 注入网络延迟 60 秒
3. 所有走 Redis 的路径（限流、锁、幂等、Bloom、L2 缓存）延迟整体抬升
4. Redis client 默认 timeout 3 秒，远大于 50ms，**慢但不失败**
5. 注入结束延迟立即恢复

### 关键断言

- ✅ start P99 < 800ms（chaos 档 SLO，比 baseline 500ms 放宽）
- ✅ start 错误率 < 4%
- ✅ Bloom 拦截率仍 > 98%（防御层不退化）
- ✅ **不出现雪崩**（不应该因限流变慢导致请求堆积到 OOM）

### 预期 RTO / RPO

- **RTO ≈ 0**（注入结束立即恢复，不是真"故障"是降级容忍测试）
- **RPO = 0**（没数据丢失，只是慢）

### 口头表述

> "T+0 给 Redis pod 注 50ms 延迟加 10ms 抖动后，所有走 Redis 的路径——限流、接单锁、幂等、Bloom、L2 缓存——延迟都增加。**关键是不应该出错也不应该雪崩**：Redis client 默认 timeout 3 秒远大于 50ms，所以慢但不失败。我会断言 start P99 在 chaos 档 SLO 800ms 以内、错误率小于 4%、Bloom 拦截率仍超 98%。注入结束立即恢复，所以 RTO ≈ 0，RPO = 0。**这个场景验证降级路径和防雪崩**——如果限流脚本依赖 Redis 而没有客户端超时，单点 Redis 抖动会把整个 api-gateway 拖垮，这是要主动测出来的。"

## 高频追问

| 问 | 答 |
|---|---|
| **为什么用 Chaos Mesh 不手动 `kubectl delete pod`？** | 手动 kill 不可复现、不能精确控时间窗口、不能注入网络延迟/丢包。Chaos Mesh 是声明式 CRD，**可复现 + 可编排**。 |
| **设计第一个混沌场景选哪个？** | **PodKill**——YAML 最简单、出图最快、不挑环境、验证最基础的 K8s 自愈假设。NetworkChaos 等更激进的渐进式叠加，一口气全上踩坑概率高。 |
| **跑过完整流程没？** | 诚实答：**场景设计 + YAML 已落地，完整跑通是后续 TODO**，目前用于演示稳定性测试方法论和场景规划能力。 |

# §7 质量门禁与 CI 自动化

## 一句话定位

> 测试都写了，但开发提交时容易忘跑全量。把质量检查卡进 PR，PR 不绿合不进 main——GitHub Actions 两个 job 并行 lint + test，最小可演进结构。

## 实现流程

### Lint Job

1. `actions/checkout@v4` 拉代码
2. `actions/setup-go@v5` 装 Go，**开 `cache: true` 按 go.sum hash 缓存依赖**
3. `gofmt -l .` 检查格式，有 diff 直接 exit 1
4. `go vet ./...` 静态分析

### Test Job

1. **service container 起真实 mongodb**（mongo:6 + health check）
2. checkout + setup-go（带 cache）
3. `go build ./...` 验证全模块能构建
4. **跑并发安全测试 + 覆盖率检测**（统一一条命令）
5. 输出覆盖率 summary 到 stdout
6. **上传 coverage.out artifact**，PR 评审时可下载本地用 `go tool cover -html` 看红绿

### 关键决策

- **两 job 并行**：lint 失败立刻断不浪费 test 算力（用 `needs: lint`）
- **真实 mongo 不用 mock**：mongo-driver mock 容易和真实行为偏离（索引、CAS、writeConcern）
- **只 report 不卡覆盖率**：现阶段覆盖率分布不稳定，先看真实数据再加阈值
- **没用 golangci-lint**：渐进引入，先 gofmt + vet 跑稳，再叠加

## 口头表述

> "我用 GitHub Actions 配 PR 级卡口，两个 job 并行。**第一个 lint job 跑 gofmt 加 vet 快失败**——格式不对或静态分析报错立刻断，不浪费 test 算力。第二个 test job 用 service container 起真实 mongodb——**不用 mock 是因为 mongo-driver mock 测不出索引、CAS、writeConcern 这些真实行为**——然后跑并发安全测试加覆盖率检测，最后上传 coverage 报告做 artifact。**关键决策三条**：service container 不用 testcontainers 是为了简单；只 report 不卡覆盖率是因为现阶段分布不稳定先看真实数据；没用 golangci-lint 是渐进引入，先把基础跑稳再叠加。**演进路线图**：短期加 golangci-lint 加覆盖率门禁，中期加 k6 smoke 进 PR check，长期加 chaos nightly job。"

## 高频追问

| 问 | 答 |
|---|---|
| **为什么不一开始就加覆盖率门禁？** | 突然卡 80% 会让 PR 推不动。**渐进式**：先 report 收集真实分布 → 关键模块卡 85% → 全局卡 70%。 |
| **怎么防 flaky 测试腐蚀 CI？** | 找根因（80% 是 sleep / 随机数据）+ 隔离 build tag + 长期看板。我项目并发测试用 ready chan + atomic 不用 sleep，**目前没踩到 flaky**。 |
| **本地怎么复现 CI 失败？** | yaml 里所有命令本地可执行——gofmt -l、go vet、go test -race -cover。**CI 跑通三件套本地跑通就一致**。 |

**3 个标准应对**：

1. **方法论沉淀**："症状—装置—被测对象"三层归因方法论——从 WebSocket Hijacker 真坑里固化出来，是这个项目让我最有沉淀感的产出

1. **绝对不主动讲"我跑过 Round 3 完整混沌"** —— 没跑过，被问就说"设计完成、跑通是 TODO"
