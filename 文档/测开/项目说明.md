### 高频追问

**Q：你的金字塔三层比例是多少？**
- 单元测试最多（约 70%）、集成测试中等（约 25%）、E2E 最少（5%，因为跑得慢）。这是经典金字塔形状。我不会反过来搞冰激凌锥（E2E 多单测少）——那种维护成本高、定位难、跑得慢。

**Q：为什么集成测试不全部用真实 Mongo / Redis / RabbitMQ？**
- 真实依赖的成本是"跑得慢 + CI 难配 + 环境飘"。所以我分情况：
  - Redis：用 miniredis（in-process、纯 Go 实现 Redis 协议），单测里直接 `miniredis.RunT(t)` 起一个，跑完自动销毁，比起 testcontainers 快几个数量级
  - Mongo：必须用真 Mongo（mongo-driver mock 容易和真实行为偏离，比如索引、CAS 语义），在 CI 里用 service container 起
  - RabbitMQ：用 channel mock 验证消息路由逻辑就够，broker 行为另起 docker-compose 手工验证

**Q：`go test -race` 是什么原理？为什么必须开？**
- `-race` 是 Go 内置的 happens-before 数据竞争检测器（基于 ThreadSanitizer），在每次内存访问插桩，记录 goroutine 间的 happens-before 关系，发现冲突就报。代价是内存 + CPU 各 2-10 倍。
- **必须开**：我项目有大量 goroutine 并发（接单锁、消息幂等、缓存击穿、限流），没有 `-race` 就是裸奔；不开 `-race` 漏掉的并发 bug 会在生产偶发，最难复现。

**Q：Go benchmark 怎么写才有说服力？**
- 4 个要点：
  1. `b.ResetTimer()` 排除 setup 时间
  2. `b.N` 由框架决定，循环里写真实 workload
  3. 并发场景用 `b.RunParallel` + `pb.Next()`，模拟真实并发分布
  4. 跑完用 `benchstat` 比较多次运行的均值方差，不被单次偶发噪声骗
- 我项目里 `lock_bench_test.go` 跑出接单锁单实例 2.4k QPS、12 核 12.9k QPS——这是真数据，不是估算。

**Q：覆盖率到多少算够？**
- 没有统一答案。我的判断：
  - 关键路径（鉴权、支付、并发锁）≥ 85%
  - 业务 service 层 ≥ 70%
  - 工具/utility 类 ≥ 60%
  - 100% 覆盖是个陷阱——会被 if-err-return 这种琐碎分支充水，反而忽略真正的边界场景
- 我的 CI 现在只 report 覆盖率不卡，下一步会加阈值门禁。

### 接口测试覆盖（HTTP handler 层 · 共 35 个）

集成测试里**接口测试**是最大的一块，按模块拆解：

| 模块 | 测试数 | 覆盖路径 |
|---|---|---|
| 鉴权 handler | 17 | register × 6（happy / 手机号格式 / 弱密码 / 角色非法 / 重复手机号 / 坏 JSON）/ login × 3（happy / 密码错 / 用户不存在）/ refresh × 4（happy / 误用 access token / 被撤销 / 重复使用）/ logout × 3 / me × 1 |
| 鉴权 middleware | 8 | valid / 缺 header / 畸形 header / 过期 / refresh 误当 access / 撤销 / context 透传 / Bearer 大小写 |

**设计原则**：每个 endpoint 至少覆盖 happy path + 所有错误码分支 + 所有 token 边界，不留死区。

### 接口测试示例代码

最简单的边界断言型 handler 测试 —— **不依赖下游 gRPC、不需要 mock、~10 行**：

```go
// services/api-gateway/trip_handler_test.go
//
// 单元层面只覆盖「不触达下游 gRPC」的分支 —— 空 id 的 400。
// 200 / 404 真实链路在 tilt up 后的 E2E curl + k6 attackerFlow 压测覆盖。

func TestHandleGetTrip_EmptyID_400(t *testing.T) {
    req := httptest.NewRequest(http.MethodGet, "/trip/", nil)
    rec := httptest.NewRecorder()

    handleGetTrip(rec, req)

    if rec.Code != http.StatusBadRequest {
        t.Fatalf("status got %d want 400", rec.Code)
    }
}
```

**为什么这个例子有代表性**：
1. **用 `net/http/httptest`**：Go 原生 HTTP 测试工具，零依赖
2. **Request + ResponseRecorder 模式**：构造请求 → 调 handler → 断言 status code，所有 handler 测试都套这个模板
3. **明确测试边界**：注释里写清楚"哪些分支由这个单测覆盖、哪些由 E2E 覆盖"，避免重复测试
4. **`go test ./services/api-gateway/...` 跑全部 35 个测试 < 5 秒**，CI 里非常快

### 接口测试相关追问

**Q：handler 测试为什么不全部 mock 下游？**
- mock 增加维护成本——下游接口变了 mock 也要跟着改。我的策略：
  - **能不 mock 就不 mock**：trip handler 的 200 路径由 E2E + k6 压测覆盖，单测只测不触达下游的分支（如空 ID）
  - **必须 mock 时优先用 Go 的 interface**：依赖注入比 gomock 更轻
  - **真实数据库一律不 mock**：Mongo / Redis 用 service container 或 miniredis

**Q：为什么 Mongo repo 的"索引强制"测试一定要真 Mongo？**
- 唯一索引在 mock 里你可以自己写一个 map check，但 Mongo 真实行为还包括：复合索引顺序、稀疏索引、TTL 索引过期、`writeConcern` 投票。这些 mock 写不出来。**真依赖的价值就在这种"你以为对，跑起来不对"的细节。**

**Q：35 个测试里你印象最深的是哪个？**
- `TestHandleRefresh_UsedTwice` —— refresh token 用过一次后必须立刻失效，否则被中间人嗅探到就能无限续期。这个测试逼着我把 refresh token 设计成**一次性**（用过即撤销 + 发新的）。如果只测 happy path 就漏掉这个安全边界。

## 2. 并发正确性专项测试

### 口头表述（STAR）

> **S 背景**：分布式系统最难测的就是并发——锁互斥、消息幂等、缓存击穿这些只在 N 个 goroutine 同时进来时才暴露问题。
>
> **T 任务**：给四类并发风险设计**断言型测试**——不是"看起来对"，而是"用数字断言对"。
>
> **A 行动**：四个专项断言场景：
> 1. **分布式锁互斥**：100 goroutine 抢同一 tripID，断言只有 1 个成功
> 2. **消息幂等收敛**：100 goroutine 拿同一 MessageId 调消费，断言业务函数只被执行 1 次
> 3. **缓存击穿合并**：50 goroutine 同时 GetTripByID 同一 ID（L1+L2 都冷），断言 repo.GetTripByID 只被调 1 次（验证 singleflight）
> 4. **限流精确放行**：200 goroutine 1 秒内打同一 key（limit=10），断言精确放行 10 个，多 1 少 1 都不行
>
> **R 结果**：四个场景全部断言通过，全部跑 `go test -race` 验证无 data race。我把 dbLatency / ready chan / atomic counter 这些"制造并发窗口"的技巧固化进 test helper，可以复用。

### 数据钩子

| 场景 | 文件 | 关键断言 |
|---|---|---|
| 接单锁互斥 | `services/trip-service/internal/infrastructure/events/lock_bench_test.go`（含正确性） | `successCount == 1` |
| 消息幂等收敛 | `shared/messaging/idempotency_test.go` | `businessCallCount == 1` |
| 缓存击穿合并 | `services/trip-service/internal/service/service_singleflight_test.go` | `repo.getTripCalls == 1`（50 并发） |
| 限流精确放行 | `shared/cache/ratelimit_test.go` | `allowed == 10`（200 并发 limit=10） |

### 高频追问

**Q：怎么制造"N 个 goroutine 同时挤进来"的并发窗口？**
- 三招组合：
  1. **ready chan 起跑线**：所有 goroutine 先 `<-ready` 阻塞，主线程 `close(ready)` 同时放闸
  2. **dbLatency 拉长窗口**：mock repo 里 `time.Sleep(50ms)`，让 leader 慢慢打 DB，其他 goroutine 有时间堆到 singleflight.Do
  3. **sync.WaitGroup 收尾**：所有 goroutine 跑完再断言，避免主线程提前结束
- 没有这套技巧，50 个 goroutine 顺序进出，singleflight 永远合并不到。

**Q：你怎么证明 100% 互斥而不是侥幸？**
- 跑 `-race` + 跑 N 次（CI 里跑 1 次，本地手动 `go test -count=100` 跑 100 次）
- 加 stress 标志：`go test -race -count=100 -timeout=30s`
- 最终是统计置信而不是绝对证明——但 100 次 + race 检测都通过，比"我觉得没问题"强 N 个数量级

**Q：50 并发 singleflight 测试，万一 50 个 goroutine 没真正并发挤到一起呢？**
- 这就是 `dbLatency=50ms` 的作用：DB 调用故意慢 50ms，给所有 goroutine 至少 50ms 的窗口堆进来。
- 我额外校验：50 goroutine 总耗时应该在 50-150ms 之间（如果是 50ms*50=2.5s 就说明 singleflight 没合并）。这是隐式断言。

**Q：限流精确放行 10 是怎么做到精确的？为什么不是 9 或 11？**
- 因为我的限流是 Redis ZSET + Lua 脚本"删过期 → 计数 → 写入"三步原子执行。Lua 在 Redis 单线程里跑，N 个并发请求被串行处理，第 11 个进来时 count 已经是 10，Lua 直接返回拒绝。
- 测试断言：`allowed == 10 && rejected == 190`，少一个多一个都不行。

**Q：消息幂等的 `processing → done` 两态机怎么测？**
- 两个测试：
  1. 100 goroutine 并发：`businessCallCount == 1`（只有抢到 processing 状态的 goroutine 跑业务）
  2. 业务失败后重试：手动让业务函数 panic，验证 processing key 被 release，下一次重试能进入业务
- 第二个测试很关键——保证幂等不变成"永久卡死"。

## 3. 缓存正确性对照实验

### 口头表述（STAR）

> **S 背景**：多级缓存 L1+L2+singleflight 加起来是个复杂系统，每加一层都得证明它确实有效，不能凭感觉。
>
> **T 任务**：搭建可对比的测试床，量化每一层的真实贡献。
>
> **A 行动**：写了 `service_cache_compare_test.go`，同一个 workload 跑三个模式：
> - **Mode A：L2-only**（只有 Redis 缓存）
> - **Mode B：L1+L2**（加 Ristretto 本地缓存）
> - **Mode C：L1+L2+singleflight**（再加缓存击穿防护）
>
> 三个模式跑完后断言：
> - DB 调用次数：A=N、B=N/k（k 由命中率决定）、C=1（singleflight 合并）
> - Redis 命中次数：A=N-1、B=远低于 A、C=和 B 类似
> - 本地缓存命中次数：A=0、B>0、C>0
>
> **R 结果**：定量证明 L1 显著降 Redis 压力，singleflight 显著降 DB 压力，而不是"加了应该有用"。

### 数据钩子

```
services/trip-service/internal/service/
├── service_cache_test.go              三个 mode 共用的 helper
├── service_cache_compare_test.go      三模式对照断言
└── service_singleflight_test.go       singleflight 专项 50 并发断言
```

### 高频追问

**Q：为什么要做对照？不能直接看压测吞吐吗？**
- 压测看的是"端到端 RPS"，多变量混在一起：DB 也许快了、Redis 也许慢了、网络抖动一下都会改变结论。
- 对照测试**隔离变量**：同一 workload、同一 mock、只有缓存层不同，差异完全归因到缓存。这才是"科学"。

**Q：三个 mode 怎么共享同一份 workload？**
- 把"读多少次 + 读哪些 ID + 顺序" 抽成 `workload` 函数，三个 mode 用 `t.Run("mode-A", ...)` 复用。每个子测试独立的 service 实例 + 独立 counter，断言互不污染。

**Q：怎么断言"DB 调用次数 = N"？**
- 用 `mockTripRepository` 结构体，每次 `GetTripByID` 自增 `getTripCalls` 字段。子测试结尾断言 `repo.getTripCalls == 期望值`。
- 不用 `gomock` 那种声明式 mock——对计数断言来说太重，直接手写 mock 结构体更直观。

**Q：singleflight 不影响热路径性能吗？**
- singleflight 只在"L2 miss → DB 回源"段插一道 `sfg.Do`，热路径（L1 命中、L2 命中）完全不经过 singleflight。所以 0 性能影响。
- 我专门写了 `TestGetTripByID_SingleflightAllowsSequentialCacheHits` 验证这点：warm 后两次连续读，repo.getTripCalls 仍然 = 1，证明热路径没被 singleflight 拦截。

## 4. 端到端性能压测体系

> **本节大量复用 `../压测/面试四层速背.md`。下面只给"测开视角"的浓缩版，深度追问全部转去那份文件。**

### 口头表述（STAR · 60 秒）

> **S**：业务路径看着正常，但没人量化过它在突发流量下的真实表现。
>
> **T**：建立端到端压测体系，按"演唱会散场"模型（瞬时几千人同时打车）压出真实 SLO。
>
> **A**：
> - **k6** 写四阶段场景（预热→爆发→稳态→回落），rider / driver / attacker 三种角色并发
> - **xk6-output-prometheus-remote** 把 k6 客户端指标 push 到 Prometheus
> - **shared/metrics** 自建 8 个业务白盒指标（HTTP / RabbitMQ DLQ / Bloom 命中 / 锁竞争 / 幂等去重）
> - **Grafana** 出 4 行业务面板
> - **thresholds.js** 把 SLO 编码成构建产物——k6 跑完不达标进程 exit 非 0，可直接挂 PR
>
> **R**：17 分钟跑出 276,326 个 HTTP 请求、峰值 1200 VU。preview p99=44.55ms、attacker_blocked_by_bloom=100%；**同时故意把三个真瓶颈打出来**：auth p99=15s（bcrypt CPU 抢占）、派单容量 trip_assigned=0.74%（架构容量）、start 边缘 1.95% 失败（Mongo 单实例）。这些**如实写进报告，不调阈值掩盖**。

### 高频追问（速答版，详细见 `../压测/面试四层速背.md`）

**Q：为什么用 k6 不用 JMeter / Locust / wrk？**
- JMeter XML+GUI 重、CI 不友好；Locust Python GIL 限并发；wrk 只能打单 URL 不能表达多步骤业务流 + WebSocket；**k6 写 JS 像写代码、scenarios 能同时跑多角色、原生支持 WS、threshold 直接当断言**。

**Q：Prometheus 为什么 pull + push 混用？**
- k6 是短命客户端，pull 模型来不及 scrape，所以 k6 用 remote_write 推；服务端长期存活仍走 pull。**两种模型按生命周期分工**。

**Q：自建 8 个业务指标，不用 k6 自带的不行吗？**
- k6 指标是黑盒客户端视角（请求多久回来），业务指标是白盒服务端视角（消息堆没堆 DLQ、锁竞争多不多、Bloom 挡住没）。**定位瓶颈必须两边对照**。

**Q：高基数 label 怎么办？**
- path 模板化：`/trip/<24位hex>` 在中间件归一成 `/trip/:id` 再打 label。**没做这步 Prometheus 会因为 N 个不同 tripID = N 条独立时间序列而 OOM**——我真踩到过，重启 25 次。

**Q：SLO / SLA / SLI 区别？**
- SLI 是"我能测到的指标"（如 p99 延迟、错误率）
- SLO 是"我承诺自己达到的阈值"（如 p99<300ms）
- SLA 是"对外承诺的合同，违约要赔"（通常比 SLO 宽松）
- 测开主要工作在 SLI 和 SLO——把 SLO 编码进 thresholds.js 当卡口

**Q：发现真瓶颈后你做了什么？**
- 三件事：① 写进 REPORT.md 的"瓶颈分析"章节、② 给生产扩展方案（auth bcrypt 靠水平扩容 + 长 token、派单容量靠区域分片消费）、③ **不调阈值掩盖**。这是测开的职业操守。

## 5. 跨服务可观测性与故障定位

### 口头表述（STAR）

> **S**：微服务的故障定位最痛——一个请求穿过 HTTP → gRPC → RabbitMQ → MongoDB，日志散在 4 个服务里，靠 grep 日志 30 分钟才能拼出一次完整调用。
>
> **T**：搭一套可观测性能让"任意请求的全链路 1 分钟内还原"。
>
> **A**：
> - **OpenTelemetry SDK** 注入 4 个服务，统一通过 Jaeger 收集 trace
> - HTTP 入口、gRPC 调用、RabbitMQ publish/consume 三类边界全部包装 propagator，trace_id 跨进程传递
> - Prometheus + Grafana 出 4 行面板：流量 / 消息系统 / 并发控制 / 资源
> - 业务关键指标全部预留 trace_id label
>
> **R**：压测中靠这套体系定位到一个**最难的隐藏 bug**——`trip_assigned=0%`，详细见下文真坑剖析。

### 真坑剖析（必背 · 来源 `../压测/面试四层速背.md` 坑 1）

**现象**：第一轮 Round 2，`trip_assigned_within_15s` = **0%**，但 preview / start 的 HTTP 都 200，`ws_session_duration` avg 只有 166ms——像是 WS 一连上就断。

**排查路径**：
1. 先怀疑司机匹配链路坏 → 查 RabbitMQ 链路，消息流是通的，排除
2. 怀疑 GEO 查不到司机 → 查 driver-service GEOSEARCH，逻辑没问题
3. 用 `curl -i -H "Upgrade: websocket"` 直接打 `/ws/riders` → 返回 **400 Bad Request**，不是 101。锁定在 WS 升级这一步
4. 读 gorilla/websocket 源码：升级时它要把 `http.ResponseWriter` 断言成 `http.Hijacker` 拿底层 TCP conn

**根因**：metrics 中间件包了一层 `statusRecorder` 来记录响应状态码，但这个 wrapper **没实现 `http.Hijacker` 接口**。gorilla 一断言失败就直接 400，WS 永远建不起来。

**修复**：给 `statusRecorder` 加 8 行——一个 `Hijack()` 方法把底层 ResponseWriter 的 Hijack 透传出去。重跑 trip_assigned 立刻从 0% 变成真值。补了一个 channel 同步的回归单测（`go test -race` 防回归）。

**测开教训**："**症状是死值（永远 0%）就要怀疑测量/链路装置本身，不是被测对象**。我盯着 0% 做了两轮错误归因，最后靠'变量法'——curl 单独打 WS 看到 400，才跳出业务思维定位到中间件。"

### "症状—装置—被测对象"三层归因方法论

这是我从这个坑里固化出来的方法论：

| 层级 | 含义 | 例子 |
|---|---|---|
| **症状层** | 我看到的现象 | trip_assigned=0% |
| **装置层** | 我的测量工具 / 测试链路 / 中间件 | metrics 中间件 wrapper |
| **被测对象层** | 真正的业务逻辑 | trip-service 匹配逻辑 |

**规则**：症状是死值（0% / 100%）或异常规律时，**先怀疑装置层**——不然就会像我那样在被测对象层瞎查两轮。

### 高频追问

**Q：trace_id 怎么打？怎么跨服务串？**
- 用 OpenTelemetry SDK，每个 span 自动有 trace_id；跨服务调用时 propagator 把 trace_id 写进 HTTP header / gRPC metadata / RabbitMQ message header，下游 service 起新 span 时 parent 自动指向上游。
- 关键是边界都要包装：HTTP middleware、gRPC interceptor、RabbitMQ publish/consume hook，缺一个就断链。

**Q：业务指标和 k6 指标分工？**
- k6 指标是黑盒：客户端视角的 RPS / 延迟 / 错误率
- 业务指标是白盒：服务端的 DLQ 深度 / 锁竞争次数 / Bloom 拦截率 / 幂等去重计数
- 压测中两者对照看：客户端 P99 飙了，业务指标里 DLQ 在堆，就锁定消息链路是瓶颈

**Q：Grafana 4 行面板怎么设计？**
- Row 1：流量（QPS / 延迟分位 / 错误率）
- Row 2：消息系统（RabbitMQ 队列深度 / DLQ / 消费速率）
- Row 3：并发控制（Bloom 命中 / 锁竞争 / 幂等去重）
- Row 4：资源（CPU / Memory / Pod 数量）
- 一行一个关注点，按"流量进来→消息流转→并发处理→资源消耗"的因果链组织

**Q：链路追踪开销大不大？**
- OTel 默认 100% 采样，开销约 1-3% CPU + 少量内存。生产可降到 1-10% 采样 + 关键链路 always-on。我项目是开发环境 100% 采样。

## 6. 混沌测试场景设计

> **如实声明**：混沌测试场景**已设计但未在本地完整跑通**——主要展示稳定性测试的方法论和场景规划能力，不编造结果数字。

### 口头表述（STAR）

> **S**：单测和压测都是"按预期工作"，但生产事故几乎都是"非预期"——pod 突然挂、网络抖动、依赖部分不可用。这些必须主动注入才能验证。
>
> **T**：基于 Chaos Mesh 设计一套故障注入时间线，验证系统的 RTO / RPO 和自愈能力。
>
> **A**：设计了四阶段时间线，叠在压测主轴上跑：
>
> ```
> T+8min   [PodChaos]      pod-kill driver-service     —— 验证副本自愈 + 派单接管
> T+9min   [NetworkChaos]  delay redis 50ms             —— 验证限流/缓存对网络抖动的容忍
> T+10min  [NetworkChaos]  loss mongodb 10%             —— 验证 RabbitMQ 重投 + 消费端幂等
> T+11min  [PodChaos]      pod-kill api-gateway         —— 验证 WS 客户端重连
> ```
>
> **R**：场景以 Chaos Mesh CRD YAML + Workflow 时间线编排的方式落地（YAML 已写，详见 `loadtest/chaos/`），Round 3 完整跑通是后续 TODO。但**场景设计本身已经在 REPORT.md 的"场景时间线"章节锁定**。

### 高频追问

**Q：为什么用 Chaos Mesh 不手动 `kubectl delete pod`？**
- 手动 kill **不可复现**、**不能精确控时间窗口**、**不能注入网络延迟/丢包**。Chaos Mesh 是声明式 CRD（PodChaos / NetworkChaos / IOChaos / Workflow），能编排"T+8 kill driver、T+10 给 Mongo 注 10% 丢包"这种**时间线编排 + 可复现**。
- 一句话：要的是可复现、可编排，手动 kill 做不到。

**Q：RTO / RPO 怎么测？**
- **RTO (Recovery Time Objective)**：从故障发生到业务恢复的时间。测法：业务指标（如 `trip_assigned_rate`）跌破 SLO 那一刻打个 mark，恢复到 SLO 那一刻打另一个 mark，差值就是 RTO
- **RPO (Recovery Point Objective)**：故障后丢失的数据量。测法：注入前后对比 `rabbitmq_consumed_total` 计数、对比 DB 中订单数，差值就是 RPO
- 我项目的 RPO 设计目标是 0（所有消息最终通过 RabbitMQ 重投处理），RTO 目标是 < 60s

**Q：PodKill driver-service 后怎么验证幂等接管？**
- 三步：
  1. PodKill 前的派单消息已经在 RabbitMQ 里
  2. PodKill 触发后，K8s 重启新 pod，新 pod 重连 RabbitMQ 重新消费这些消息
  3. **关键断言**：`idempotency_dedup_total` 计数有增量（说明重投消息被识别为重复）、`trip` 表里这批订单的派单字段没变（说明没重复派单）
- 这把混沌测试和我前面做的"消息幂等"绑死了——幂等不只是单测里证明"counter==1"，混沌里也得证明"实际 PodKill 重投不会双派"

**Q：限流和混沌怎么配合？**
- 注入 Redis 50ms 延迟时，限流脚本的执行也会被拖慢，可能误伤正常请求。这就是混沌的价值——单测里限流 P99=0.9ms 是"理想态"，混沌里能看到"依赖抖动下的真实表现"

**Q：你怎么知道注入故障期间业务**恰好**该挂的挂、不该挂的不挂？**
- 提前定义 invariants（不变量）：
  - PodKill driver-service：rider 那侧请求 5 秒内自动 retry 到新 pod，不应直接 500
  - NetworkChaos loss mongo：写请求最多失败 10%，但 RabbitMQ 应承接重投保证最终一致
  - PodKill api-gateway：WS 客户端应自动重连，丢的是中间几秒消息，不是连接永久断
- 这些 invariants 应当编码成 Prometheus alert rules + Grafana 注释竖线，混沌跑完肉眼复盘

**Q：假如让你给一个新服务设计第一个混沌场景，你选哪个？**
- **PodKill**，原因：
  1. YAML 最简单（~10 行）
  2. 出图最快（pod 不见 + 重启）
  3. 能立刻验证最基础的"副本数 > 1 + K8s 自愈"假设
  4. 不挑环境（NetworkChaos 在某些容器运行时上会失败）
- 跑通 PodKill 再叠 NetworkChaos / IOChaos，**渐进式**比"一口气全上"安全得多

## 8. 收尾 - 流程 / 协作 / 度量观

### 我的测开度量观

- **真值优先**：跑出 auth p99=15s、trip_assigned=0.74% 这些"丑数字"如实写进 REPORT，不调阈值掩盖
- **断言数字化**：100% 互斥、50:1 合并、200 并发精确放行 10——所有正确性都用数字断言，不用"应该对"
- **每个 bug 补回归**：WebSocket Hijacker bug 修完后补了 channel 同步的回归单测，避免未来重新踩
- **测试代码也走 review**：测试代码和业务代码同 PR 提交，review 标准一致

### 我对测试代码质量的标准

- 测试名要能读出意图：`TestGetTripByID_SingleflightCoalescesConcurrentMisses` 比 `TestGetTripByID3` 强一个数量级
- 不要 sleep——用 channel / WaitGroup / atomic 同步；只在故意"制造窗口"时才 sleep
- 一个测试只断言一件事（除非是对照测试）
- 跑得快——单测套件总跑时 < 30 秒，不然没人愿意每次 PR 等

### 如果让我从 0 给一个新项目建测试体系，第一周做什么？

1. Day 1-2：把测试金字塔骨架搭起来——单测 + 集成测试目录约定 + 一个示例
2. Day 3：写 `.github/workflows/ci.yml` 跑 `go test -race + vet + gofmt`，把骨架卡进 PR
3. Day 4：识别关键并发路径（锁 / 幂等 / 缓存），每个写一个断言型并发测试
4. Day 5：用 k6 写一个 smoke 场景跑 30 秒，进 CI 当 PR check
5. **第二周**才开始压测和混沌——基础不打好就上重武器是反模式
