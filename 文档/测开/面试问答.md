## A. 测试基础理论

### A1. 测试金字塔三层是什么？为什么单测多 E2E 少？

**通用答**：金字塔由下到上是 unit / integration / E2E。底部多顶部少，是因为单测**跑得快、定位准、隔离性好**，E2E **跑得慢、定位难、维护贵**。倒过来（冰激凌锥）就是反模式。

**我项目里的证据**：
- 单测：`shared/auth/`、`shared/cache/`、`shared/messaging/`，纯函数 + miniredis，套件跑时 < 5s
- 集成测试：`services/api-gateway/auth_handler_test.go` 真 HTTP + Mongo、`driver_consumer_test.go` 走 RabbitMQ channel
- E2E：`loadtest/k6/scenarios/concert.js` 17 分钟完整业务流，只在本地手动 + CI nightly 跑

---

### A2. unit / integration / E2E / smoke / load / chaos 各自定位是什么？

**通用答**：

| 类型 | 范围 | 跑时 | 何时跑 |
|---|---|---|---|
| unit | 单函数/单类 | ms | 每次 commit |
| integration | 多模块联调（含依赖） | s | 每次 PR |
| E2E | 完整业务流 | min | nightly / release |
| smoke | E2E 的子集，"能跑通就行" | < 1min | 每次部署 |
| load | E2E + 高并发 | 10min+ | 周/月级 |
| chaos | E2E + 故障注入 | 10min+ | nightly / pre-release |

**我项目里的证据**：smoke = `k6 scenarios/smoke.js`、load = `concert.js`、chaos = `loadtest/chaos/schedule.yaml`（已设计未跑完）

---

### A3. 黑盒测试 vs 白盒测试，你怎么用？

**通用答**：
- 黑盒：只看输入输出，不关心内部实现（用户视角）
- 白盒：基于代码结构和分支（开发视角）
- 实践中两者必须**结合**：黑盒覆盖"用户期望"，白盒覆盖"代码路径"

**我项目里的证据**：
- 黑盒：k6 压测从客户端打 HTTP / WS，只看请求成败和延迟
- 白盒：`shared/metrics` 8 个自建业务指标（DLQ 深度、Bloom 命中、锁竞争）暴露内部状态
- 两者对照：客户端看到 P99 飙 → 业务指标 DLQ 在堆 → 定位到消息链路瓶颈

---

### A4. 覆盖率多少算够？你怎么看 100% 覆盖？

**通用答**：没有统一答案。**关键路径 ≥ 85%、业务层 ≥ 70%、utility ≥ 60%** 是合理参考。**100% 覆盖是反模式**——会被 `if err != nil` 这种琐碎分支充水，反而忽略真正的边界场景。

**我项目里的证据**：
- CI 现在只 report 不卡（`go tool cover -func` 输出总行），等覆盖率分布稳定再加阈值
- 关键路径（鉴权、并发锁、幂等）单测密度高，但具体百分比要等 CI 跑几次拉数据

## B. 自动化与框架

### B1. 你用什么工具栈做自动化？为什么不搭一套 Pytest？

**通用答**：项目是 Go，**用 Go 原生 `testing` + miniredis + service container 是最低摩擦方案**。再搭 Pytest 等于跨语言维护两套断言风格 + 双倍工具链负担。

**我项目里的证据**：
- `go test ./...` 一条命令跑全部
- miniredis 在 import 里直接 `miniredis.RunT(t)`，不需要外部 docker
- Mongo 用 service container（CI）+ tilt（本地）
- Benchmark 直接 `go test -bench=.`，不引入额外框架

---

### B2. 集成测试如何不依赖真实环境？

**通用答**：分依赖类型用不同方案：
- Redis → miniredis（in-process 实现 Redis 协议）
- 消息队列 → channel mock 或 testcontainers
- Mongo → 必须真，因为索引和 CAS 语义无法 mock
- HTTP 外部依赖 → `httptest.NewServer` 或 `gock`

**我项目里的证据**：
- `shared/cache/ratelimit_test.go` 用 `miniredis.RunT(t)` 起 in-process Redis，跑完自动销毁
- `services/api-gateway/auth_handler_test.go` 用 `httptest.NewServer` 起测试 HTTP server
- Mongo 用真实实例（CI 是 service container，本地是 tilt 起的）

---

### B3. Go 的 `-race` 检测器原理？为什么并发测试必须开？

**通用答**：`-race` 是 Go 内置的 happens-before 数据竞争检测器（基于 ThreadSanitizer），编译时插桩每个内存访问，运行时记录 goroutine 间的 happens-before 关系，发现冲突立刻报告。代价是内存 + CPU 各 2-10 倍。

**我项目里的证据**：
- CI workflow 强制 `go test -race -cover ./...`
- 项目里 100 司机抢锁、100 goroutine 幂等、50 缓存击穿这些场景**没有 -race 就是裸奔**
- 修 WebSocket Hijacker bug 时补的回归单测，用 channel 同步避免 sleep，专门为 race 友好

---

### B4. benchmark 怎么设计才有说服力？

**通用答**：4 个要点：
1. `b.ResetTimer()` 排除 setup 时间
2. `b.N` 由框架决定，循环里写真实 workload
3. 并发用 `b.RunParallel` + `pb.Next()`
4. 跑多次用 `benchstat` 比较均值方差

**我项目里的证据**：
- `lock_bench_test.go` 用 `b.RunParallel` 模拟多司机并发抢锁，跑出单实例 2.4k QPS、12 核 12.9k QPS
- `ratelimit_bench_test.go` 跑出限流 P99 0.90ms / 4.5k QPS
- `bloom_bench_test.go` 跑出 20w ObjectID 误判率 0.118%
- 数据写进 `文档/压测/基准测试文档.md`，不是凭感觉

## C. 性能 / 压测

### C1. k6 / JMeter / Locust / wrk 怎么选？

**通用答**：
| 工具 | 适合 | 不适合 |
|---|---|---|
| k6 | JS 脚本、多角色 scenario、原生 WS、CI 友好 | 学习成本中 |
| JMeter | GUI 调试、企业团队 | CI 不友好、写复杂流程别扭 |
| Locust | Python 团队 | GIL 限并发 |
| wrk | 单 URL 极致性能 | 不能多步骤业务流 |

**我项目里的证据**：选 k6，因为业务流是"登录 → preview → start → 等 WS 派单"多步骤 + WS 长连接 + 多角色并发（rider / driver / attacker），其他工具表达不了。

---

### C2. SLO / SLA / SLI 区别？阈值怎么定？

**通用答**：
- **SLI**：可观测的指标（如 p99 延迟、错误率）
- **SLO**：内部承诺的目标（如 p99 < 300ms）
- **SLA**：对外签的合同，违约要赔（通常比 SLO 宽松）

**阈值怎么定**：3 步——
1. 拉历史数据看分布
2. 业务方谈"用户能容忍的体验"
3. 在 SLO 和 SLA 之间留 20-50% 缓冲

**我项目里的证据**：`loadtest/k6/thresholds.js` 把 SLO 编码：preview p99 < 300ms、start p99 < 500ms、Bloom 拦截率 > 98%。这些直接进 k6 断言，不达标进程 exit 非 0，可挂 PR 卡口。

---

### C3. Prometheus pull vs k6 remote_write，为什么混用？

**通用答**：
- pull：Prometheus 定时 scrape 服务的 `/metrics`，适合长期存活的服务端
- remote_write（push）：客户端主动推，适合短命进程

**我项目里的证据**：
- 4 个微服务暴露 `/metrics`，Prometheus 定时 scrape → pull
- k6 跑 17 分钟就退，pull 模型来不及抓 → 用 `xk6-output-prometheus-remote` 推
- 两种模型**按生命周期分工**

---

### C4. 高基数 label 的危害？怎么避免？

**通用答**：Prometheus 每个不同 label 值 = 一条独立时间序列。如果用户 ID、tripID 这种基数高的字段做 label，会**时间序列爆炸 + Prometheus OOM**。

**我项目里的证据**：第一轮压测时 path label 用了原始 URL（`/trip/abc`、`/trip/def`），Prometheus 31 小时内 OOMKilled 25 次。解决：在 metrics 中间件里把 `/trip/<24位hex>` 模板化成 `/trip/:id` 再打 label。同时 Prometheus memory limit 从 512Mi → 1Gi 兜底。

---

### C5. 压测发现 auth p99=15s，你会怎么定位和处理？

**通用答**：4 步——① 看链路追踪定位耗时段、② 区分是 CPU 密集还是 IO 密集、③ 判断是否 bug 还是设计 tradeoff、④ 给扩展方案

**我项目里的证据**：auth p99=15s 是**bcrypt 故意的慢哈希**（抗暴力破解），bcrypt cost=10 单次 ~100ms，爆发登录时 CPU 抢占。**不能降 cost**——那是安全设定。处理：① 写进 REPORT.md 瓶颈分析章节、② 给生产扩展方案（api-gateway 水平扩容 + 长 token 摊薄登录频率）、③ 不调阈值掩盖。

## D. 并发 / 分布式正确性测试

### D1. 怎么测一个分布式锁是真互斥？

**通用答**：N 个 goroutine 同时抢同一 key，断言只有 1 个成功 + 跑 `-race`。N 越大越有说服力（100 起步）。

**我项目里的证据**：
- `lock_bench_test.go` 跑 100 司机抢同一 tripID
- 用 `sync.WaitGroup` + `atomic.Int32` 计数成功 goroutine
- 断言 `successCount == 1`
- 跑 `go test -race -count=100` 共 100 次都通过

---

### D2. 怎么测消息幂等？

**通用答**：100 goroutine 拿同一 MessageId 调消费，断言**业务函数只被执行 1 次**。验证 `processing → done` 状态机收敛。

**我项目里的证据**：
- `shared/messaging/idempotency_test.go` 100 goroutine 并发
- mock 业务函数用 `atomic.AddInt32(&callCount, 1)` 计数
- 断言 `callCount == 1` 且 `99 个 goroutine 跳过`
- 第二个测试验证业务失败时 processing key 被 release，重试能进入业务（不变永久卡死）

---

### D3. 怎么测缓存击穿防护是否生效？

**通用答**：N 个 goroutine 同时 GetX 同一 key（L1+L2 都冷），断言 repo 只被调 1 次。**关键是制造并发窗口**——mock repo 加 sleep。

**我项目里的证据**：
- `service_singleflight_test.go` 50 goroutine 同一 tripID
- mock repo 加 `dbLatency = 50ms` 给所有 goroutine 时间堆到 sfg.Do
- ready chan 起跑线对齐，close(ready) 同时放闸
- 断言 `repo.getTripCalls == 1`（50 并发只触发 1 次 DB）

---

### D4. 如何不引入随机时序仍能稳定复现并发问题？

**通用答**：避免 sleep，用 channel / WaitGroup / atomic 同步；故意延长窗口时才 sleep（且 sleep 时长应远大于并发分布范围）。

**我项目里的证据**：
- ready chan 起跑线：所有 goroutine 先 `<-ready` 阻塞，主线程 `close(ready)` 同时放闸
- sync.WaitGroup 收尾：所有 goroutine 跑完才断言，避免主线程提前结束
- atomic.Int32 计数：无锁原子计数，不引入 mutex 影响时序
- 仅在制造"50ms 并发窗口" 这种**意图明确的等待**时才 sleep

---

## E. 故障 / 混沌

### E1. 混沌工程的目的是什么？为什么不只靠单测？

**通用答**：单测验证"按预期工作"，混沌验证"非预期下的退化"。生产事故几乎都是非预期组合——pod 挂、网络抖动、依赖部分不可用。这些只有主动注入才能验证。

**我项目里的证据**：单测里限流 P99=0.9ms 是"理想态"，混沌注入 Redis 50ms 延迟时能看到"依赖抖动下的真实表现"。这是单测永远测不到的。

---

### E2. RTO / RPO 怎么测量？

**通用答**：
- **RTO（Recovery Time Objective）**：故障到恢复的时间。测法：业务指标跌破 SLO 那一刻打 mark，恢复那一刻打另一个 mark，差值就是 RTO
- **RPO（Recovery Point Objective）**：故障后丢失的数据量。测法：对比故障前后的消息计数 / 订单计数

**我项目里的证据**：设计目标 RTO < 60s、RPO = 0（所有消息通过 RabbitMQ 重投保证最终一致）。Round 3 chaos 跑完后会回填实测数据到 REPORT.md。

---

### E3. 你设计了 4 个 chaos 场景，逐个讲讲预期验证什么？

**通用答**：

| 场景 | 验证目标 |
|---|---|
| T+8 PodKill driver-service | 副本数 ≥ 2 时 K8s 自愈 + 派单接管 + 消息重投幂等不重复派 |
| T+9 NetworkChaos delay redis 50ms | 限流/缓存对网络抖动的容忍 + 是否产生雪崩 |
| T+10 NetworkChaos loss mongodb 10% | 写失败时 RabbitMQ 重投承接 + 最终一致性 |
| T+11 PodKill api-gateway | WS 客户端自动重连 + 中间几秒消息丢失但连接恢复 |

**我项目里的证据**：场景已在 `loadtest/chaos/schedule.yaml` 落地为 Chaos Mesh CRD Workflow，Round 3 跑通是 TODO。

---

### E4. 假如让你给一个新服务设计第一个混沌场景，你选哪个？

**通用答**：**PodKill**。原因：
1. YAML 最简单（~10 行）
2. 出图最快（pod 消失 + 重启）
3. 验证最基础的"副本数 > 1 + K8s 自愈"假设
4. 不挑环境（NetworkChaos 在某些容器运行时上会失败）

**渐进式更安全**——跑通 PodKill 再叠 NetworkChaos / IOChaos，比一口气全上稳得多。

## F. CI / 质量门禁

### F1. 你的 PR 卡口是什么？

**通用答**：lint（gofmt + vet）+ build + test（-race -cover）+ 覆盖率报告。lint 单独 job 快失败。

**我项目里的证据**：见 `.github/workflows/ci.yml`：
- Job 1 lint：gofmt + vet
- Job 2 test：service container 起 mongodb，go build + go test -race -cover，上传 coverage artifact
- 两个 job 并行，lint 失败立刻断
- 详细见 `./CI 设计说明.md`

---

### F2. 覆盖率门禁怎么定？

**通用答**：分模块定，不要一刀切。
- 关键路径（鉴权 / 并发锁 / 幂等）：≥ 85%
- 业务 service 层：≥ 70%
- utility：≥ 60%
- 100% 覆盖是陷阱——会被琐碎分支充水

**我项目里的证据**：当前只 report 不卡，等覆盖率分布稳定再加阈值。**渐进式引入**——突然卡 80% 会让 PR 推不动。

---

### F3. 怎么防止 flaky 测试腐蚀 CI？

**通用答**：3 招——
1. 找根因，80% 的 flaky 是依赖时序（sleep、随机数据），改成 deterministic
2. 隔离运行，flaky 测试单独 build tag、独立 job、允许重试 3 次
3. 长期看板，记录每个测试的失败率，超过 1% 限期修复

**我项目里的证据**：项目目前没踩到 flaky，因为并发测试用 ready chan + atomic 而不是 sleep。

## G. 故障定位方法论

### G1. 讲一个你定位过的最难的 bug

**通用答**：直接讲 WebSocket Hijacker bug，固化"症状—装置—被测对象"三层归因方法论。

**完整剧本**：
- **症状**：压测发现 `trip_assigned_within_15s = 0%`，但 preview / start HTTP 都 200
- **错误归因 1**：怀疑司机匹配链路 → 查 RabbitMQ 通的
- **错误归因 2**：怀疑 GEO 查不到司机 → driver-service 逻辑正确
- **跳出业务思维**：用 `curl -i -H "Upgrade: websocket"` 单独打 `/ws/riders` → 返回 400 不是 101
- **定位**：读 gorilla/websocket 源码，发现升级需要把 ResponseWriter 断言成 `http.Hijacker`
- **根因**：metrics 中间件包了一层 statusRecorder 来记状态码，**没实现 Hijacker 接口**
- **修复**：加 8 行 Hijack() 方法透传底层；补 channel 同步的回归单测
- **教训**：**症状是死值（0% / 100%）时先怀疑装置，不是被测对象**

---

### G2. 看到"接口 P99 飙升"先查什么？

**通用答**：5 个常见嫌疑——
1. DB 慢查询（看 mongo profile / slow log）
2. GC（Go runtime 看 STW 时长、heap size）
3. 限流（看限流命中数是否突增）
4. 上游依赖（看 RPC 延迟分位）
5. CPU / 内存饱和（看 Pod 资源使用）

按"近因到远因"顺序查。

**我项目里的证据**：auth p99=15s 一开始也是这么查的——排除 DB、排除 GC，最后定位到 bcrypt CPU 抢占（是设计 tradeoff 不是 bug）。

---

### G3. 测出了 bug 但开发说"我本地不复现"，你怎么办？

**通用答**：3 步——
1. 列差异：环境（OS / 依赖版本）、数据（dataset / seed）、并发（VU 数）
2. 给最小复现：精简到一个 shell 命令 + 一个数据文件
3. 录屏 / 截图 / 日志打包，让开发能离线分析

**我项目里的证据**：调试 WebSocket Hijacker bug 时，给开发的是 `curl -i -H "Upgrade: websocket" http://localhost:8081/ws/riders` 一行命令 + 返回 400 截图，开发立刻能复现。

## H. 软技能 / 流程

### H1. 测开和开发的边界你怎么看？

**通用答**：边界是**协作焦点不同**，不是**能力分割**。
- 开发：建造系统、首先对功能正确性负责
- 测开：质量基础设施 + 验证方法论 + 度量体系

**好的测开必须懂开发**——不然写不出有意义的测试。我项目里我**既开发了业务（CV 第一项）也补了测开体系（CV 第二项）**，这种"双视角"在面试中是加分项。

---

### H2. 测试和需求文档冲突时你怎么办？

**通用答**：
1. 先确认是真冲突还是误解（90% 是需求模糊）
2. 拉产品 + 开发对齐，把决议写进需求文档而不是测试代码注释
3. 我倾向"测试是需求的可执行版本"——决议一定要在文档里留底

**我项目里的证据**：`loadtest/k6/thresholds.js` 里 SLO 阈值就是产品和我对齐后写死的，不在测试代码里 hardcode "magic number"。

---

### H3. 你的测试代码也需要 review 吗？标准是什么？

**通用答**：**必须 review**，标准和业务代码一致。三条额外标准：
1. 测试名要能读出意图（`TestGetTripByID_SingleflightCoalescesConcurrentMisses` > `TestGetTripByID3`）
2. 一个测试只断言一件事
3. 不要 sleep，用 channel / WaitGroup / atomic 同步

**我项目里的证据**：测试代码和业务代码同 PR 提交；CI 卡口对测试代码生效（gofmt / vet / race）。

## 收尾：被问"还有什么要补充的"怎么回答？

3 个标准应对：

1. **主动说局限**："这次压测坐标是均匀随机近似，没还原'演唱会散场起点集中、终点长尾'的真实分布；司机是 k6 模拟的 WS 客户端不是真手机 GPS。压测结果有它的适用范围。"

2. **抛"演进路线图"**："基础打完了，下一步会加 golangci-lint、k6 smoke 进 PR check、chaos-mesh 进 nightly job、覆盖率阈值门禁。"

3. **强调度量观**："我做测开最大的收获是'真值优先'——auth 15s、trip_assigned 0.74% 这些丑数字我都如实写进 REPORT，不调阈值掩盖。压测的价值是暴露真实容量，不是表演全绿报告。"
