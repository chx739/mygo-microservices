# 2. 测试金字塔分层与覆盖

## 一句话定位

> 把测试分成四层金字塔——**每一层用对工具，跑时分开但产出统一**。

## 四层实现流程

| Layer | 范围 | 覆盖对象 | 工具 | 跑时 |
|---|---|---|---|---|
| **L1 单元测试** | 单函数、纯逻辑、零外部依赖 | JWT 签发、密码哈希、布隆、本地缓存、消息构造 | Go 原生 `testing` | < 5s |
| **L2 集成测试** | 多组件协作 + 真实依赖 | HTTP handler 全套、middleware、Mongo repo、Redis 操作 | miniredis / 真 Mongo / httptest / amqp channel mock | < 30s |
| **L3 并发安全验证** | 横切关注点（不是单独一层） | 所有测试统一 `-race` 跑 | Go 内置 race detector（基于 ThreadSanitizer） | CPU 慢 2-10× |
| **L4 端到端压测** | 真实业务路径，跨多服务/网络/MQ | rider/driver/attacker 三角色完整业务流 | k6 + xk6 + Prometheus + Grafana | smoke 30s / concert 17min |

## 口头表述

> "我把测试体系分成四层金字塔——底层单元测试覆盖 JWT、密码哈希、布隆、本地缓存这种纯逻辑函数，套件总跑时不到 5 秒。第二层集成测试覆盖 HTTP handler 全套加 middleware 加 Mongo repo，Redis 用 miniredis 起 in-process 实例，Mongo 必须用真实例因为索引和 CAS 行为 mock 不出来。第三层不是独立层而是横切关注点——所有测试统一 -race 跑，验证并发安全，代价是 CPU 慢 2-10 倍但漏掉的并发 bug 在生产偶发最难复现，所以必须开。最顶层是 k6 端到端压测，17 分钟一轮覆盖真实业务路径。**这四层的关键不是数量而是分工——底层快跑频次高，顶层慢但接近真实**。"

## 高频追问

| 问 | 答 |
|---|---|
| **金字塔三层比例？** | 单测 70%、集成 25%、E2E 5%。倒过来变冰激凌锥是反模式。 |
| **覆盖率多少？** | 关键路径（鉴权/支付/锁）≥85%、业务 service ≥70%、utility ≥60%。100% 是陷阱。 |

# 3. 并发正确性专项断言（四个场景）

## 一句话定位

> 分布式系统最难测的就是并发——N 个 goroutine 同时进来时才暴露的问题。我针对四类典型并发风险**用数字断言而不是"看起来对"**。

## 通用方法论（每个场景都用）

1. **制造并发窗口**：mock 依赖里加 sleep / dbLatency，给 N 个 goroutine 时间堆到同一段
2. **ready chan 起跑线**：所有 goroutine 先 `<-ready` 阻塞，主线程 `close(ready)` 同时放闸
3. **sync.WaitGroup 收尾**：所有 goroutine 跑完再断言
4. **atomic 计数**：无锁原子计数，不引入额外 mutex 影响时序
5. **跑 `-race` + `-count=10`**：多次稳定验证

## 场景 1：分布式锁互斥（接单锁）

**流程**：100 goroutine 同时调 `TryAcquireTripAcceptLock(同一 tripID)` → atomic 计成功次数 → **断言 == 1**。释放用 Lua 脚本"比较 owner 再删"防误删。

**口头表述**：
> "100 个 goroutine 模拟 100 个司机同时抢同一个 tripID 的极限场景，用 atomic 计数成功次数。**断言只有 1 个成功，99 个失败**——这就是分布式锁的核心契约。释放锁用 Lua 脚本做'比较 owner 再删'的原子操作，防止 TTL 自动释放后别的 goroutine 抢到新锁、我再 DEL 误删的窗口。-race + count=10 跑过，完全稳定。"

**真实数字**：100% 互斥 / benchmark 单实例 2.4k QPS、12 核 12.9k QPS / P99 加锁释放 0.8ms

## 场景 2：消息幂等收敛

**流程**：起 miniredis → 100 goroutine 拿同 MessageId 并发调 `ClaimMessageForProcessing` → 业务回调 atomic 计数 → **断言 == 1**。第二个测试验证业务失败时 processing key release，下次重试能进入业务（防永久卡死）。

**口头表述**：
> "消息幂等用的是 `processing → done` 两态机——抢到 SetNX `processing:msg-id` 的那个 goroutine 才执行业务，业务成功后改成 `done`。100 个 goroutine 拿同一 MessageId 并发调，业务回调里 atomic 加一，**断言计数 == 1**。第二个测试验证业务失败时 processing key 被 release，下一次重试能正常进入业务——**这是防止幂等变永久卡死的关键测试**。"

**真实数字**：100% 收敛 / benchmark 全流程 2.5k QPS

## 场景 3：缓存击穿合并（singleflight）

**流程**：起真 Redis + 写 tripID 进布隆 → mock repo 加 `dbLatency = 50ms` 制造并发窗口 → 50 goroutine 用 ready chan 对齐起跑 → 同时 `GetTripByID(同一 tripID)` → **断言 `getTripCalls == 1`**。第二个测试验证 warm 后顺序读 getTripCalls 仍 == 1（singleflight 不影响热路径）。

**口头表述**：
> "缓存击穿是热点 key 在 L1 和 L2 同时过期那一刻，N 个并发请求同时穿透到 DB。singleflight 是 Go 官方的 `golang.org/x/sync/singleflight` 库，把'相同 key 的并发 fn 调用'合并成只跑一次。我用 50 个 goroutine 同时 GetTripByID 同一个 ID，mock repo 加 50ms 延迟制造并发窗口，**断言 repo.GetTripByID 只被调 1 次**——50:1 合并。还专门写了第二个测试验证 singleflight 不影响热路径——warm 后顺序读两次 repo 仍 == 1。"

**真实数字**：50 并发合并为 1 次 DB 调用 / 50 个 goroutine 总耗时 ~70ms（如果没合并是 50 × 50ms = 2.5s，**10 倍差距是合并的证明**）

## 场景 4：限流精确放行

**流程**：起真 Redis → 200 goroutine 1 秒内打同一 key（limit=10） → atomic 计 allowed/rejected → **断言 `allowed==10 && rejected==190`**。

**口头表述**：
> "限流我用 Redis ZSET + Lua 脚本做滑动窗口：删过期 → 计数 → 写入三步在 Lua 里原子执行。测试是 200 个 goroutine 同时打同一个 key，limit 设 10。Lua 在 Redis 单线程跑，N 个并发被串行处理，**第 11 个进来时 count 已经是 10，Lua 直接拒绝**。断言**放行精确等于 10、拒绝精确等于 190**——多一个少一个都不行。这种精确性是滑动窗口的关键卖点：固定窗口在边界会双倍放行，滑动窗口不会。"

**真实数字**：精确放行 10 / benchmark P99 0.90ms、4.5k QPS

# 4. 缓存正确性三模式对照实验

## 一句话定位

> 多级缓存加了 L1 又加了 singleflight，**每一层都得证明它确实有效**。搭对照测试床用同一个 workload 跑三遍，定量验证每层的真实贡献。

## 实现流程

1. **共享 workload**：预生成 200 个唯一 tripID + 2000 次访问序列（**Zipf s=1.07** 模拟生产偏斜流量）
2. **定种子**：`rand.NewSource(42)` 保证三次运行序列**完全相同**
3. **三模式切换**：两个 bool 参数（withRedis / withL1）：
   - NoCache（false, false）→ mock repo 每次 sleep
   - L2Only（true, false）→ Bloom + Redis + 回源
   - L1+L2（true, true）→ 完整三级
4. **每次跑前清空**：FlushDB + 重置 mock 计数器
5. **输出对比表**：P50 / P95 / P99 / max / db_calls

## 真实数字

| 模式 | P50 | P95 | P99 | db_calls |
|---|---|---|---|---|
| NoCache | ~10ms | ~10ms | ~11ms | **2000** |
| L2Only | ~400µs | ~3-5ms | ~10ms | **~200** |
| L1L2 | **<10µs** | ~300µs | ~10ms | **~200** |

## 口头表述（必背）

> "三模式对照本质就是控制变量法——同一个 workload 跑三遍，只改'有没有 L1' 和 '有没有 L2'。Workload 是 2000 次访问、200 个唯一 ID、Zipf 偏斜分布。定种子 42 保证三次跑的序列完全相同。**结果分两块看：一是 db_calls 列**——NoCache 是 2000、L2Only 和 L1L2 都是约 200，**缓存把 DB 压力降了 10 倍**；**二是 P50 列**——NoCache 10ms（mock sleep）、L2Only 约 400µs、L1L2 小于 10µs，**L1 比 L2 又快 40 倍**。**P99 三模式接近**，因为 cold miss 每个 ID 第一次必回源 DB，缓存救不了首次访问——这告诉我们降 P99 要靠预热脚本不是加缓存层。"

## 高频追问

| 问 | 答 |
|---|---|
| **dbLatency 10ms 是真 Mongo 吗？** | 不是，mock 里 `time.Sleep(10ms)` 合成。**对照看相对加速比不看绝对值**。 |
| **为什么 Zipf 不用 uniform？** | uniform 等概率会高估缓存效果。生产流量都是 Zipf 偏斜，用 Zipf 才符合真实。 |
| **总命中率多少？** | 从 db_calls 反推 ≈ 90%。**没直接打 hit_rate 指标，下一步会启用 ristretto 自带 Metrics() 推到 Prometheus**。 |
| **L1 价值在哪？** | 不是降 DB 压力（这是 L2 的事），是**降 Redis 网络往返**。L1 命中 µs 级、L2 几百 µs，差 40 倍。 |

# 5. 端到端性能压测体系（k6）

## 一句话定位

> k6 是 Go 写的 JS 脚本式压测工具，单进程多 goroutine 支持高并发，原生支持 WS 和多角色场景。**业务流是多步骤 + WS + 多角色**，只有 k6 的 scenarios 能表达。

## 5 步实现流程

| 步骤 | 做了什么 |
|---|---|
| ① 选工具 | k6 vs JMeter（XML/GUI 重）/ Locust（Python GIL）/ wrk（单 URL）—— **多步骤业务流 + WS 选 k6** |
| ② 写场景 | `scenarios` 块配 rider / driver / attacker 三个 executor 并发跑 |
| ③ 写业务流 | 每角色一个 default function，按真实业务流写多步骤 |
| ④ 编 SLO | `thresholds.js` 把 SLO 写成断言，没达标 exit 非 0 |
| ⑤ 推指标 | xk6 编译进 `xk6-output-prometheus-remote`，跑时 push 到 Prom |

## 三个角色 scenarios（必背）

- **rider**：`ramping-vus` 阶梯爬坡（50 → 2000）模拟突发流量
- **driver**：`constant-vus` 800 个长连接 WS 全程在线
- **attacker**：`constant-arrival-rate` 200 RPS 恒定打伪造 ID 验证 Bloom 防御

## 口头表述（必背！）

> "k6 我配了三个角色 scenarios——rider 用 ramping-vus 阶梯爬坡 50 到 2000、driver 用 constant-vus 800 个长连接 WS、attacker 用 constant-arrival-rate 200 RPS 打伪造 ID 验证防御层。rider 的业务流是登录拿 token → **先 WS 连上 `/ws/riders`、在 open 回调里发 preview → start → 15 秒等 driver_assigned 消息**。**这个顺序是踩坑出来的——必须先 WS 连上再发 start，否则 gateway 还没注册 conn，派单消息推不回来**。SLO 写在 thresholds.js 里，比如 preview p99 < 300ms、attacker_blocked_by_bloom > 98%，k6 跑完不达标进程 exit 非 0，**可以直接挂 PR 卡口当 CI 门禁**。指标用 xk6 编译进 prometheus remote_write 扩展，跑时 push 给 Prometheus，**和服务端的 pull 指标在同一个 Grafana 面板上对照看**——黑盒和白盒双视角。一条命令 `./k6 run --summary-export=...json` 跑完 summary JSON 留底做多轮对比。"

## 真实数字 + 找到的瓶颈

**规模**：17 分钟 / 276K 请求 / 1200 VU 峰值

| 接口/链路 | 实测 | 类型 |
|---|---|---|
| preview p99 | **44.55ms**（SLO 300ms ✅，余量 6 倍） | 同步链路 OK |
| attacker_blocked_by_bloom | **100%** | Bloom 防御层 OK |
| auth bcrypt | p99 = **15s** ❌ | CPU 慢哈希（设计 tradeoff 不调 cost） |
| 派单容量 | trip_assigned = **0.74%** ❌ | 架构容量（非脚本 bug） |
| start 写入 | failure rate = **1.95%** ❌ | Mongo 单实例无副本集 |

**关键金句**："这些丑数字我都如实写进 REPORT 不调阈值掩盖——**压测的价值是暴露真实容量边界，不是表演全绿报告**。"

## 高频追问

| 问 | 答 |
|---|---|
| **VU 和 iteration 区别？** | VU = 虚拟用户并发数；iteration = 一个 VU 跑完一遍 default function，跑完接着跑下一轮。 |
| **threshold 干嘛的？** | SLO 编码成断言，没达标 k6 exit 非 0，**可直接挂 CI 门禁**——区别于 wrk 的关键。 |
| **遇到最难的坑？** | trip_assigned 永远 0%。curl 单独打 `/ws/riders` 看到 400 不是 101，定位到 **metrics 中间件没实现 http.Hijacker 接口**，gorilla 断言失败直接 400。8 行代码加 Hijack 修复。**症状是死值就要怀疑测量装置本身**，不是被测对象。 |
| **怎么找瓶颈？** | k6 黑盒看到 P99 飙，配合白盒业务指标对照——`auth p99=15s` 是 bcrypt 慢哈希；`trip_assigned=0.74%` 是派单容量。**两边对照才能定位**。 |

# 6. 跨服务可观测性（OTel + Jaeger + Prometheus + Grafana）

## 一句话定位

> 微服务故障定位最痛的是日志散在多个服务里，靠 grep 30 分钟才能拼一次完整调用链。OTel + Jaeger + Prometheus + Grafana 让任意请求的全链路 1 分钟内还原。

## 6.A Trace 链路追踪（OTel + Jaeger）

**流程**：
1. 4 个服务都引入 OTel SDK + Jaeger exporter
2. HTTP 入口、gRPC 调用、RabbitMQ publish/consume 三类边界用 propagator 包装
3. propagator 把 trace_id 写进 HTTP header / gRPC metadata / RabbitMQ message header
4. 下游 service 起新 span 时 parent 自动指向上游
5. Jaeger UI 输入 trace_id 还原完整调用链

## 6.B Metrics 监控（Prometheus）

### Prometheus 一句话定位
> Prometheus 是 CNCF 出品的开源 TSDB + Pull 模型监控系统，PromQL 查询，K8s 生态事实标准。

### 5 组件
**Server（主进程）+ Exporters（第三方系统适配）+ Pushgateway（短命任务）+ Alertmanager（告警）+ Grafana（可视化）**

### 5 步流程
1. **暴露**：服务在 `/metrics` 暴露纯文本指标
2. **采集**：Prometheus 按 `scrape_interval` 定时 pull
3. **存储**：写入本地 TSDB（默认 2h 内存 + 块文件，长期靠 Thanos）
4. **查询**：PromQL
5. **告警**：周期评估 rules → Alertmanager 路由

### 4 种指标类型（必背）

| 类型 | 语义 | 我项目里用在哪 |
|---|---|---|
| **Counter** | 只增不减 | 请求总数、消费总数、Bloom 命中 |
| **Gauge** | 可增可减瞬时值 | DLQ 当前深度 |
| **Histogram** | 分桶统计 | HTTP 延迟分位 |
| **Summary** | 客户端预算分位 | **不用** |

**关键金句**："多副本必须用 Histogram 不能用 Summary——Histogram 在服务端存 bucket，Prometheus 可以 `histogram_quantile()` 跨副本算全局 P99；Summary 在客户端算分位，多实例聚合时分位数不能合并。"

### 8 个业务指标（背三层分组）

| 层 | 指标 |
|---|---|
| **流量层** | `http_requests_total`（Counter）、`http_request_duration_seconds`（Histogram） |
| **消息层** | `rabbitmq_consumed_total`（Counter，result=ok/dlq/retry）、`rabbitmq_dlq_depth`（Gauge） |
| **并发控制层** | `trip_accept_lock_contention_total`、`bloom_filter_hits_total`、`rate_limit_rejections_total`、`idempotency_dedup_total`（都是 Counter） |

### PromQL 5 个核心模式

```promql
# 1. QPS
rate(http_requests_total[1m])

# 2. P99 延迟（多副本聚合关键写法）
histogram_quantile(0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

# 3. 错误率
sum(rate(http_requests_total{status=~"5.."}[1m])) / sum(rate(http_requests_total[1m]))

# 4. DLQ 堆积（Gauge 直接用）
rabbitmq_dlq_depth

# 5. 告警 rule（持续 5min 才触发防抖）
rate(http_requests_total{status=~"5.."}[5m]) > 0.05  for: 5m
```

## 6.C 实现 wiring（口头表述必背）

> "我用 prometheus client_golang 在 `shared/metrics` 包统一定义 8 个指标，4 个服务共用同一个 Register 函数，用 `sync.Once` 防重复注册避免单测 panic。所有指标加 `service` 这个 ConstLabel，Grafana 面板按 service 过滤。HTTP 自动埋点走 `Middleware`——内部包一层 `statusRecorder` 抓 status code 和延迟，**这个 wrapper 必须实现 `http.Hijacker` 接口，否则 WebSocket 升级 100% 失败**。`pathTemplate` 用白名单 + `strings.HasPrefix("/trip/")` 把 `/trip/<24位hex>` 折叠成 `/trip/:id`，**否则高基数 label 会让 Prometheus OOMKilled**，第一轮压测 Prometheus 真重启了 25 次才发现这个坑。每个服务 main.go 三行连贯：`metrics.Register("xxx") → mux.Handle("/metrics", metrics.Handler()) → metrics.Middleware(mux)`。Prometheus 用 K8s ConfigMap 配 `static_configs` 静态抓 4 个服务，同时开 `--web.enable-remote-write-receiver` 接 k6 推上来的压测指标——**压测客户端是短命进程 pull 抓不到所以 push；服务端长期存活仍用 pull，两种模型按生命周期分工**。retention=2h，memory limit 从默认 512Mi 上调到 1Gi 防 OOM。"

## 6.D 真坑剖析（必背！）

**症状**：压测 trip_assigned 永远 0%，但 HTTP 全 200。

**排查路径**：
1. 怀疑司机匹配链路 → RabbitMQ 通的，排除
2. 怀疑 GEO 查不到司机 → 逻辑正确，排除
3. **跳出业务思维**用 curl 单独打 `/ws/riders` → 400 不是 101，锁定 WS 升级
4. 读 gorilla 源码，发现升级需把 ResponseWriter 断言成 `http.Hijacker`
5. **根因**：metrics 中间件包了一层 statusRecorder 抓 status code，**没实现 Hijacker 接口**
6. 修复 8 行代码加 Hijack 方法透传底层 conn

**方法论**：**症状—装置—被测对象三层归因**——症状是死值（0%/100%）时**先怀疑装置**（中间件、测试链路、测量工具），不是被测对象。

### 真坑口头版

> "压测里发现 trip_assigned 永远 0%，但 HTTP 接口全 200。我先怀疑业务链路——查 RabbitMQ 消息流通的，查 GEO 撮合逻辑也对，**两轮排查都没结果**。最后用 curl 单独打 /ws/riders 看到 400 不是 101，定位到 WS 升级失败。读 gorilla 源码发现升级需要把 ResponseWriter 断言成 http.Hijacker，**而我的 metrics 中间件包了一层 statusRecorder 抓 status code，没实现这个接口**——gorilla 断言失败直接 400，WS 永远建不起来。8 行代码加个 Hijack 方法透传底层连接修复，重跑 trip_assigned 立刻从 0% 变成真值。**这件事让我固化了一个方法论：症状是死值时先怀疑测量装置本身，不是被测对象**。如果一开始就这么想，能省两轮错误归因。"

## 6.E 高频追问

| 问 | 答 |
|---|---|
| **Pull vs Push 怎么选？** | Pull 服务发现简单 + 监控挂了不影响业务，所以服务端用 pull；短命进程（k6/cron）pull 抓不到所以 push。**按生命周期分工**。 |
| **为什么不用 OTel Metrics？** | 项目只有 trace 走 OTel，metrics 直用 prom client 更轻，少一层 SDK 转译。OTel Metrics 还是 beta 不如 prom client 稳。 |
| **高基数怎么办？** | path 模板化（`/trip/<24hex>` → `/trip/:id`），错误详情走日志不走指标。**真踩到过，Prom 重启 25 次**。 |
| **长期存储？** | Prometheus 单实例几周，要长期看用 **Thanos / Cortex / Mimir** 接 S3。 |
| **告警怎么做？** | Prometheus Server 评估 PromQL rule → Alertmanager 去重/分组/路由到 Slack/PagerDuty。`for: 5m` 持续触发才告警防抖。 |

# 7. 混沌测试场景设计（Chaos Mesh）

## 一句话定位

> 单测和压测都是"按预期工作"，混沌验证"非预期下的退化"。生产事故几乎都是非预期组合——pod 挂、网络抖动、依赖部分不可用，这些**只有主动注入才能验证**。Chaos Mesh 是 K8s 上的声明式故障注入框架，CRD 编排可复现的故障，比 `kubectl delete pod` 强一个数量级。

## RTO / RPO（必背）

| 缩写 | 全称 | 中文 | 一句话 |
|---|---|---|---|
| **RTO** | Recovery **Time** Objective | 恢复时间目标 | 故障到业务恢复的**时长上限** |
| **RPO** | Recovery **Point** Objective | 恢复点目标 | 故障可容忍的**数据丢失量上限** |

**金句**："RTO 是恢复多快，RPO 是丢多少。互联网业务一般 RTO < 5min、RPO < 1min；金融业务 RTO 可放宽但 RPO 必须 = 0。"

## 通用流程（每个场景共用）

1. 写 CRD YAML 定义 kind、action、selector、duration
2. `kubectl apply -f xxx.yaml` 注入
3. **同时跑 k6 压测**做负载背景
4. **Grafana 加 annotation 竖线**标记注入点
5. 业务指标跌破 SLO 那一刻打 mark、恢复回去那一刻再打一个，**差值 = RTO**
6. 跑完 `kubectl delete -f` 清理

## 场景 1：PodKill driver-service

### YAML 骨架（对应真文件 `loadtest/chaos/pod-kill-driver.yaml`）

```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: concert-pod-kill-driver
  namespace: chaos-mesh                # CRD 本身放 chaos-mesh ns
spec:
  action: pod-kill
  mode: one                            # 只杀一个；可选 all / fixed / fixed-percent
  selector:
    namespaces: ["default"]            # 被杀的 pod 在 default ns
    labelSelectors:
      app: driver-service
  duration: "60s"                      # 实验 CR 存活时间
```

**关键字段背点**：
- `mode: one` 选一个目标——还有 `all`（全杀）、`fixed: 2`、`fixed-percent: 50`
- `namespace: chaos-mesh` vs `selector.namespaces: ["default"]` 是**两个 ns**——CRD 装在 chaos-mesh，目标在 default
- `duration` 对 pod-kill 是"实验 CR 存活时间"，不是"pod 死多久"——pod 杀完 K8s 立刻重启

### 流程（按时间轴讲）

1. **T+0s**：apply YAML，Chaos Mesh kill 一个 driver-service pod
2. **T+0~T+30s**：K8s 检测 NotReady，新 pod 拉起；故障窗口内 rider 拉单的 `trip.event.created` 消息**在 RabbitMQ 队列堆积不丢**（persistent + 未 ack）
3. **T+30s 左右**：新 pod 起来，重连 RabbitMQ，**重投消息**开始消费
4. **T+30s 后**：业务指标短暂下探后恢复

### 关键断言

- ✅ `rabbitmq_consumed_total` 速率短暂归零后追平堆积
- ✅ **`idempotency_dedup_total` 增量 > 0**——证明重投消息被识别为重复
- ✅ Mongo trip 表**无重复派单**
- ✅ `trip_assigned_rate` 下探后 1min 内恢复

### 预期 RTO / RPO

| 指标 | 数值 |
|---|---|
| **RTO** | < 60s（pod 启动 30s + 消费追平 10-20s） |
| **RPO** | **0**（消息持久化 + 重投 + 业务幂等三层兜底） |

### 口头表述（背这段！）

> "T+0 杀掉 driver-service 一个 pod 后，K8s 检测 NotReady 拉新 pod，**故障 30 秒内 rider 拉单的消息在 RabbitMQ 队列堆积但不丢**——消息是 persistent + 未 ack 状态。新 pod 起来重连 RabbitMQ，重投消息开始消费。**关键断言是 `idempotency_dedup_total` 有增量**，证明重投消息被我的幂等状态机识别为重复跳过，**Mongo trip 表也没出现重复派单**。**预期 RTO < 60s，RPO = 0**——这个场景本质验证消息可靠性加幂等接管，RabbitMQ 当缓冲、幂等保证不重复，两层配合实现故障期间业务无感。"

### 高频追问

| 问 | 答 |
|---|---|
| **为什么 RPO = 0？** | RabbitMQ 消息 persistent + 未 ack，pod 挂了消息不丢；新 pod 重投 + 业务幂等保证不重复处理。两层保障让 RPO = 0。 |
| **怎么测 RTO？** | Grafana 在故障注入点和恢复点打 annotation 竖线，业务指标跌破 SLO 那一刻打 mark，恢复回去那一刻再打一个，差值就是 RTO。 |
| **副本数 = 1 时怎么办？** | RTO 更长（要等新 pod 完全启动），但 RPO 仍 = 0。生产建议 replicas >= 2 才能秒级 RTO。 |

## 场景 2：NetworkChaos delay redis 50ms

### YAML 骨架（对应真文件 `loadtest/chaos/network-delay-redis.yaml`）

```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: concert-redis-delay
  namespace: chaos-mesh
spec:
  action: delay
  mode: one
  selector:
    namespaces: ["default"]
    labelSelectors:
      app: redis
  delay:
    latency: "50ms"                    # 平均延迟
    correlation: "25"                  # 相邻包延迟相关性 25%
    jitter: "10ms"                     # 抖动 ±10ms
  duration: "60s"
```

**关键字段背点**：
- `action` 五种：`delay`（延迟）/ `loss`（丢包）/ `duplicate`（重复）/ `corrupt`（损坏）/ `partition`（网络分区）
- `latency + jitter + correlation` 三件套**才接近真实网络**——纯 50ms 是理想模型，加 jitter 才模拟抖动
- `correlation` 越大延迟越平稳；为 0 时每个包独立随机抖动

### 流程（按时间轴讲）

1. **T+0s**：apply YAML，Chaos Mesh 给 Redis pod 注入 50ms 出入向网络延迟
2. **T+0~T+60s**：**所有走 Redis 的路径延迟增加**——限流脚本（Lua）、接单锁（SETNX）、幂等状态机、Bloom 过滤器、L2 缓存全部受影响
3. **T+0~T+60s**：业务 P99 抬升但**不应该出错**——Redis client 默认 timeout 3 秒远大于 50ms
4. **T+60s 后**：延迟立刻恢复

### 关键断言

- ✅ start P99 < 800ms（chaos 档 SLO，比 baseline 500ms 放宽）
- ✅ start 错误率 < 4%（chaos 档）
- ✅ **不出现雪崩**（不应该因限流变慢导致请求堆积到 OOM）
- ✅ Bloom 拦截率仍 > 98%（防御层不退化）

### 预期 RTO / RPO

| 指标 | 数值 |
|---|---|
| **RTO** | 注入结束**立即恢复**（这不是真"故障"恢复，是降级容忍测试） |
| **RPO** | **0**（没数据丢失，只是慢） |

### 口头表述（背这段！）

> "T+0 给 Redis pod 注 50ms 延迟加 10ms 抖动后，所有走 Redis 的路径——限流、接单锁、幂等、Bloom、L2 缓存——延迟都增加。**关键是不应该出错也不应该雪崩**：Redis client 默认 timeout 3 秒远大于 50ms，所以慢但不失败。我会断言 start P99 在 chaos 档 SLO 800ms 以内、错误率小于 4%、Bloom 拦截率仍超 98%。注入结束立即恢复，所以 RTO ≈ 0、RPO = 0。**这个场景验证降级路径和防雪崩**——如果限流脚本依赖 Redis 而没有客户端超时，单点 Redis 抖动会把整个 api-gateway 拖垮，这是要主动测出来的。"

### 高频追问

| 问 | 答 |
|---|---|
| **为什么不模拟 Redis 挂掉？** | 全挂是更极端故障，但 **50ms 延迟更现实**——生产网络抖动远比"全挂"常见，是测开应该重点覆盖的灰色场景。 |
| **如果客户端没设 timeout 会怎样？** | 请求堆积——goroutine 阻塞在 Redis 调用不释放最终 OOM。**这就是要测出来的，是混沌的价值**。 |
| **50ms 这个数怎么定的？** | 生产 Redis 平均 RTT < 5ms，注入 50ms 即 10 倍延迟模拟"网络异常但未中断"。再大（200ms+）就接近"挂了"，意义不同。 |

## 7.A Chaos 收尾追问（必背）

| 问 | 答 |
|---|---|
| **为什么用 Chaos Mesh 不手动 `kubectl delete pod`？** | 手动 kill 不可复现、不能精确控时间窗口、不能注入网络延迟/丢包。Chaos Mesh 是声明式 CRD，**可复现 + 可编排**。 |
| **设计第一个混沌场景选哪个？** | **PodKill**——YAML 最简单、出图最快、不挑环境、验证最基础的 K8s 自愈假设。NetworkChaos 渐进叠加，**一口气全上踩坑概率高**。 |
| **跑过完整流程没？** | 诚实答："**场景设计 + YAML 已落地，完整跑通是后续 TODO**，目前用于演示稳定性测试方法论和场景规划能力。" |

# 8. 质量门禁与 CI 自动化

## 一句话定位

> 测试都写了，但开发提交时容易忘跑全量。把质量检查卡进 PR，PR 不绿合不进 main——GitHub Actions 两个 job 并行 lint + test，最小可演进结构。

## 实现流程

### Lint Job
1. `actions/checkout@v4` 拉代码
2. `actions/setup-go@v5` 装 Go，**开 `cache: true`** 按 go.sum hash 缓存依赖
3. `gofmt -l .` 检查格式，有 diff 直接 exit 1
4. `go vet ./...` 静态分析

### Test Job
1. **service container 起真实 mongodb**（mongo:6 + health check）
2. checkout + setup-go（带 cache）
3. `go build ./...` 验证全模块能构建
4. **跑并发安全测试 + 覆盖率检测**
5. 输出覆盖率 summary 到 stdout
6. **上传 coverage.out artifact**，PR 评审可下载本地用 `go tool cover -html` 看红绿

## 关键决策

| 决策 | 理由 |
|---|---|
| **两 job 并行 + needs: lint** | lint 失败立刻断不浪费 test 算力 |
| **真 mongo 不用 mock** | mongo-driver mock 容易和真实行为偏离（索引、CAS、writeConcern） |
| **只 report 不卡覆盖率** | 现阶段覆盖率分布不稳定，先看真实数据再加阈值 |
| **没用 golangci-lint** | 渐进引入，先 gofmt + vet 跑稳再叠加 |

## 口头表述

> "我用 GitHub Actions 配 PR 级卡口，两个 job 并行。**第一个 lint job 跑 gofmt 加 vet 快失败**——格式不对或静态分析报错立刻断不浪费 test 算力。第二个 test job 用 service container 起真实 mongodb——**不用 mock 是因为 mongo-driver mock 测不出索引、CAS、writeConcern 这些真实行为**——然后跑并发安全测试加覆盖率检测，最后上传 coverage 报告做 artifact。**关键决策三条**：service container 不用 testcontainers 是为了简单；只 report 不卡覆盖率是因为现阶段分布不稳定先看真实数据；没用 golangci-lint 是渐进引入。**演进路线图**：短期加 golangci-lint 加覆盖率门禁，中期加 k6 smoke 进 PR check，长期加 chaos nightly job。"

## 高频追问

| 问 | 答 |
|---|---|
| **为什么不一开始就加覆盖率门禁？** | 突然卡 80% 会让 PR 推不动。**渐进式**：先 report 收集真实分布 → 关键模块卡 85% → 全局卡 70%。 |
| **怎么防 flaky 测试腐蚀 CI？** | 找根因（80% 是 sleep / 随机数据）+ 隔离 build tag + 长期看板。我项目并发测试用 ready chan + atomic 不用 sleep，**目前没踩到 flaky**。 |
| **本地怎么复现 CI 失败？** | yaml 里所有命令本地可执行——gofmt -l、go vet、go test -race -cover。**三件套本地跑通 = CI 跑通**。 |
