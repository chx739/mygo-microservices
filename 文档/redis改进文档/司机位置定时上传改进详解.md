# 司机位置定时上传改进详解（Redis GEO + 后台任务生命周期）

## 1. 改进目标

本次改进对应 [改进方向 redis.md](改进方向%20redis.md) 的“六、司机位置定时上传”。

目标是把司机位置从“注册时写一次静态坐标”升级为“注册后持续上报动态坐标”，并保证：

1. 位置持续更新：每 3 秒推进一帧路线。
2. 数据一致性：Redis GEO 与司机 Hash 中的 `lat/lng` 同步更新。
3. 生命周期安全：司机注销时后台任务可停止并等待退出，避免竞态写回。
4. 可验证：有单元测试覆盖“会移动、能停止、不回写”。

## 2.2 后台任务状态管理（可停止 + 等待退出）

文件： [services/driver-service/service.go](services/driver-service/service.go)

```go
type driverMovementTask struct {
    cancel context.CancelFunc
    done   chan struct{}
}

type Service struct {
    rdb redis.UniversalClient

    movementMu      sync.Mutex
    driverMovements map[string]driverMovementTask
    movementInterval time.Duration
}
```

关键点：

- `driverMovements` 记录每个司机的任务句柄。
- `cancel` 用于停止任务。
- `done` 用于等待 goroutine 真实退出，避免停止后仍有异步写入。

## 2.3 周期更新 GEO + Hash

文件： [services/driver-service/service.go](services/driver-service/service.go)

```go
func (s *Service) simulateMovement(
    ctx context.Context,
    driverID string,
    packageSlug string,
    route [][]float64,
    interval time.Duration,
) {
    ticker := time.NewTicker(interval)
    defer ticker.Stop()

    // route[0] 在注册时已写入，模拟从下一帧开始。
    nextIndex := 1

    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            point := route[nextIndex%len(route)]
            nextIndex++

            updateCtx, cancel := context.WithTimeout(ctx, 2*time.Second)
            err := s.UpdateDriverLocation(updateCtx, driverID, packageSlug, point[0], point[1])
            cancel()
            if err != nil {
                log.Printf("failed to update simulated driver location: driverID=%s err=%v", driverID, err)
            }
        }
    }
}
```

## 2.4 注销时先停任务再删数据

文件： [services/driver-service/service.go](services/driver-service/service.go)

```go
func (s *Service) UnregisterDriver(ctx context.Context, driverID string, packageSlug string) error {
    // 先停止后台任务并等待退出。
    _ = s.stopDriverMovement(driverID)

    // 再执行 Redis 删除，避免“刚删除又被后台写回”。
    pipe := s.rdb.Pipeline()
    pipe.Del(ctx, driverInfoKey(driverID))
    pipe.SRem(ctx, driversOnlineKey(packageSlug), driverID)
    pipe.ZRem(ctx, driversGeoKey(packageSlug), driverID)
    _, err := pipe.Exec(ctx)
    return err
}
```

## 3. 为什么要做（场景 + 困难）

## 3.1 场景

1. Demo 体验问题
- 司机坐标静止不动，前端地图没有“实时移动”感。

2. 匹配准确性问题
- GEO 搜索只能基于注册时位置，不符合真实调度场景。

3. 生命周期问题
- 司机下线后若后台更新未停，可能出现“已下线司机重新出现在在线数据里”。

## 3.2 困难

1. 不能用请求上下文跑长期任务
- gRPC 请求返回后，`ctx` 会被取消，后台任务会立刻终止。

2. 要避免并发竞态
- “注销删除”和“后台定时写”可能并发，需要保证顺序与退出确认。

3. 要保持可测试性
- 定时逻辑天然异步，必须通过可调间隔与 eventually 机制做稳定测试。

---

## 4. 怎么实现（技术原理）

## 4.1 任务生命周期建模

每个司机一个任务句柄：

- 启动：`startDriverMovement`
- 停止：`cancel`
- 等待退出：`<-done`

这种模型的本质是“可控 goroutine”。

## 4.2 Redis 双写同步

通过 [services/driver-service/service.go](services/driver-service/service.go) 的 `UpdateDriverLocation`，每次 tick 同时更新：

- `GEO` 索引：用于距离检索。
- `driver:info:{id}` 的 `lat/lng`：用于直读展示。

同时续期 `driver:info` TTL，保持在线状态活跃。

## 4.3 停止顺序保证

注销时严格执行：

1. 取消并等待任务退出。
2. 删除 Hash / Set / GEO 成员。

这样能避免“删除后异步回写”的经典竞态。

司机注册后位置固定，地图无动态效果，GEO 搜索基于陈旧坐标，调度体验差。

## T（Task）
实现司机位置定时上传，让坐标持续变化，并保证司机下线后不会发生异步回写。

## R（Result）
司机位置从静态升级为动态，地图与调度数据一致性明显提升；改造后单测与构建全通过，方案可稳定复用到真实 GPS 上报链路。

## 7. 其他技术可行性与取舍

## 7.1 可以用消息队列上报位置吗？
可以，但当前不优先。

原因：

- 当前目标是“快速提升 Demo 与匹配真实性”，本地定时任务 + Redis 即可落地。
- 引入 MQ 会增加 producer/consumer、幂等、堆积治理等复杂度。
- 真实终端接入前，先把存储与生命周期模型打稳更划算。

## 7.2 可以用 cron 风格全局任务统一推进吗？
可以，但不如“每司机独立任务”直观。

原因：

- 全局任务需要维护司机全量扫描与分发，复杂度更高。
- 每司机任务更贴近“司机在线即上报、下线即停止”的业务语义。

## 7.3 为什么不用仅更新 GEO，不写 Hash？
不建议。

原因：

- 前端或其他接口常常直接读 `driver:info`，不写 Hash 会导致展示与检索数据不一致。
- 双写同步能保证“检索结果”和“详情展示”一致。

## 9. 面试高频 10 问 10 答

1. 问：为什么不能直接把 gRPC 请求 `ctx` 传给后台 goroutine？
答：请求返回后 `ctx` 会被取消，后台任务会立即停止，无法持续上报。

2. 问：为什么要 `cancel + done`，只 cancel 不行吗？
答：只 cancel 不能保证 goroutine 已退出；`done` 可等待真实退出，避免并发写回。

3. 问：为什么更新位置要同时写 GEO 和 Hash？
答：GEO 用于距离检索，Hash 用于详情直读，双写保证读写视图一致。

4. 问：为什么 interval 选 3 秒？
答：是体验和成本平衡点：地图变化明显，同时 Redis 写入压力可控。

5. 问：后台任务异常怎么办？
答：单次更新加短超时并记录日志，不让 goroutine卡死；下一轮继续尝试。

6. 问：重复注册同一司机如何处理？
答：先停旧任务并等待退出，再启动新任务，避免并行任务重复写。

7. 问：注销时先删 Redis 再停任务可以吗？
答：不推荐，可能出现删除后下一 tick 又写回，导致“幽灵在线司机”。

8. 问：这个方案如何迁移到真实 GPS 上报？
答：保留 `UpdateDriverLocation` 作为统一写入入口，把模拟数据源替换为终端上报即可。

9. 问：有没有资源泄漏风险？
答：有，若不做生命周期管理会泄漏 goroutine；本方案通过 `stop + wait` 避免。

10. 问：如何验证改造有效？
答：看单测（移动/停止/不回写）+ 线上指标（更新成功率、陈旧位置数、匹配距离 P95）。
