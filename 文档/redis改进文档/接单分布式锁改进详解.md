# 接单分布式锁改进详解（面试导向）

## 1. 改进背景与问题

### 1.1 业务问题
在抢单场景中，司机 A 和司机 B 可能在毫秒级同时点击接单。改造前链路是：

1. Trip Consumer 收到 accept 事件
2. 直接调用 UpdateTrip 把状态改成 accepted
3. 发布 driver_assigned 和 payment.create_session

这会带来两个风险：

- 并发写入竞争：同一 trip 可能被多个 accept 并发处理。
- 下游副作用重复：可能触发多次支付会话创建。

### 1.2 目标

- 在 Trip Service 接单入口加分布式互斥，只有第一个 accept 能继续。
- 在 Mongo 更新层加状态条件闸门，形成二次兜底。
- 保持现有事件协议不变，最小侵入改造。
- 补齐自动化测试，并通过编译验证。

---

## 2. 实现方案总览

本次采用“双保险”设计：

- 第一层：Redis 锁（前置拦截）
- 第二层：Mongo 条件更新（最终一致性闸门）

处理链路：

1. 收到 accept 事件后，先执行 SET NX EX 抢锁。
2. 抢锁失败直接返回，不继续更新 Trip。
3. 抢锁成功后注册 defer，在函数退出时尝试提前释放锁。
4. 提前释放使用 Lua 脚本原子执行“校验 owner + 删除锁”。
5. 业务流程继续执行 UpdateTrip。
6. UpdateTrip 在 accepted 场景要求旧状态必须为 pending。
7. 满足条件才允许真正写库并继续发布事件。

这样即使 Redis 锁在极端场景偶发失效，Mongo 也能拦住重复 accepted。

## 3. 代码改动明细

### 3.1 Trip Consumer：增加接单锁

文件：services/trip-service/internal/infrastructure/events/driver_consumer.go

关键改动：

- 结构体新增 Redis 客户端依赖。
- 构造函数新增 redisClient 入参。
- 在 handleTripAccepted 开头增加 tryAcquireTripAcceptLock。
- 新增 tripAcceptLockTTL、tripAcceptLockKey、tryAcquireTripAcceptLock。
- 新增 releaseTripAcceptLock 与 Lua 解锁脚本 tripAcceptUnlockScript。
- 在 handleTripAccepted 中加入 defer 提前释放锁逻辑。

核心逻辑（简化）：

```go
ok, err := c.tryAcquireTripAcceptLock(ctx, tripID, driver.GetId())
if err != nil {
    return err
}
if !ok {
    return nil
}
// 锁成功后继续原有接单流程
```

锁键设计：

- key: trip:lock:{tripID}
- value: driverID
- TTL: 30s

说明：

- 30 秒是“处理窗口”保护值，防止锁永久占用。
- 抢锁成功后会在 defer 中尝试提前释放，降低锁空转时间。
- 提前释放使用 Lua 原子脚本，只有 owner 匹配时才会删除，避免误删他人锁。

Lua 解锁脚本（简化）：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
return 0
```

## 4. 技术原理（面试可讲）

### 4.1 为什么用 SET NX EX

SET NX EX 具备原子语义：

- key 不存在才设置（NX）
- 同时设置过期时间（EX）

所以“检查+加锁”在一条命令内完成，避免了先查后写的竞态。

### 4.2 为什么提前释放必须用 Lua

提前释放要满足两个条件：

- 只能释放自己持有的锁。
- 校验 owner 与删除锁必须原子执行。

如果用两条命令（GET 后 DEL），中间可能被并发请求插入，导致误删新 owner 的锁。Lua 脚本把两步放在 Redis 单线程里一次完成，避免竞态。

### 4.3 为什么要 Mongo 条件更新

仅靠 Redis 锁并不等于绝对一致性，仍可能出现：

- 锁超时过早
- 网络抖动导致请求重放
- 消费重试导致重复进入

因此在数据库层加 accepted 只能从 pending 迁移的条件，是最终状态机约束。

### 4.4 双保险的收益

把并发问题拆成两层控制：

- Redis 层减少无效并发请求进入业务逻辑。
- Mongo 层保证最终状态不可被重复覆盖。

这类设计在高并发场景比单点防线更稳。

## 8. 面试高频问答（10 组）

### Q1：为什么不是只做 Redis 锁？
A：Redis 锁负责前置限流，但数据库才是最终状态源。Mongo 条件更新可以防止极端情况下的重复 accepted。

### Q2：锁为什么不手动释放？
A：现在已经支持提前释放，但不是直接 DEL，而是走 Lua 脚本做“owner 校验 + 删除”的原子操作，避免误删其他请求持有的锁；TTL 作为兜底防止异常路径死锁。

### Q3：30 秒 TTL 怎么定？
A：按接单处理链路的 P99 耗时预留安全余量。目标是“覆盖一次完整处理窗口”且避免长时间占锁。

### Q4：如果 Redis 崩了怎么办？
A：服务启动时会 Ping Redis，保证锁能力不可用时不带病启动；并且 Mongo 条件更新仍是最后防线。

### Q5：如果收到重复消息会怎样？
A：重复消息大概率在锁层被挡住；即使穿透，也会在 Mongo pending 条件上失败。

### Q6：为什么用 MatchedCount 而不是 ModifiedCount？
A：MatchedCount 能准确区分“条件不匹配/不存在”与“更新值相同”两类情况，语义更稳定。

### Q7：有没有可能出现锁误判？
A：在网络分区、超时重试等场景仍可能出现边界问题，所以才需要数据库状态机兜底。

### Q8：这算幂等吗？
A：是幂等控制的一部分。锁控制并发入口，状态条件更新控制最终状态幂等。

### Q9：为什么把锁放在 Trip Service 而不是 Driver Service？
A：Trip Service 是行程状态的归属方，接单状态变更在这里发生，放这里可以最小化跨服务一致性成本。

### Q10：下一步还能怎么增强？
A：可继续加锁观测指标（冲突率、持锁时长、超时率）和消息幂等（MessageId 去重），进一步降低重复消费带来的无效处理。

## 10. 一句话简历版本

在 Trip Service 接单链路实现 Redis 分布式锁（SET NX EX）与 Mongo 条件更新双保险，解决多司机并发接单竞态，降低重复状态写入和重复支付触发风险，并通过自动化测试与全量构建验证。

在上述双保险设计中，Redis 分布式锁可能失效的原因主要包括以下几类：

---
redis 锁失效的常见原因：

### 1. 锁过期导致并发写入

- **业务执行超时**：获取锁的线程因为 GC、网络延迟、下游服务慢等原因，执行时间超过了锁的 TTL（如 30 秒）。锁自动释放后，另一个线程获取到锁，而此时原线程仍在执行，导致两个线程同时进入临界区。
- **锁未及时续期**：虽然可以开启 Watchdog 自动续期，但若续期线程本身出现问题（如死循环、被阻塞），仍可能超时。

---

### 2. 锁被误删除

- **解锁时未校验 owner**：如果解锁操作直接 `DEL key`，而没有先用 Lua 脚本比较 value（唯一标识），那么可能删除其他线程持有的锁（例如线程 A 锁过期后，线程 B 拿到锁，线程 A 延迟后执行 `DEL` 删除了 B 的锁）。
- **网络超时重试**：客户端因网络超时认为加锁失败，发起重试并成功获得新锁，但之前超时的请求实际已在 Redis 上创建了锁，导致同一把锁被多个客户端持有。

---

### 3. Redis 高可用架构的缺陷

- **主从异步复制**：在 Redis Sentinel 或 Cluster 模式下，客户端向主节点写入锁（`SET NX EX`），主节点返回成功，但数据尚未同步到从节点。此时主节点宕机，从节点被提升为主，新主节点没有该锁数据，另一个客户端可以成功加锁，导致锁丢失。
- **网络分区**：发生脑裂时，多个客户端可能同时与不同主节点通信，分别获得同一资源的锁。

---

### 4. 时钟漂移

- Redis 节点的系统时钟发生跳跃（例如 NTP 回拨），可能导致锁的过期时间计算不准确，锁提前或延后过期。

---

### 5. 客户端逻辑缺陷

- **未正确释放锁**：程序崩溃、死循环、`defer` 未执行等导致锁残留，虽然不影响其他客户端获取锁（因为锁会过期），但可能造成短期不可用。
- **锁的可重入性未处理**：同一线程在未释放锁的情况下再次请求锁，若未设计可重入机制，可能死锁。

---

### 6. Redis 服务本身故障

- **内存耗尽被 OOM Killer 杀死**：导致所有锁丢失。
- **配置错误**：如 `maxmemory` 设置过小触发 key 淘汰，可能误淘汰锁 key。
- **慢查询阻塞**：Redis 单线程处理，其他慢命令（如 `KEYS *`）阻塞了锁的读写操作，导致客户端超时。
