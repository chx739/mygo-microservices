## 第一层：背景与职责（STAR · 30 秒开场，必须流畅）

> **S 背景**：我做的是一个 Go 网约车微服务系统——网关 / 行程 / 司机 / 支付四个服务，gRPC 同步 + RabbitMQ 异步。业务路径平时看着正常，但**没人量化过它在突发流量下的真实表现**。
>
> **T 任务**：我要建一套可观测 + 压测体系，用"演唱会散场"模型（瞬时几千人同时打车）压一遍，拿到真实 SLO，并找出真瓶颈。
>
> **A 行动**：用 **k6** 写四阶段场景脚本（预热→爆发→稳态→回落），**Prometheus remote_write** 收 k6 指标 + 自建 8 个业务指标，**Grafana** 出面板，**Chaos Mesh** 注入故障。第一轮 SLO 全炸，逐字段对齐脚本和服务契约后发现是 8 个 bug（含 1 个生产 bug），修完拿到真值。
>
> **R 结果**：17 分钟跑出 27.6 万 HTTP 请求、峰值 1200 VU。preview p99 = 44.55ms（SLO 300ms，余量 6 倍）、布隆拦截恶意流量 100%；**同时故意把 3 个真瓶颈打出来**：auth 在 bcrypt 下 p99=15s、派单容量撑不起爆发、start 边缘 1.95% 失败。这些如实写进报告，**不调阈值掩盖**。

**一句话版**（被打断时用）："我给一个 Go 微服务系统做了演唱会级压测，k6+Prometheus+Grafana 自建体系，找出并修了 8 个 bug，暴露了 3 个真实容量瓶颈。"

## 第二层：技术选型为什么这么选（必带对比）

### Q：为什么用 k6 不用 JMeter / Locust / wrk？

| 工具 | 取舍 |
|---|---|
| **JMeter** | XML 配置、GUI 重、写复杂业务流（登录→preview→start→等 WS）很别扭，CI 不友好 |
| **Locust** | Python，GIL 限制单机并发上不去，要多 worker |
| **wrk** | 极快但只能打单 URL，**没法表达"多步骤业务流 + WebSocket 等事件"** |
| **k6（选它）** | JS 写场景像写代码、单进程 goroutine 模型并发高、原生支持 WS、`scenarios` 能同时跑多种角色（rider/driver/attacker），threshold 直接当 SLO 断言 |

一句话："业务流是多步骤 + 长连接 WS + 多角色并发，wrk/JMeter 表达不了，k6 的 scenario 模型天生适配。"

### Q：Prometheus 为什么用 remote_write，不用默认 pull？

- Prometheus 默认是 **pull**：定时 scrape 服务的 `/metrics`。这适合采**服务端**指标。
- 但 **k6 是压测客户端，进程跑完就退**，pull 模型来不及 scrape。
- 所以 k6 侧用 **remote_write（push）**：xk6 编译进 `xk6-output-prometheus-remote`，k6 主动把 VU/RPS/延迟推给 Prometheus（需要 Prometheus 开 `--web.enable-remote-write-receiver`）。
- **服务端指标仍走 pull**（4 个服务暴露 `/metrics`，Prometheus 定时抓）。
- 一句话："压测客户端是短命进程，pull 抓不到，所以 k6 用 remote_write 推；服务端长期存活，仍用 pull。两种模型按生命周期分工。"

### Q：为什么自建 8 个业务指标，不只用 k6 自带的？

- k6 自带指标只看到**客户端视角**（请求发出去多久回来）。
- 但我要回答的是**系统内部为什么慢**：消息堆没堆 DLQ？锁竞争多不多？布隆挡住没？幂等去重生效没？
- 所以在 `shared/metrics` 加了 8 个：HTTP 耗时直方图、RabbitMQ 消费/DLQ 深度、布隆命中、Redis 锁竞争、幂等去重等。
- 一句话："k6 指标是黑盒外部视角，业务指标是白盒内部视角，定位瓶颈必须两边对照。"

### Q：指标的 path 为什么要模板化（`/trip/:id`）？

- Prometheus 每个不同 label 值 = 一条独立时间序列。
- 如果 path 用原始 URL，`/trip/abc`、`/trip/def`…百万 tripID = 百万时间序列 → **高基数爆炸，Prometheus 内存打爆**（这次真踩到，见第三层）。
- 解法：中间件把 `/trip/<24位hex>` 归一成 `/trip/:id` 再打 label。
- 一句话："高基数会让 Prometheus OOM，path 必须模板化收敛 label 基数。"

### Q：Chaos Mesh 为什么用它，不手动 kill pod？

- 手动 `kubectl delete pod` 不可复现、不能精确控时间窗口、不能注入网络延迟/丢包。
- Chaos Mesh 是声明式 CRD（PodChaos/NetworkChaos/Workflow），能编排"T+8 kill driver、T+10 给 Mongo 注 10% 丢包"这种**时间线编排 + 可复现**。
- 一句话："要的是可复现、可编排的故障注入，手动 kill 做不到精确控制。"

## 第三层：技术难点（2-3 个真坑，答好基本稳过）

### 坑 1 ⭐（最值钱）：WebSocket 升级全失败，`trip_assigned=0%`

- **现象**：第一轮 Round 2，`trip_assigned_within_15s` = **0%**（一个都没派到），但 preview/start 的 HTTP 都 200。`ws_session_duration` avg 只有 166ms——像是 WS 一连上就断。
- **排查**：
  1. 先怀疑司机匹配链路坏 → 查 RabbitMQ 链路，消息流是通的，排除。
  2. 怀疑 GEO 查不到司机 → 查 driver-service GEOSEARCH，逻辑没问题。
  3. 用 `curl -i -H "Upgrade: websocket"` 直接打 `/ws/riders` → 返回 **400 Bad Request**，不是 101。锁定在 WS 升级这一步。
  4. 读 gorilla/websocket 源码：升级时它要把 `http.ResponseWriter` 断言成 `http.Hijacker` 拿底层 TCP conn。
- **根因**：我的 **metrics 中间件**包了一层 `statusRecorder` 来记录响应状态码，但这个 wrapper **没实现 `http.Hijacker` 接口**。gorilla 一断言失败就直接 400，WS 永远建不起来 → rider 收不到 `driver_assigned` → `trip_assigned` 永远 0%。
- **解决**：给 `statusRecorder` 加 8 行——一个 `Hijack()` 方法，把底层 `ResponseWriter` 的 `Hijack()` 透传出去（断言失败返回明确 error）。重跑 `trip_assigned` 立刻从 0% 变成真值。还补了一个 channel 同步的回归单测（`go test -race` 防回归）。
- **教训**："**症状是死值（永远 0%）就要怀疑测量/链路装置本身，不是被测对象**。我盯着 0% 做了两轮错误归因，最后靠'变量法'——curl 单独打 WS 看到 400，才跳出业务思维定位到中间件。"

### 坑 2：脚本字段和服务契约不对齐，preview 失败率 75%

- **现象**：preview 接口失败率 75%，trip 全部派不出去。
- **排查**：抓 trip-service 日志，发现写出来的 geometry 是空的；再看坐标，全是 `(0, 0)`——大西洋几内亚湾。
- **根因**：k6 脚本 `payload.js` 用的字段名是 `startLocation/endLocation`，但 gateway 的 `previewTripRequest` 结构体 JSON tag 是 `pickup/destination`。**字段名对不上 → JSON 解析默认零值 → 坐标 (0,0) → OSRM 路径为空 → GEO 在大西洋查不到司机**。
- **解决**：脚本字段改成 `pickup/destination`，逐字段对齐 gateway 的 struct tag。
- **教训**："**压测脚本本身就是被测系统的一部分**，脚本和服务契约必须逐字段对齐，否则压的是 bug 不是性能。这次 8 个 bug 里有 5 个是这类契约不对齐（WS 缺 query param、driver 回执 type 错、tripID 取值路径错、packageSlug 不对齐）。"

### 坑 3：Prometheus 被 OOMKilled，压测数据丢

- **现象**：长时间跑后 Grafana 面板断档，`kubectl get pod` 看到 prometheus 反复重启，exit code **137**（OOMKilled），累计重启 25 次。
- **排查**：`kubectl describe pod` 确认 OOMKilled；查 WAL，31 小时累积 + scrape 的时间序列基数偏高，512Mi limit 扛不住。
- **解决**：两手——① 内存 limit 512Mi → 1Gi；② path 模板化（坑里说的 `/trip/:id`）从源头压低时间序列基数。
- **教训**："可观测性组件自己也会成为瓶颈。高基数 label 是 Prometheus 头号杀手，设计指标时就要把 label 基数当一等公民。"

> 背诵口诀：**Hijacker 死值、字段不对齐、Prometheus 高基数 OOM**。

## 第四层：边界与扩展（量上来怎么办，体现思考即可）

### Q：如果流量再翻 10 倍，瓶颈在哪、怎么扩？

按这次压测**实测**的瓶颈顺序答（这是优势——我有真数据）：

**① 派单容量（最先顶不住，trip_assigned 实测只有 0.74%）**
- 现象：36,780 个 session 只有 274 个收到 `driver_assigned`，`ws_msgs_received` 仅 2,636。
- 根因：driver 数量撑不起 rider 爆发拉单，driver-service 的 GEO 撮合 + RabbitMQ 派单 fan-out 是单点串行。
- 扩展方案：① driver-service 水平扩容；② 派单流**按地理区域分片消费**（geohash 前缀做 RabbitMQ routing key，不同区域不同消费者并行）；③ GEOSEARCH 半径动态收窄（高峰只找最近的，降低候选集）；④ 派单加超时重投——司机 N 秒不接换下一个。

**② auth bcrypt（p99 实测 15s）**
- 根因：bcrypt 是**故意设计的慢哈希**（抗暴力破解），CPU 密集，爆发登录时 CPU 抢占。
- **不能降 cost**——那是产品安全设定。扩展方案：① api-gateway 水平扩容分摊 CPU；② 长 token（access TTL 调长）摊薄登录频率；③ 登录限流 + 排队，保护下游;④ 真要快可换 argon2id 调参，但这是安全团队的决策不是压测能定的。
- 这题的关键是**表态**："这不是 bug，是安全和性能的固有 tradeoff，工程上靠扩容和 token 策略摊薄，不靠削弱安全。"

**③ /trip/start 边缘失败 1.95%**
- 推断：高并发下 Mongo `CreateTrip` 写入 + Redis 幂等 SETNX 任一抖动就失败；Mongo 单实例无副本集、无 majority writeConcern。
- 扩展方案：Mongo 上副本集 + majority writeConcern + 写重试；幂等 key 失败做有限退避重试。

### Q：这次压测有什么没测到 / 局限？（主动说，加分）

- 坐标是**均匀随机近似**，没还原"演唱会散场起点集中、终点长尾"的真实分布。
- 司机是 **k6 模拟的 WS 客户端**，不是真实手机 GPS 上传（但协议帧 trip_request→trip_accept 是真的）。
- 受本机硬件限制用了 `K6_SCALE=0.4` 等比缩流量，方案目标是 2000 rider 峰值，实际跑 800。
- 没测**支付链路**的压力（Stripe 是外部依赖，压测打真 Stripe 不现实）。
- 主动说边界 = 体现你知道压测结果的适用范围,不是"全绿就万事大吉"。

### Q：为什么不直接调阈值让 SLO 全过？

"压测的价值是**暴露真实容量边界**，不是表演一张全绿报告。auth 15s、派单 0.74% 这些我都如实写进 REPORT 的'瓶颈分析'章节，并给出生产扩展方案。**调阈值掩盖问题 = 把风险留给线上**，这违背做压测的初衷。"

## 背诵优先级

1. **必背**：第一层 STAR 30 秒 + 坑 1（Hijacker）完整版——这俩占面试 70% 命中率。
2. **重点**：第二层 k6/Prometheus 选型对比 + 第四层"量上来怎么扩"的派单容量答案。
3. **加分**：主动说局限（第四层 Q2）+ "不调阈值掩盖"的态度。
