## 1. 压测三件套总览(为什么是这个组合)

### 三件套各自的职责(一图 + 一句话)

```
   [k6 加压侧]            [Prometheus 数据侧]         [Grafana 可视化]
   ┌────────────┐          ┌─────────────────┐        ┌─────────────┐
   │ 模拟 rider │  HTTP    │ scrape /metrics │ query  │ 一张面板    │
   │   driver   │ ───────► │ business 指标   │ ─────► │ 看 4 行图   │
   │  attacker  │          │                 │        │ 故障 anno   │
   └────┬───────┘          │ remote_write    │        └─────────────┘
        │ k6_* metrics     │ k6 指标         │             ▲
        └────────────────► │                 │             │ data
                           └─────────────────┘             │
                                  ▲                        │
                                  │ scrape                 │
                                  │                        │
                            [SUT 业务服务]                 │
                            api-gateway / trip /            │
                            driver / payment                │
                                  ▲                        │
                                  │ kill / delay / loss    │
                            ┌─────┴─────┐                  │
                            │ Chaos Mesh│ ─── annotation ──┘
                            │  Workflow │
                            └───────────┘
                            [故障侧]
```

**一句话**:**k6 模拟用户打流量**,**业务服务暴露 /metrics 端点 + k6 自己的指标都进 Prometheus**,**Grafana 一张面板看业务+压测指标 + 故障注解**,**Chaos Mesh 在峰值窗口注入故障验证 SLO 退化**。

### 为什么是这个组合,不是 JMeter / Locust / InfluxDB

| 选 ✓ | 弃 ✗ | 理由 |
|---|---|---|
| **k6**(JS 脚本) | JMeter(GUI/XML) | k6 脚本是代码,可 review、可 git 管理、可写复杂逻辑(WS、JWT 复用、状态共享);JMeter 的 XML 工程量大且不可读 |
| **k6**(JS,goja 引擎) | Locust(Python) | k6 单机能起 1000+ VU,goja 性能比 Python 解释器好;Locust 上 1000 VU 要分布式 |
| **Prometheus**(单实例 scrape + remote_write) | InfluxDB / TimescaleDB | k6 自带 `xk6-output-prometheus-remote` 扩展,业务+压测指标直接走同一个数据源,Grafana 不用切 datasource;若用 InfluxDB,k6 的 metrics 在 InfluxDB、业务指标在 Prometheus,面板要切 |
| **Chaos Mesh**(k8s CRD) | Toxiproxy / Pumba | Chaos Mesh 原生支持 PodChaos / NetworkChaos / Workflow 编排,k8s 项目无缝集成;Toxiproxy 只能注网络故障 |

**一句话**:全在 Kubernetes 内,业务指标 + 压测指标 + 故障注入**全部能看到同一时间线**,这是写报告和讲面试的关键。

### 三件套各自的「最小心智模型」(20 字以内)

| 工具 | 最小心智模型 |
|---|---|
| k6 | "用 JS 脚本控的并发请求发射器" |
| Prometheus | "定时拉 /metrics + 接收 remote_write 的时序数据库" |
| Grafana | "查 Prometheus + 画图 + 标 annotation 的看板" |
| Chaos Mesh | "用 YAML CRD 在 k8s 里安排故障的工具" |

### 面试速答(三件套总览)

> "k6 当加压器,业务和 k6 的指标都通过 Prometheus 收(scrape + remote_write 同源),Grafana 一张面板看 4 行图,Chaos Mesh 在峰值窗口用 Workflow 串行注入故障 —— 全在 Kubernetes 里跑,SLO 退化和恢复曲线在同一时间线上一目了然。"

## 2. k6 — 加压侧(STAR)

### 2.1 核心概念(从零)

**VU(Virtual User)**:k6 跑的并发执行单元。**1 VU ≈ 1 个 goroutine**(k6 用 Go 写的)。每个 VU 独立调度。

**Iteration(迭代)**:1 个 VU 跑完 1 次脚本主体(`export default function`)叫 1 次 iteration。VU 默认无限循环 iteration。

**Scenario(场景)**:k6 的「执行模式定义」,描述一组 VU 怎么调度。一个脚本可以有多个 scenario 同时跑,每个 scenario 有自己的 `executor`、自己的 `exec` 函数。

**Executor(执行器)**:Scenario 的调度策略。常用三种:
- `ramping-vus`:VU 数量按时间线爬升/回落(模拟流量曲线)
- `constant-vus`:VU 数量恒定(模拟一直在线的用户)
- `constant-arrival-rate`:每秒发起固定次数 iteration(关注 RPS 而非 VU 数)

**Threshold(阈值)**:k6 内置 SLO 表达式,跑完后违反阈值 → exit code 非 0,适合 CI 卡门禁。
```js
thresholds: {
  'http_req_duration{endpoint:start}': ['p(99)<500']
}
```

**Check**:类似 assertion 但不会让脚本停。统计 pass/fail rate。
```js
check(res, { 'preview 2xx': r => r.status === 200 });
```

**Tag**:给 metric 打 label,后续可以按 label 过滤聚合。
```js
http.post(url, body, { tags: { endpoint: 'start' } });
// 之后 http_req_duration{endpoint:"start"} 单独可查
```

**xk6**:k6 的扩展构建工具。官方 k6 二进制功能受限,要用 `xk6 build --with <扩展>` 自己编。本项目用 `xk6-output-prometheus-remote` 把 k6 metrics 推到 Prometheus。

### 2.2 STAR — k6 在本项目里怎么用的

**Situation(场景)**:演唱会散场,2000 个乘客 1 秒内涌入叫车,800 个司机在线接单,加上 500 RPS 的恶意流量打伪造 tripID(防穿透验证)。系统部署在本地 Minikube,要验证 SLO(p99 延迟、错误率、派单成功率、Bloom 拦截率)。

**Task(任务)**:**一份 k6 脚本一次跑完「基线 → 爬升 → 峰值 → 故障注入 → 恢复」全流程**,无需人工中途干预。

**Action(做法)**:`loadtest/k6/scenarios/concert.js` 一个脚本里定义三个并行 scenario:

```js
export const options = {
  scenarios: {
    riders: {                          // 乘客 — 关心延迟和成功率
      executor: 'ramping-vus',
      stages: [
        { duration: '1m',  target: 50 },    // 基线
        { duration: '2m',  target: 2000 },  // 爬升(2 分钟内涨 40 倍)
        { duration: '10m', target: 2000 },  // 峰值(故障注入窗口)
        { duration: '2m',  target: 300 },   // 回落
        { duration: '2m',  target: 50 },    // 恢复
      ],
      exec: 'riderFlow',
    },
    drivers: {                         // 司机 — 关心 WS 长连接的稳定性
      executor: 'constant-vus',
      vus: 800,
      duration: '17m',
      exec: 'driverFlow',
      startTime: '30s',                // 等 rider 有订单再让 driver 上线
    },
    attackers: {                       // 攻击者 — 验 Bloom 拦截
      executor: 'constant-arrival-rate',
      rate: 500, timeUnit: '1s',       // 锁死 500 RPS
      duration: '17m',
      preAllocatedVUs: 100, maxVUs: 200,
      exec: 'attackerFlow',
    },
  },
  thresholds: profile === 'baseline' ? baselineThresholds : chaosThresholds,
};
```

三角色对应三个 `exec` 函数,共用 `helpers/auth.js` 拿 token、`helpers/payload.js` 构造请求体。

**为什么三种 executor 都用上了?**
- 乘客用 `ramping-vus`:**真实流量是有曲线的**,不是恒定。基线 → 爬升 → 峰值 → 回落是演唱会场景的天然形状。
- 司机用 `constant-vus`:司机一开班就在线,不随单量增减,所以恒定 VU。
- 攻击者用 `constant-arrival-rate`:攻击关心**RPS**(每秒打多少包),不关心 VU 数。`constant-arrival-rate` 自动调 VU 来打到目标 RPS。

**SLO 阈值拆 baseline / chaos 两档**(`loadtest/k6/thresholds.js`):
- baseline(无故障):严格 — preview p99 < 300ms / start p99 < 500ms / 派单 > 98%
- chaos(故障窗口):宽松 — preview p99 < 500ms / start p99 < 800ms / 派单 > 96%
- **Bloom 拦截率两档都不放宽**(>98%):故障下也不应该让攻击穿透到 Mongo

**WebSocket 用法**(rider 等 driver_assigned 事件,driver 接 trip_request):
```js
ws.connect(wsURL, { headers }, function (socket) {
  socket.setTimeout(() => socket.close(), 15000);    // 15s 超时
  socket.on('message', msg => {
    const data = JSON.parse(msg);
    if (data.type === 'trip.event.driver_assigned') {
      tripAssignedWithin15s.add(true);                // 自定义 Rate metric
      socket.close();
    }
  });
});
```

**自定义 metric**(k6 内置 metric 不够用时):
```js
import { Rate } from 'k6/metrics';
const tripAssignedWithin15s = new Rate('trip_assigned_within_15s');
// ... 后续 .add(true/false) 累计
```

**xk6 自编二进制**:
```bash
go install go.k6.io/xk6/cmd/xk6@latest
xk6 build --with github.com/grafana/xk6-output-prometheus-remote
# 产物 ./k6,跑的时候:
./k6 run -o 'experimental-prometheus-rw=http://localhost:9090/api/v1/write' concert.js
```

**Result(结果)**:Round 2(SCALE=0.4)真值:
- 总请求 276,326,17min,`vus_max=1200`,`dropped_iterations=2592`(0.97%,执行器没饱和)
- 三角色全部按预期执行:rider 端拿到 800 个并发账号、driver 端 320 个常驻 WS、attacker 端稳定 200 RPS
- 自定义 metric `trip_assigned_within_15s = 0.74%` 暴露派单容量瓶颈,`attacker_blocked_by_bloom = 100%` 验证防穿透
- 阈值全部用 `--summary-export` 导出 JSON 归档

### 2.4 常见追问

**Q:为什么 k6 不用 Locust / JMeter?**
> Locust 单机 1000 VU 就要分布式;JMeter 是 GUI/XML 工程不可读不易 review。k6 脚本是 JS 可以 git 管理 + 写复杂逻辑(WS、JWT 复用、自定义 metric),单机 2000 VU 没问题。

**Q:`ramping-vus` 和 `constant-arrival-rate` 区别?**
> ramping-vus 控**并发数**(同时多少 VU 在线),constant-arrival-rate 控**RPS**(每秒发多少 iteration)。前者适合模拟"流量曲线"(峰值散场),后者适合"恒定攻击"(攻击者不在乎 VU 数,只在乎打多快)。

**Q:k6 thresholds 不通过会发生什么?**
> 测试跑完 exit code 非 0,k6 stdout 标 ✗,适合接 CI 卡 PR 门禁。本项目压测不进 CI(一次性活动),阈值用来人工判定 SLO 是否达标。

**Q:为什么 k6 metrics 也走 Prometheus 不用 k6 自己的 InfluxDB?**
> 单一数据源原则。业务 /metrics 走 Prometheus scrape、k6 走 Prometheus remote_write,**Grafana 同一面板查同一个 datasource**;否则切 datasource 看图很难做对照(故障期间业务 P99 vs k6 客户端测的 P99 是不是一致)。

**Q:VU 和真实用户数的关系?**
> 不能 1:1 换算。1 VU 是一个**循环跑脚本的执行单元**,iteration 之间没有思考时间(除非 `sleep()`);1 个真实用户的「思考-请求-思考」节奏可能 10s 才发 1 次请求,所以 1 VU ≈ 几十个真实用户的并发等价。

## 3. Prometheus — 数据侧(STAR)

### 3.1 核心概念(从零)

**Pull 模型**:Prometheus 是**主动拉**的,定时(默认 15s)去每个 target 的 `/metrics` HTTP endpoint 抓数据。这点和 InfluxDB / StatsD 的 push 模型不同。

**Time Series**:Prometheus 的数据单位是**带 label 的时间序列**。一条时间序列由 metric name + labels 唯一确定:
```
http_requests_total{service="api-gateway", method="POST", path="/trip/start", status="200"}
```
每个时间序列存一连串 (timestamp, value)。

**4 类指标**(必须能区分):

| 类型 | 用途 | 例子 | 用 PromQL 怎么查 |
|---|---|---|---|
| Counter | 单调递增计数器 | 请求总数、错误数 | `rate(http_requests_total[1m])` |
| Gauge | 可增可减当前值 | 当前 VU 数、队列深度 | `rabbitmq_dlq_depth` |
| Histogram | 把观测值分桶 | 请求延迟分布 | `histogram_quantile(0.99, rate(*_bucket[1m]))` |
| Summary | 客户端预算分位数 | 同上(不推荐,无法跨实例聚合) | `*_quantile{quantile="0.99"}` |

**Histogram 是怎么算 P99 的?** 客户端把每次观测落到对应 bucket(如 `[0.005, 0.01, 0.025, ..., 5]` 秒),增加该 bucket 的计数。服务端用 `histogram_quantile(0.99, ...)` 反算 P99 —— **是估算,不是精确值**,bucket 切得越密越准。

**Scrape Config**:Prometheus 服务端配置,告诉它去哪些 target 拉数据:
```yaml
scrape_configs:
  - job_name: 'api-gateway'
    static_configs:
      - targets: ['api-gateway:8081']    # 业务服务的 Service DNS
```

**Remote Write Receiver**:Prometheus 反过来**接收**外部写入(通过 `--web.enable-remote-write-receiver` 启用)。k6 的 Prometheus 输出走这条路:k6 把 metrics 用 protobuf 推到 Prometheus 的 `/api/v1/write` endpoint,等于把 push 模型嫁接到 pull 模型的 Prometheus 上。

**PromQL 速查(必会)**:
```promql
# 1m 内 QPS by 端点
sum by (path) (rate(http_requests_total[1m]))

# P99 延迟 by 端点(Histogram)
histogram_quantile(0.99,
  sum by (le, path) (rate(http_request_duration_seconds_bucket[1m]))
)

# 5xx 错误率
sum(rate(http_requests_total{status=~"5.."}[1m]))
  / sum(rate(http_requests_total[1m]))

# Bloom 拦截率(rate)
sum(rate(bloom_filter_hits_total{result="miss_rejected"}[1m]))
  / sum(rate(bloom_filter_hits_total[1m]))
```

### 3.2 STAR — Prometheus 在本项目里怎么用的

**Situation**:压测期间产生 4 类数据需要看到同一时间线:
1. 业务侧的 HTTP 延迟、错误率、QPS
2. 业务侧的 RabbitMQ 消费成功率、DLQ 深度
3. 业务侧的并发控制指标(Bloom 命中、限流拦截、接单锁冲突、幂等去重)
4. k6 客户端测得的延迟和 VU 数

如果分两个数据源(业务 Prometheus + k6 InfluxDB),Grafana 切 datasource 看不到时间对齐。

**Task**:用一个 Prometheus 实例同时承担 scrape(业务侧) + receive(k6 侧),Grafana 单一 datasource。

**Action**:

1. **业务服务侧加 `/metrics` endpoint**(`shared/metrics/metrics.go` + `middleware.go`):

```go
var (
    httpRequestsTotal = prometheus.NewCounterVec(
        prometheus.CounterOpts{Name: "http_requests_total"},
        []string{"service", "method", "path", "status"},
    )
    httpRequestDuration = prometheus.NewHistogramVec(
        prometheus.HistogramOpts{
            Name: "http_request_duration_seconds",
            Buckets: []float64{0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5},
        },
        []string{"service", "method", "path"},
    )
)

func Middleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        rec := &statusRecorder{ResponseWriter: w, status: 200}
        next.ServeHTTP(rec, r)
        path := normalizePath(r.URL.Path)            // /trip/abc → /trip/:id 防高基数
        httpRequestsTotal.WithLabelValues(...).Inc()
        httpRequestDuration.WithLabelValues(...).Observe(time.Since(start).Seconds())
    })
}
```

**关键设计点**:
- **path 模板化**:`/trip/abc123` → `/trip/:id`,否则 ObjectID 千变万化会炸时间序列基数
- **Hijacker 透传**(Round 2 教训):`statusRecorder` 包了 ResponseWriter 必须实现 `http.Hijacker.Hijack()`,否则 `/ws/*` 路由握手失败 400
- **Histogram bucket** 选 `[0.005, ..., 5]` 秒,覆盖 5ms-5s 的合理延迟区间;P99 估算误差 ≤ 相邻两个 bucket 的差

2. **Prometheus 配置**(`infra/development/k8s/prometheus.yaml`):

```yaml
spec:
  containers:
    - name: prometheus
      args:
        - "--config.file=/etc/prometheus/prometheus.yml"
        - "--storage.tsdb.retention.time=2h"          # 一场压测 17min,2h 够复盘
        - "--web.enable-remote-write-receiver"        # 关键:接收 k6 推送
      resources:
        limits:
          memory: "1Gi"                               # 关键:WAL 累积下 512Mi 会 OOM
data:
  prometheus.yml: |
    scrape_configs:
      - job_name: 'api-gateway'
        static_configs: [{targets: ['api-gateway:8081']}]
      - job_name: 'trip-service'
        static_configs: [{targets: ['trip-service:9100']}]
      # ... 4 个业务服务
```

3. **k6 输出到 Prometheus**:
```bash
./k6 run -o 'experimental-prometheus-rw=http://localhost:9090/api/v1/write' concert.js
```
k6 自动把 `http_req_duration`、`vus`、自定义 metric 都序列化成 Prometheus 格式 push 过去,前缀通常是 `k6_*`。

**Result**:
- 业务侧采到 8 个核心指标(HTTP / RabbitMQ / 并发控制),scrape interval 15s,Round 2 17min 共 ~68 个数据点/series
- k6 侧采到 `k6_vus`、`k6_http_reqs`、`k6_http_req_duration_seconds_*` 等 ~30 个 series
- Grafana 一张面板上同图叠加 `http_request_duration_seconds`(业务测) 和 `k6_http_req_duration_seconds`(k6 测),延迟数字基本一致(差异 < 5ms,源于网络栈差),证明业务侧 metrics 中间件的统计是对的

### 3.4 常见追问

**Q:Prometheus pull 模型有什么好处?**
> 服务发现简单(scrape_configs 列出 target);target 挂了 Prometheus 知道(`up=0`),push 模型则不知道是没数据还是 client 挂了;target 自己控制 expose 频率不会被打挂。

**Q:Histogram 和 Summary 的区别?**
> Histogram 在客户端只算桶计数,服务端用 PromQL `histogram_quantile` 反算分位数,**可以跨实例聚合**(把 4 个 pod 的 histogram 加起来再算 P99 是有意义的);Summary 在客户端就算好了 quantile,**不能跨实例聚合**(把 4 个 pod 的 P99 取平均没意义)。生产几乎只用 Histogram。

**Q:Histogram bucket 怎么选?**
> 覆盖你关心的延迟区间 + 阈值附近密一点。本项目阈值是 P99 < 500ms,所以在 100ms-1s 区间放了 4 个 bucket(`0.1, 0.25, 0.5, 1`),保证 P99 估算误差 < 250ms。

**Q:为什么 path 要模板化?**
> Prometheus 时间序列基数 = labels 笛卡尔积。`/trip/507f1f...` 这种 ObjectID 是高基数,几百万个 trip 就有几百万条 series,Prometheus 内存爆。模板化成 `/trip/:id` 把基数降回常数。

**Q:remote_write receiver 是什么、怎么用?**
> Prometheus 加 `--web.enable-remote-write-receiver` 启动参数后,`/api/v1/write` 路径接受外部 push(protobuf 编码的时间序列)。k6 的 `xk6-output-prometheus-remote` 扩展、Grafana Agent、OpenTelemetry collector 都可以这么推。

**Q:为什么不直接让 Prometheus 抓 k6?**
> k6 是临时进程(压测结束就退),Prometheus pull 模型要求 target 长期可达。Push 是 stateless 进程的标准做法。

### 3.5 面试速答(Prometheus 部分)

> "Prometheus 是 pull 模型时序数据库,业务每个服务暴露 `/metrics` 端点(Counter / Gauge / Histogram 三类),Prometheus 每 15s scrape 一次。**项目关键配置是开了 `--web.enable-remote-write-receiver`**,k6 通过 `xk6-output-prometheus-remote` 把客户端测的延迟和 VU 数 push 到同一个 Prometheus,Grafana 单 datasource 看业务+压测指标的同一时间线。Histogram 的 P99 用 `histogram_quantile` 在 PromQL 里反算,bucket 选在阈值附近密一点保证估算精度。"

## 5. Chaos Mesh — 故障侧(STAR)

### 5.1 核心概念(从零)

**Chaos Mesh** 是云原生混沌工程平台,所有故障都是 **Kubernetes CRD**(Custom Resource Definition)。你写 YAML 描述「在哪个 namespace、选哪些 pod、注什么故障、持续多久」,Chaos Mesh Controller 就执行。

**核心 CRD 类型**:

| CRD | 作用 | 项目用例 |
|---|---|---|
| **PodChaos** | kill / failure / container-kill | T+8 kill driver-service、T+11 kill api-gateway |
| **NetworkChaos** | delay / loss / partition / corrupt / duplicate | T+9 redis 延迟 50ms、T+10 mongo 丢包 10% |
| **StressChaos** | CPU / memory 压测 | (本项目未用) |
| **IOChaos** | 文件系统延迟/错误 | (本项目未用) |
| **TimeChaos** | 调时钟 | (本项目未用) |

**Selector(选择器)**:决定故障打到谁身上。常用字段:
```yaml
selector:
  namespaces: ["default"]
  labelSelectors:
    app: "driver-service"
mode: one          # one(随机选 1 个) / all / fixed(选固定数量) / fixed-percent / random-max-percent
```

**Workflow**:把多个 chaos 实验**串行/并行编排**,带 Suspend(等待)节点。本项目用 Workflow 来精确控制故障注入时间线:
```yaml
spec:
  entry: chaos-sequence
  templates:
    - name: chaos-sequence
      templateType: Serial
      deadline: 20m
      children:
        - wait-8min        # Suspend 8m
        - kill-driver-pod  # PodChaos 60s
        - wait-1min        # Suspend 1m
        - redis-delay      # NetworkChaos 60s
        - wait-1min
        - mongo-loss       # NetworkChaos 60s
        - wait-1min
        - kill-gateway-pod # PodChaos 60s
```

**Schedule**:周期性触发故障(本项目用一次性的 Workflow,没用 Schedule)。

### 5.2 STAR — Chaos Mesh 在本项目里怎么用的

**Situation**:Round 2 baseline 跑出无故障真值后,需要验证「故障下 SLO 退化幅度 + RTO」—— 不是看系统有多快,而是看**它有多韧**。演唱会现场不可能没故障,关键是恢复速度。

**Task**:在峰值窗口(T+8 到 T+12)按时间线串行注入 4 类故障,每次只打一个依赖,便于单独归因;故障期间 SLO 阈值放宽到 chaos 档,故障窗口结束后 60s 内各指标必须回到基线 ±10%。

**Action**:`loadtest/chaos/schedule.yaml` 一个 Workflow 编排 4 个 60s 的故障实验:

```yaml
# 1. T+8min:kill driver-service pod 60s
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata: {name: kill-driver-pod}
spec:
  selector:
    namespaces: ["default"]
    labelSelectors: {app: "driver-service"}
  mode: one
  action: pod-kill
  duration: "60s"

# 2. T+9min:redis 延迟 50ms 60s
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata: {name: network-delay-redis}
spec:
  selector:
    namespaces: ["default"]
    labelSelectors: {app: "redis"}
  mode: all
  action: delay
  delay: {latency: "50ms"}
  duration: "60s"

# 3. T+10min:mongo 10% 丢包 60s
# 4. T+11min:kill api-gateway pod 60s
```

**故障窗口为什么放在 T+8 到 T+12 而不是 T+0**?
- T+0 到 T+3:rider ramping 0→2000,系统在爬升,这时打故障归因不清(是爬升失败还是故障打的)
- T+3 到 T+13:稳态峰值,这时打故障能清晰看到「稳态 → 退化 → 恢复」三段曲线
- 故障之间留 1 分钟恢复窗口,避免下一次注入时还没从上一次恢复

**4 次故障各自要看的 SLO 反应**:

| 故障 | 期望反应 | 验证什么 |
|---|---|---|
| driver-service kill | `trip_assigned` 瞬时跌到 ~80% → 10s 内恢复 | RabbitMQ 消费者自动重连 + 消费端幂等让重投不重复派单 |
| redis 50ms delay | preview / start P99 顶到 1.5s 后回落 | 缓存降级:Bloom miss 走 Mongo,但不应导致 5xx |
| mongo 10% loss | trip 写失败 + RabbitMQ DLQ 涨 | 写失败重试,消费端幂等 release → 重试自愈,RPO=0 |
| gateway kill | k6 VU 短暂失败,gateway 重启后重连 | k8s Service 自动负载均衡到新 pod |

**Result(目前 Round 2 已跑,Round 3 待跑)**:
- Round 2 基线已确认 baseline 5/7 SLO,3 真瓶颈记录在案
- Round 3 跑后期望产出:**4 条 annotation 竖线** + **每个故障窗口的 SLO 退化峰值** + **恢复时长(RTO)**

### 5.4 常见追问

**Q:为什么是 Chaos Mesh 不是 Toxiproxy / Pumba?**
> Toxiproxy 只能注网络故障(延迟/丢包/带宽),不能 kill pod;Pumba 只针对 docker 不原生支持 k8s。Chaos Mesh 是 CNCF 项目,k8s 原生 CRD + Workflow 编排,故障种类齐全。

**Q:故障编排为什么要用 Workflow 而不是 Schedule?**
> Schedule 是周期性触发(cron 风格),用于持续性混沌测试。本项目是一次性压测,用 Workflow 精确控制时间线(Serial 串行 + Suspend 等待),四次故障在固定 T+8/9/10/11 注入。

**Q:`mode: one` 是什么意思?**
> 选中 selector 匹配的 pod 中的 1 个(随机)注故障。还有 `all`(全部)、`fixed`(固定数量)、`fixed-percent`(固定百分比)。本项目 driver-service 多副本时只 kill 1 个,看流量重分配;redis 是单副本所以 `mode: all`。

**Q:NetworkChaos 怎么实现的?**
> Chaos Daemon 在每个 k8s 节点跑一个 DaemonSet pod,注故障时通过 nsenter 进入目标 pod 的 network namespace,用 `tc qdisc`(Linux Traffic Control)加 `netem` 规则实现 delay / loss / corrupt。生命周期结束自动 `tc qdisc del` 还原。

**Q:Chaos 实验什么时候算"恢复"?**
> 实验自带 `duration` 字段,到期 Chaos Mesh 自动撤销故障(kill pod 后 k8s 自己重建,delay 规则被 `tc qdisc del`)。RTO = 业务指标回到基线 ±10% 的时间,通常滞后 duration 几十秒(消费者重连、缓存预热、连接池重建都要时间)。

**Q:annotation 怎么打到 Grafana 上?**
> 两种方式:① Chaos Mesh 写 k8s event,kube-state-metrics + Grafana annotation query 自动同步(复杂);② 简化版:`loadtest_run.sh` 实验启停时自己 curl Grafana 的 `/api/annotations` API 打注解(本项目这么做)。

### 5.5 面试速答(Chaos Mesh 部分)

### T — 跑出 baseline 真值,定位真瓶颈

阈值表(baseline 严):
| 指标 | 阈值 |
|---|---|
| preview p99 | < 300ms |
| start p99 | < 500ms |
| auth p99 | < 1000ms |
| preview / start 失败率 | < 1% |

### A — 三轮跑 + 8 bug 修复 + 第三轮真值

**第 1 次 Round 2(2026-04-27)**: SCALE=0.25,4c CPU 撞顶,preview p99=60s 撞 gateway 超时,**没参考价值**。
**第 2 次(2026-04-28 00:07)**: 集群重建升到 12c/24G,吞吐 19×(537k 请求),症状从「全部很慢」变成:
- preview 失败率 75%(不是 0%)
- `trip_assigned=0%`(永 0)
- Bloom 拦截 53%(从 100% 退到一半)

**错误归因路径**(我栽过的坑):怀疑 Mongo Atlas 跨区延迟、Bloom 高并发 BF.EXISTS timeout、driver-assigned 事件路由错。**全错**。

**正确诊断起点**:`ws_session_duration` avg = 166ms。正常应该 ≤ 15s(rider 等满超时)。**WS 根本没建立**,不是匹配链路。

**对症 curl 复现**:`curl -i -H "Upgrade: websocket" /ws/riders` 返回 **400 Bad Request**。

**读源码**:gorilla/websocket `Upgrader.Upgrade()` 第一步 `w.(http.Hijacker)` 类型断言,失败 400。问题在 `shared/metrics/middleware.go` 的 `statusRecorder` 没实现 `http.Hijacker`。

**这是第 1 个 bug 的诊断起点,后面顺藤摸出 8 个**:

| # | bug | 修复对应 |
|---|---|---|
| 1 | metrics middleware 没透传 `http.Hijacker` | `statusRecorder` 加 `Hijack()` |
| 2 | k6 payload 字段 `startLocation/endLocation` 与 gateway `pickup/destination` 不对齐 | 改字段名 |
| 3 | `/ws/riders` 缺 query param `userID` | URL 加 `?userID=...` |
| 4 | `/ws/drivers` 缺 query param `packageSlug` | URL 加 `?userID=...&packageSlug=suv` |
| 5 | driver 回执 type "driver_response" 不在 gateway switch case | 改成 `driver.cmd.trip_accept/decline` |
| 6 | tripID 路径 `data.tripID` 不存在(实际是 `data.trip.id`) | 路径改对 |
| 7 | driver 用 `packageSlug=luxury`,rider 取 `rideFares[0]` 是 `suv`,司机池不在同一分区 | driver 改 `suv` |
| 8 | `attacker_blocked_by_bloom` 口径仅 `status===404`,把 graceful degradation 当漏 | 改 `status !== 200` |

**第 3 次(2026-04-29 00:01,SCALE=0.4)真值出炉**。

### R — 真值 + 3 个真瓶颈

**5/7 SLO 全过(改善幅度量级级):**
- preview p99: 3119ms → **44.55ms**(70× 改善)
- start p99: 6545ms → **367.41ms**(17× 改善)
- preview 失败率: 75% → **0%**
- start 失败率: 81% → 1.95%(41× 改善,贴边但未达标)
- Bloom 拦截率: 53% → **100%**

**剩下 3 项暴露真瓶颈(不是 bug):**

| 真瓶颈 | 数字 | 根因 | 工程做法 |
|---|---|---|---|
| **B1 bcrypt** | auth p99=15.18s | bcrypt cost=10 在启动期 800 rider 集中登录被 CPU 抢占 | 长 token 摊薄 / 水平扩 api-gateway / 不降 cost |
| **B2 派单容量** | `trip_assigned_within_15s = 0.74%` | driver VU 320 撑不起 rider 800 爆发,`ws_msgs_received` 仅 2636 / 36780 sessions | 水平扩 driver-service + 派单按区域分片消费 + 调小 GEO 半径 |
| **B3 start race** | `failed = 1.95%` | Mongo CreateTrip + Redis 幂等 SETNX 任一抖动都可能失败 | Mongo 上副本集 + majority writeConcern,Redis Cluster |

**附加澄清**:`http_req_failed: 73%` 是 attacker 设计预期的 404(全打伪造 tripID),不是业务失败。

### 这一轮拿到的方法论(面试金句)

1. **症状变化是诊断信号,不是病情加重** — Bloom 100% → 53% 看着是回退,实际是吞吐变大后真值显形。
2. **压测 bug 多在脚本不在系统** — 7/8 修复在 k6/中间件层,业务代码动 0 行。
3. **错误归因比没归因更危险** — 我曾错怪 Mongo Atlas、Bloom timeout、事件路由,读源码对照协议字段一次到位。
4. **执行器饱和 vs 真瓶颈要分开** — `dropped_iterations > 5%` 是执行器饱和,数据不可信;Round 2 第 3 次跑出 0.97%,数据干净。
5. **Go 中间件包 ResponseWriter 必须显式透传可选接口** — `Hijacker` / `Flusher` / `Pusher` 任一漏一个,WS / SSE / HTTP/2 push 都会无声坏掉。

### 面试讲法(2 分钟终极版)

> "项目里我做了一套演唱会散场端到端压测。**S**:模拟 2000 个乘客 1 秒内同时叫车 + 司机长 WebSocket 在线 + 攻击者 500 RPS 持续打伪造 tripID。**T**:用一个 k6 脚本跑完三角色基线/爬升/峰值/故障注入/恢复,SLO 阈值拆 baseline 严格档和 chaos 宽松档,业务指标和 k6 指标走同一个 Prometheus,Grafana 一张面板看 4 行图,Chaos Mesh Workflow 在峰值窗口串行注入 4 次故障。
>
> **A**:第一次跑 SLO 全炸,我先错怪了 Mongo 和 Redis,后来发现 `ws_session_duration` 才 166ms 是死值,curl 一打 `/ws/riders` 是 400 Bad Request,读 gorilla/websocket 源码定位到我自己写的 metrics 中间件没实现 `http.Hijacker.Hijack()`,顺藤摸出 8 个脚本/中间件 bug —— 全在压测层,业务代码动了 0 行。
>
> **R**:第三次重跑得到真值,5/7 SLO 全过(preview p99 44.55ms / start p99 367ms / Bloom 拦截 100%);剩下 3 项暴露真瓶颈 —— bcrypt 是 auth 慢路径(p99 15s,产品安全设定不能动)、driver-service 撮合容量撑不起 800 rider 爆发(`trip_assigned=0.74%`)、start 边缘 1.95% 失败贴近 Mongo 单实例的写入抖动阈值。这些写进了 REPORT,不调阈值掩盖问题。
>
> 最大的教训是:**症状变化是诊断信号,压测 bug 多在脚本不在系统,Go 中间件包 ResponseWriter 必须显式透传可选接口**。"

## 7. 面试速答清单(常见追问的一行答)

### 总体设计

| 问题 | 一行答 |
|---|---|
| 你们怎么压测的? | k6 三角色一脚本 + Prometheus 同源数据 + Grafana 同面板 + Chaos Mesh 峰值窗口注入 |
| 为什么不用 JMeter? | JMeter XML 工程不可读、不可 git 管理;k6 脚本是 JS 代码、可 review 可写复杂逻辑 |
| 为什么压测在本地不在公网? | 本机 Minikube 全栈可重现,不污染线上指标;追的是 SLO 验证不是极限 QPS |
| SLO 阈值怎么定的? | baseline 档严(preview p99 < 300ms)、chaos 档宽(< 500ms);Bloom 拦截率两档都不放宽 |

### k6

| 问题 | 一行答 |
|---|---|
| VU 是什么? | k6 的并发执行单元 ≈ 1 个 goroutine,每个 VU 独立循环跑 iteration |
| 三种 executor 区别? | ramping-vus 控并发数 / constant-vus 恒定 VU / constant-arrival-rate 锁 RPS |
| threshold 和 check 区别? | threshold 不通过 exit 非 0 适合卡 CI;check 是 assertion,不停脚本只统计 pass rate |
| 为什么自编 xk6? | 官方 k6 不带 Prometheus remote_write 输出,要 `xk6 build --with xk6-output-prometheus-remote` |
| Tag 干什么用? | 给 metric 打 label,后续 `http_req_duration{endpoint:"start"}` 单独可查 |

### Prometheus

| 问题 | 一行答 |
|---|---|
| pull 模型好处? | 服务发现简单 / target 挂了能感知(up=0)/ target 自控 expose 频率不会被打挂 |
| Histogram vs Summary? | Histogram 客户端只算桶可跨实例聚合;Summary 客户端算 quantile 不能跨实例聚合,生产几乎只用 Histogram |
| Histogram bucket 怎么选? | 覆盖关心的延迟区间 + 阈值附近密一点,P99 估算误差 ≤ 相邻 bucket 差 |
| path 为什么模板化? | `/trip/abc123` 这种 ObjectID 千变万化会炸时间序列基数,模板化为 `/trip/:id` 降回常数 |
| remote_write 是什么? | Prometheus `--web.enable-remote-write-receiver` 后接受 push,k6 / Grafana Agent 都这么推 |
| PromQL 算 P99? | `histogram_quantile(0.99, sum by (le, path) (rate(*_bucket[1m])))` |

### Chaos Mesh

| 问题 | 一行答 |
|---|---|
| Chaos Mesh vs Toxiproxy? | Toxiproxy 只注网络故障,Chaos Mesh 是 CNCF k8s 原生 CRD,故障种类齐全可 Workflow 编排 |
| 为什么峰值窗口注入不是 ramp up? | ramp up 期归因不清(爬升失败 vs 故障打的),稳态注入能看清「稳态→退化→恢复」三段 |
| `mode: one` 什么意思? | selector 匹配的 pod 里随机选 1 个注故障;还有 all / fixed / fixed-percent |
| NetworkChaos 怎么实现的? | Chaos Daemon DaemonSet 用 nsenter 进 target pod netns,`tc qdisc + netem` 注 delay/loss,duration 到自动还原 |
| RTO 怎么算? | 业务指标回到基线 ±10% 的时间,通常滞后 duration 几十秒(消费者重连/缓存预热/连接池重建都要时间) |

### 真瓶颈 / 故事

| 问题 | 一行答 |
|---|---|
| auth p99 怎么 15s 这么慢? | bcrypt cost=10 在启动期集中登录被 CPU 抢占,产品安全设定不该降 cost,生产靠水平扩 api-gateway 解决 |
| 为什么 trip_assigned 只有 0.74%? | driver VU 320 撑不起 rider 800 爆发,`ws_msgs_received` 仅 2636/36780 sessions —— 是架构容量不是脚本 bug |
| 你怎么发现 trip_assigned=0% 的 bug 的? | `ws_session_duration` avg 只有 166ms 是死值,curl 一打 WS 是 400,读 gorilla 源码定位到 metrics 中间件没实现 `http.Hijacker.Hijack()` |
| 73% 总失败率怎么解释? | 全是 attacker 设计预期的 404(打伪造 tripID 触发 Bloom 拦截),不是业务失败 |
| 压测最大的教训? | 症状变化是诊断信号 / 压测 bug 多在脚本不在系统 / Go 中间件包 ResponseWriter 必须透传可选接口 |

## 8. 学习路径建议(1 小时 / 半天 / 一天)

### 1 小时:能讲一句话(防止被问蒙)

1. 读本文 § 1 三件套总览(15 min)
2. 读本文 § 6 项目终极 STAR(20 min)
3. 读本文 § 7 面试速答清单(15 min)

**到这一步**:能讲清楚「我们用 k6+Prometheus+Chaos Mesh 做了什么、SLO 数字是多少、3 个真瓶颈是什么」。

### 半天:能讲细节(覆盖大部分追问)

1. 1 小时路径全做完
2. 读本文 § 2 / § 3 / § 5(各 30-40 min,STAR + 项目代码)
3. 打开 `loadtest/k6/scenarios/concert.js` 自己读一遍,确认能解释每个 scenario 为什么用那个 executor(20 min)
4. 打开 `infra/development/k8s/prometheus.yaml` 看 scrape_configs 和启动参数(10 min)
5. 打开 `loadtest/chaos/schedule.yaml` 看 Workflow 节点顺序(10 min)
6. 读 `loadtest/report/REPORT.md` 把 SLO 表里的数字背下来(15 min)

**到这一步**:能讲细节,被追问 PromQL / k6 executor 选型 / NetworkChaos 实现原理时不慌。

### 一天:能扛深问(超出"准备的范围"也能反应)

2. 读 `文档/TUTORIAL.md § 9.2`(8 bug 详细叙事,1 小时)

**到这一步**:能扛 30 分钟以上的连续追问,即使被问到没准备过的细节(比如「histogram bucket 怎么选才能让 P99 误差小于 50ms」)也能现场推导。
