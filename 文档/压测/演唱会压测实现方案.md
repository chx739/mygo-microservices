## 0. 目标 & 不做清单（Boundary）

### 必须做到（Must）

- 一份 k6 脚本一次跑完「基线 → 爬升 → 峰值 → 故障注入 → 恢复」全流程，**无需人工中途干预**。
- 覆盖三角色并发：乘客（ramping-vus）、司机（constant-vus）、攻击者（constant-arrival-rate）。
- 峰值期间注入 4 类故障：pod kill、Redis 延迟、Mongo 丢包、driver-service 重启。
- Prometheus + Grafana 面板能在故障时间点看到**可视化自愈曲线**（故障 annotation + 业务指标叠图）。
- 产出 **3 张 Grafana 截图** + **1 份 Markdown 压测报告**，作为面试弹药。
- 所有 JWT 鉴权路径在压测中被真实打穿（`Authorization: Bearer <token>` 全程携带）。

### 不做（Out of Scope）

- **不追求极限 QPS**：目标是「峰值 + 故障下 SLO 达成」，不是把系统压崩。
- **不做公网压测**：全部在本地 tilt up 的 k8s 集群内。
- **不引入新语言**：k6 脚本用 JavaScript（k6 内置），不引入 Python/Locust。
- **不改业务代码逻辑**¹：只加指标暴露点（metrics endpoint），不改 handler 返回值/签名。
- **不做 CI 集成**：压测是一次性验证活动，不进 CI。

> ¹ **例外**：新增 `GET /trip/:id` 只读接口（api-gateway 透传到 trip-service，走既有 Bloom 预检），是压测覆盖 Bloom 链路的必需扩展。不属于业务逻辑修改，只是把现有能力暴露成 HTTP。

## 1. 技术栈（已定，不再决策）

| 组件 | 版本 | 用途 | 部署方式 |
|---|---|---|---|
| k6 | v0.50+ | HTTP + WebSocket 压测 | 宿主机直接跑 `k6 run`，通过 `host.docker.internal` 或 Ingress 打到 k8s |
| Prometheus | v2.50+ | 指标采集 | k8s Deployment，`infra/development/k8s/prometheus.yaml`（新增） |
| Grafana | v10+ | 可视化 | k8s Deployment，`infra/development/k8s/grafana.yaml`（新增） |
| Chaos Mesh | v2.6+ | 故障注入 | `curl -sSL https://mirrors.chaos-mesh.org/v2.6.0/install.sh \| bash`（官方一键） |
| Go prometheus client | `github.com/prometheus/client_golang` | 业务指标 | 各服务加 `/metrics` endpoint |
| k6 扩展 | `xk6-output-prometheus-remote`（**必选**） | k6 metrics 通过 remote_write 直推 Prometheus，单一数据源 | `xk6 build` 生成仓库根 `./k6` 二进制 |

**关键约束**：

- k6 在**宿主机**跑，用 `http://localhost:8081`（api-gateway 的 NodePort / port-forward）打流量。不在 k8s 内跑 k6，因为 k6 拖进容器里调度会污染压测目标。
- Prometheus scrape interval 固定 **15s**，保证压测 17 分钟窗口能收到 ≥60 个数据点。
- Grafana **单一 Prometheus datasource**：业务指标走 scrape、k6 指标走 remote_write，都进同一个 Prometheus，面板查询不依赖 k6 summary。
- **压测环境 JWT access TTL = 25min**（`JWT_ACCESS_TTL_SECONDS=1500`），覆盖 17min 场景总时长；生产仍保持 15min。

## 3. 实施步骤（按时间顺序，每步独立可验证）

> **硬规则**：每步完成后，先跑「该步验证」再进下一步。禁止最后统一验证。

### Day 3 前置：环境准备

#### Step 0：压测环境配置切换（TTL）

压测场景总时长 17min，生产 access TTL=15min 会导致脚本中途失效。因此**先切压测环境配置**，再进任何代码步骤。

**改动**：`infra/development/k8s/app-config.yaml`
```yaml
data:
  JWT_ACCESS_TTL_SECONDS: "1500"   # 压测环境专用：25min > 场景 17min。生产值保持 900（15min）。
```

**验证**：
- `kubectl apply -f infra/development/k8s/app-config.yaml` 后 `kubectl rollout restart deploy/api-gateway`。
- `kubectl exec deploy/api-gateway -- env | grep JWT_ACCESS_TTL_SECONDS` 输出 `1500`。
- 登录拿到的 access token 解码（`jwt.io`）`exp - iat == 1500`。

> **边界**：压测结束后必须改回 `900`，不要把 1500 提交为默认值。记得在 Round 3 后 `git restore infra/development/k8s/app-config.yaml`。

#### Step 0.5：构建自定义 k6 二进制（xk6）

压测 metrics 走 Prometheus remote_write，需要 `xk6-output-prometheus-remote` 扩展，官方 k6 二进制没带，需自编译。

```bash
# 1. 安装 xk6（k6 扩展构建工具）
go install go.k6.io/xk6/cmd/xk6@latest

# 2. 在仓库根目录构建自定义 k6，产物为 ./k6
cd /home/hx/workspace/code/mygo/mygo-microservices
xk6 build --with github.com/grafana/xk6-output-prometheus-remote

# 3. 把产物排除出版本控制
echo "/k6" >> .gitignore
```

**压测一律用仓库根目录的 `./k6` 二进制，不是 $PATH 里的官方 k6**。`loadtest/k6/README.md` 第一屏就必须强调这一点，避免误用。

**备选方案（未采用）**：k6 v0.50+ 内置 `-o experimental-prometheus-rw` 输出不需要 xk6，但本次仍走 xk6 路径，统一构建工具链，便于后续引入 xk6-browser / xk6-websockets 等扩展时不用切换。

**验证**：
- `./k6 version` 输出包含 `xk6-output-prometheus-remote` 扩展信息。
- `./k6 run --help | grep experimental-prometheus-rw` 有输出（确认 output 可用）。

### Day 3 上午：基础设施 Layer

#### Step 1：加 Prometheus 指标库（Go 端）

**依赖安装**：
```bash
go get github.com/prometheus/client_golang/prometheus
go get github.com/prometheus/client_golang/prometheus/promhttp
```

**`shared/metrics/metrics.go` 必须导出的指标**（命名遵循 Prometheus best practice）：

| 名称 | 类型 | Labels | 用途 |
|---|---|---|---|
| `http_requests_total` | Counter | service, method, path, status | QPS 统计 |
| `http_request_duration_seconds` | Histogram | service, method, path | P50/P99 延迟 |
| `rabbitmq_consumed_total` | Counter | service, queue, result | 消费成功/失败率 |
| `rabbitmq_dlq_depth` | Gauge | queue | DLQ 深度（定时采集）|
| `trip_accept_lock_contention_total` | Counter | result | 接单锁冲突次数 |
| `bloom_filter_hits_total` | Counter | filter, result | Bloom 命中/miss |
| `rate_limit_rejections_total` | Counter | endpoint | 限流拦截数 |
| `idempotency_dedup_total` | Counter | consumer, result | 幂等去重命中数 |

**Histogram buckets**：`[0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5]` 秒。

**`shared/metrics/middleware.go` 职责**：
- 包装 `http.Handler`，记录每次请求的 method/path/status/duration。
- path 要做**模板化**（`/trip/:id` 而不是具体 ID），避免高基数。方法：维护一个允许的 path 列表；不在列表里的归到 `"other"`。

**验证**：
- `curl localhost:8081/metrics` 返回 prometheus 格式文本，包含上述所有指标名。
- `shared/metrics/metrics_test.go` 跑通：注册一次指标不 panic，middleware 正确采样 latency。

#### Step 2：部署 Prometheus + Grafana

**`infra/development/k8s/prometheus.yaml`** 关键点：
- 用 **ConfigMap** 挂 `prometheus.yml`，定义 scrape_configs 抓 4 个 service。
- `static_configs` 而不是 `kubernetes_sd_configs`（简化，避免 RBAC）。
- scrape_interval: 15s，retention: 2h（够一场压测）。
- **必须启动参数** `--web.enable-remote-write-receiver`：接收 k6 remote_write 数据，否则压测指标进不来。

**`infra/development/k8s/grafana.yaml`** 关键点：
- 环境变量 `GF_AUTH_ANONYMOUS_ENABLED=true` + `GF_AUTH_ANONYMOUS_ORG_ROLE=Admin`，本地免登。
- Datasource ConfigMap 只配一条 Prometheus（`http://prometheus:9090`），k6 指标走 remote_write 进同一 Prometheus，不配独立 k6 datasource。
- Dashboard ConfigMap 挂 `loadtest/dashboards/concert-overview.json`。

**Tiltfile 改动**：
```starlark
k8s_yaml(['infra/development/k8s/prometheus.yaml', 'infra/development/k8s/grafana.yaml'])
k8s_resource('prometheus', port_forwards='9090:9090')
k8s_resource('grafana', port_forwards='3000:3000')
```

**各服务 Deployment 加注解**（以 api-gateway 为例）：
```yaml
metadata:
  annotations:
    prometheus.io/scrape: "true"
    prometheus.io/port: "8081"
    prometheus.io/path: "/metrics"
```

**验证**：
- `tilt up` 后访问 `http://localhost:9090/targets`，所有 4 个服务状态都是 **UP**。
- `http://localhost:3000` Grafana 能打开，Datasource "Prometheus" 测试连通性成功。
- 在 Grafana Explore 里查 `http_requests_total` 能出数据（此时只有健康检查流量）。
- `curl -X POST http://localhost:9090/api/v1/write` 返回 `400` 或 `405`（而非 `404`），证明 remote_write endpoint 已启用。

#### Step 4.3：proto 扩展 + 重新生成（为 GET /trip/:id 铺路）

`GET /trip/:id` 需要 trip-service 暴露一个 gRPC `GetTrip`，然后 api-gateway 透传。trip-service 内部已有 `service.GetTripByID`（含 Bloom 预检），这里只是把它暴露成 gRPC。

message GetTripRequest {

message GetTripResponse {

}
```

若 `Trip` message 已存在，直接复用。

**重新生成**：

```

#### Step 4.4：trip-service handler 实现 GetTrip

**改动**：`services/trip-service/internal/handler/grpc.go`
- 新增 `GetTrip(ctx, req *pb.GetTripRequest) (*pb.GetTripResponse, error)`。

- 命中 Bloom miss → 返回 `codes.NotFound`；服务错误 → `codes.Internal`。

**改动**：`services/trip-service/internal/handler/grpc_test.go`
- Hit case：mock service 返回合法 trip，断言 response.Trip 字段对齐。

**验证**：
- `go test -race -count=1 ./services/trip-service/...` 全绿。
- 覆盖到 Bloom miss 分支（或至少保留可观测的 log）。

#### Step 4.5：api-gateway 透传 + E2E

**改动**：`services/api-gateway/trip_handler.go`
- 新增 `handleGetTrip(w, r)`：
  - 从 URL path 取 `:id`（用现有的路由解析方式，不引新 router）。

  - gRPC `codes.NotFound` → HTTP 404；`codes.Internal` → 500；OK → 200 + JSON。
- **复用 main.go 里已有的 trip gRPC client**，不要再建一个连接。

**改动**：`services/api-gateway/main.go`
- 把 `GET /trip/:id` 挂到 mux（走 `authRequired`），handler 指向上面新增的函数。

**改动**：`services/api-gateway/trip_handler_test.go`
- Mock trip gRPC client：
  - 合法 tripID → 200。
  - Bloom miss 的 24 位十六进制伪造 ID → 404。

### Day 4 上午：k6 脚本

#### Step 5：k6 辅助模块

**`loadtest/k6/scenarios/helpers/auth.js`**：
- 启动时用 `SharedArray` 读 `users.json`。
- 登录函数：`login(phone, password) -> { accessToken, refreshToken }`。
- VU 启动时登录一次，token 存 `__ENV` 或 VU-local 变量，后续请求复用。
- **不做 token 刷新**：压测环境 access TTL = 25min（Step 0 已把 `JWT_ACCESS_TTL_SECONDS` 改为 1500），场景总时长 17min，token 跑不完不会过期；脚本里不加 refresh 逻辑。

**`loadtest/k6/scenarios/helpers/state.js`**：
- `tripIDPool`：司机侧从全局共享池里拿 tripID 去 accept。

**`loadtest/k6/scenarios/helpers/payload.js`**：

- `buildTripRequest(userID)`：返回合法的 `/trip/start` 请求体。

#### Step 6：主压测脚本

**`loadtest/k6/scenarios/concert.js`** 脚本结构：

```javascript
export const options = {
  scenarios: {
    riders: {
      executor: 'ramping-vus',
      startVUs: 50,
      stages: [
        { duration: '1m', target: 50 },     // 基线
        { duration: '2m', target: 2000 },   // 爬升
        { duration: '10m', target: 2000 },  // 峰值（故障在此窗口内注入）
        { duration: '2m', target: 300 },    // 回落
        { duration: '2m', target: 50 },     // 恢复
      ],
      exec: 'riderFlow',
    },
    drivers: {
      executor: 'constant-vus',
      vus: 800,
      duration: '17m',
      exec: 'driverFlow',
    },
    attackers: {
      executor: 'constant-arrival-rate',
      rate: 500, timeUnit: '1s',
      duration: '17m',
      preAllocatedVUs: 100,
      exec: 'attackerFlow',
    },
  },
  thresholds: thresholds,  // 见下一 step
};

export function riderFlow() {
  // 1. 登录（首次）
  // 2. POST /trip/preview（带思考时间 300~800ms）
  // 3. POST /trip/start
  // 4. WebSocket 连 /ws/riders 监听 driver_assigned 事件（最多等 15s）
  // 5. 5% 概率 30s 后取消（未来退款 Saga 压测用）
}

export function driverFlow() {
  // 1. 登录
  // 2. WebSocket 连 /ws/drivers
  // 3. 监听 trip_request：50% accept / 30% decline / 20% 超时
}

export function attackerFlow() {
  // 1. 带合法 rider token（JWT 中间件会先拦 401）
  // 2. 随机生成 24 位十六进制字符串作为伪造 tripID（格式合法但不存在）
  // 3. GET /trip/:id（走 Step 4.5 新增的透传路由 → trip-service.GetTrip → Bloom 预检）
  // 4. 期望 404（Bloom miss_rejected），bloom_filter_hits_total{result="miss_rejected"} +1
}
```

**关键决策**：
- 乘客**思考时间用 `sleep(Math.random() * 0.5 + 0.3)`**（300~800ms），模拟真实用户。
- 司机 WebSocket 用 k6 内置 `ws.connect`，收到 `trip_request` 后按概率调 `/driver/response`。
- 攻击者必须带一个**合法 rider token**（否则被 JWT 中间件先拦 401，打不到 Bloom），调的是随机生成的不存在的 tripID，目的是验证 Bloom 防穿透链路。

## 6. 风险 & 回退路径

| 风险 | Mitigation / 回退 |
|---|---|
| Chaos Mesh 装不上（WSL2 内核限制） | 回退：用 `kubectl delete pod` 手动 kill + `tc qdisc` 手动注延迟 |
| k6 从宿主机打不进 k8s | 确认 api-gateway Service 是 NodePort 或做 port-forward；或 k6 也进 k8s 跑（最后兜底）|
| Prometheus retention 不够 | 调 `--storage.tsdb.retention.time=4h` |
| 种子数据太慢（> 5 分钟） | 降级：rider 减到 2000、driver 减到 500；VU 同比调 |
| 峰值 2000 VU 本地机器扛不住 | 降级：峰值改 500 VU；报告如实说明硬件限制 |
| JWT access token 过期 | 本方案已通过 Step 0 把压测环境 `JWT_ACCESS_TTL_SECONDS=1500`（25min）> 场景总时长 17min；若再超时说明场景设计有问题，不加 refresh |
| HPA 是加分项，不配不影响验收 | 配了能在面板 Row 4 看到副本数曲线（可选）；未配时「手动 kubectl scale 验证」作为兜底演示 |
