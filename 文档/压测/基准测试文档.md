## 4. 核心测试代码

### 4.1 滑动窗口限流（接口防护）
**文件**：`shared/cache/ratelimit_bench_test.go`

并发互斥精度测试（验证 Lua 原子性）：
```go
func TestSlidingWindowAllow_ConcurrentAccuracy(t *testing.T) {
    rdb := newBenchRedisClient(t)
    const goroutines = 200
    const limit = 10

    var wg sync.WaitGroup
    var passed int64
    wg.Add(goroutines)
    for i := 0; i < goroutines; i++ {
        go func() {
            defer wg.Done()
            ok, _ := SlidingWindowAllow(ctx, rdb, "concurrent_user", limit, 5*time.Second)
            if ok { atomic.AddInt64(&passed, 1) }
        }()
    }
    wg.Wait()

    if passed > int64(limit) {
        t.Fatalf("concurrent passed=%d exceeded limit=%d (Lua atomicity broken)", passed, limit)
    }
}
```

并发吞吐基准：
```go
func BenchmarkSlidingWindowAllow_Parallel(b *testing.B) {
    rdb := newBenchRedisClient(b)
    var counter uint64
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() {
            i := atomic.AddUint64(&counter, 1)
            userID := fmt.Sprintf("bench_par_user_%d", i)
            SlidingWindowAllow(ctx, rdb, userID, 1, time.Second)
        }
    })
}
```

### 4.2 布隆过滤器（接口防护）
**文件**：`shared/cache/bloom_bench_test.go`

真实误判率测试（写入 20w ObjectID，再查 20w 不重复 ObjectID）：
```go
func TestBloomFalsePositiveRate(t *testing.T) {
    rdb := newBenchRedisClient(t)
    const insertCount = 200_000
    const queryCount  = 200_000

    inserted := make(map[string]struct{}, insertCount)
    for i := 0; i < insertCount; i++ {
        id := primitive.NewObjectID().Hex()
        inserted[id] = struct{}{}
        BloomAdd(ctx, rdb, "bench:bloom:fp", id)
    }

    falsePositives := 0
    for i := 0; i < queryCount; i++ {
        var id string
        for { // 跳过任何已写入的 ID，保证查询样本完全独立
            id = primitive.NewObjectID().Hex()
            if _, ok := inserted[id]; !ok { break }
        }
        if hit, _ := BloomExists(ctx, rdb, "bench:bloom:fp", id); hit {
            falsePositives++
        }
    }
    rate := float64(falsePositives) / float64(queryCount)
    t.Logf("inserted=%d queried=%d FP=%d rate=%.4f%%", insertCount, queryCount, falsePositives, rate*100)
}
```

### 4.3 消息幂等（消息可靠性）
**文件**：`shared/messaging/idempotency_bench_test.go`

并发收敛性验证（at-least-once 重投下，100 个 goroutine 抢同一 MessageId 必须收敛到 1 次业务执行）：
```go
func TestIdempotencyConcurrentClaim(t *testing.T) {
    rdb := newBenchRedisClient(t)
    const goroutines = 100
    msg := amqp.Delivery{MessageId: "concurrent-msg", RoutingKey: "trip.event.created", Body: []byte(`{"tripID":"t-99"}`)}

    var wg sync.WaitGroup
    var claimedFirstTime, alreadyDone, processingErr int64
    wg.Add(goroutines)
    for i := 0; i < goroutines; i++ {
        go func() {
            defer wg.Done()
            claim, err := ClaimMessageForProcessing(ctx, rdb, idemBenchNamespace, msg, idemBenchTTL)
            if err != nil { atomic.AddInt64(&processingErr, 1); return }
            if claim.AlreadyProcessed { atomic.AddInt64(&alreadyDone, 1); return }
            atomic.AddInt64(&claimedFirstTime, 1)
            MarkMessageProcessed(ctx, rdb, claim.Key, idemBenchTTL)
        }()
    }
    wg.Wait()

    if claimedFirstTime != 1 {
        t.Fatalf("expected exactly 1 goroutine to acquire processing right, got %d", claimedFirstTime)
    }
}
```

### 4.4 接单分布式锁（并发接单防护）
**文件**：`services/trip-service/internal/infrastructure/events/lock_bench_test.go`

100 司机抢同一 tripID 互斥正确性：
```go
func TestTripAcceptLockConcurrentSafety(t *testing.T) {
    rdb := newBenchRedisClient(t)
    consumer := &driverConsumer{redis: rdb}
    const goroutines = 100
    tripID := "concurrent-trip"

    var wg sync.WaitGroup
    var acquired, rejected int64
    wg.Add(goroutines)
    for i := 0; i < goroutines; i++ {
        driverID := fmt.Sprintf("driver-%d", i)
        go func(d string) {
            defer wg.Done()
            ok, _ := consumer.tryAcquireTripAcceptLock(ctx, tripID, d)
            if ok { atomic.AddInt64(&acquired, 1) } else { atomic.AddInt64(&rejected, 1) }
        }(driverID)
    }
    wg.Wait()

    if acquired != 1 {
        t.Fatalf("expected exactly 1 driver to acquire lock, got %d (rejected=%d)", acquired, rejected)
    }
}
```

> 说明：因 `tryAcquireTripAcceptLock` / `releaseTripAcceptLock` 是 `*driverConsumer` 的私有方法，benchmark 文件必须放在同包 `events`。构造时只填 `redis` 字段，不依赖 RabbitMQ 与 Service 接线，纯粹隔离测锁。

## 9. 面试口述（Quick Reference）

> 面试官问"你怎么测的"时，按这套口径讲。核心是区分清楚**三类测试**：QPS 吞吐测试 / 延迟分布测试 / 并发正确性测试，它们用**不同的并发模式**、测**不同的指标**，不要混为一谈。

### 9.1 先讲清楚三类测试的区别（开场必讲）

| 测试类型 | 并发模式 | 产出指标 | 目的 |
|---|---|---|---|
| **QPS 吞吐** (`BenchmarkXxx`) | **每次新 key，不争抢**；单线程或 `RunParallel` | ns/op → QPS | 测吞吐上限 |
| **延迟分布** (`TestXxxLatencyDistribution`) | 单线程顺序跑 5000 次 | P50 / P95 / P99 | 测尾部延迟 |
| **并发正确性** (`TestXxxConcurrentSafety/Claim/Accuracy`) | 100~200 goroutine **抢同一个 key** | 断言收敛次数 | 验证互斥/幂等逻辑 |

**常见误解澄清**：
- QPS 测试**故意不争抢**，争抢会互相阻塞，测到的是阻塞开销不是吞吐上限
- 正确性测试**故意全部争抢**，才能验证互斥逻辑是否正确
- 这两类测试用的是**完全不同的 benchmark 函数**，不要以为"100 goroutine 抢同一 key 测出的 QPS"

### 9.2 QPS 数字是怎么反推出来的

```go
// go test -bench 的工作原理
for i := 0; i < b.N; i++ {       // b.N 自动递增直到 ≥ benchtime (3s)
    key := fmt.Sprintf("k_%d", i)  // 每次新 key，无争抢
    SlidingWindowAllow(ctx, rdb, key, ...)
}
// 输出：219800 ns/op
// QPS = 1e9 / 219800 ≈ 4,550 qps   ← 简历 ~4.5k 的由来
```

并发 QPS 用 `b.RunParallel`，默认起 GOMAXPROCS (我机器 12) 个 goroutine，**总迭代数 b.N 被瓜分**：
- 单线程：219 µs/op → 4.5k QPS
- 12 核：42 µs/op → 23.4k QPS（Redis 单线程是瓶颈，不是线性 12×）

### 9.3 P50/P95/P99 怎么测（和 QPS 完全分开）

```go
durations := make([]time.Duration, 5000)
for i := 0; i < 5000; i++ {
    start := time.Now()
    SlidingWindowAllow(...)
    durations[i] = time.Since(start)
}
sort.Slice(durations, ...)
// durations[2500]=P50, durations[4750]=P95, durations[4950]=P99
```

**不是 benchmark，是普通 Test**。采 5000 个单次样本，sort 后按分位数取值。

### 9.4 四项测试的一句话口述

#### 滑动窗口限流（接口防护 · 接口层）
> "测了三件事：
> ① **纯吞吐**：每次新 userID 调 `SlidingWindowAllow`，单线程 4.5k QPS，`RunParallel` 12 核 23.4k QPS；
> ② **延迟**：5000 次串行采样 sort，P99 ≈ 0.9 ms；
> ③ **Lua 原子性**：200 个 goroutine 抢同一 userID、limit=10，如果 Lua 不是原子的会有超过 10 个通过。实测**恰好 10 个通过 190 个拒绝**，证明三步（ZREMRANGEBYSCORE → ZCARD → ZADD）被 Redis 单线程原子执行。"

#### 布隆过滤器（接口防护 · 缓存穿透层）
> "测了两件事：
> ① **误判率（核心指标）**：写入 20 万个 `primitive.NewObjectID()` 正样本，再用 map 查重生成 20 万个**完全不重叠**的负样本查询，命中即误判。实测 236 次误判 / 20 万 = **0.118%**，和理论值 0.155% 接近，证明双 FNV + 异或扰动分布均匀；
> ② **延迟和吞吐**：BloomExists 单线程 4.9k QPS，P99 ≈ 0.46 ms。
> 布隆查询都是固定 2 次 SetBit + Pipeline 批量发送，所以 hit/miss 路径延迟差不多。"

#### 消息幂等（消息可靠性）
> "测了两件事：
> ① **100 并发收敛性（核心）**：100 个 goroutine 抢同一个 MessageId 调 `ClaimMessageForProcessing`。预期结果必须是 **firstClaim=1**（只有一个进入业务）、剩余 99 个落到 `done` 快速跳过或命中 `processing` 返回错误（触发重试）。实测 firstClaim=1 / done=93 / processing 冲突=6，**三类路径合计 100，完全收敛**。这是 at-least-once 语义下保证「同一消息只执行一次业务」的关键证据；
> ② **吞吐（QPS 测试用独立 MessageId，不是同一个）**：每迭代生成新 MessageId 调 claim + markDone full flow，单线程 ~2.5k QPS、P99 0.81 ms。
>
> ⚠️ **澄清一个易误解点**：QPS 测试**不是**用 100 goroutine 抢同一 MessageId 测的 —— 那样只有 1 次业务执行 + 99 次跳过，测出来不是业务吞吐。QPS 测的是「连续处理不同消息」的端到端开销。"

#### 接单分布式锁（并发接单防护）
> "测了两件事：
> ① **100 司机抢同一 tripID 互斥正确性（核心）**：100 个 goroutine 分别用 driver-0 ~ driver-99 的 ID 调 `tryAcquireTripAcceptLock(tripID='concurrent-trip')`。预期 **acquired=1 / rejected=99**，实测完全一致，且 `go test -race` 通过，证明 SET NX EX + Lua owner 校验释放的方案在并发下强互斥；
> ② **吞吐**：每次新 tripID 做一次 acquire+release 完整往返（不争抢），单线程 2.4k QPS、P99 0.80 ms。
>
> 为什么要新 tripID？因为争抢同 tripID 时 99 个都是失败快路径，测出来的是拒绝开销不是完整加锁开销。"

### 9.5 高频追问与答案

**Q：为什么 QPS 测试要每次新 key？**
> 测吞吐上限。如果一直抢同一 key，99% 的请求走失败快路径，测到的不是真实业务吞吐。正常业务里同一 key 短时间内不会被几千个 QPS 打，每次新 key 才对应真实场景。

**Q：那你的 QPS 数字不就是"最好情况"？**
> 对，是**单组件 best case**。实际业务还有 MongoDB 写、gRPC 跨服务、网络 RTT 叠加。我这个数字代表「Redis 组件不会是业务瓶颈」，不代表端到端 QPS 就是 4.5k。

**Q：P99 和 QPS 能互推吗？**
> 不能。P99 ≈ 0.9 ms 不意味着 QPS = 1000/0.9 = 1100，因为 QPS 是平均（P50 附近），P99 是尾部。我项目 P50 263 µs → QPS 换算 3800 左右，和实测 4500 接近（因为真实 QPS 看的是众数不是 P50）。

**Q：为什么不测 100 goroutine 抢同一锁的 QPS？**
> 那测的不是吞吐，是**阻塞/拒绝开销**。争抢场景的合理指标是「**正确性（只有 1 个成功）+ 拒绝延迟**」，不是 QPS。把两个混起来是 benchmark 设计错误。

**Q：-race 通过能证明分布式锁正确吗？**
> **不能**。`-race` 只检测 Go 内存访问竞争，**不验证跨进程分布式正确性**。我的测试是单进程 100 goroutine 对 Redis 的并发，证明的是「Redis 单线程原子性 + 我的 Go 代码没有内存竞争」。真正的跨进程分布式压测需要起多 Pod + 网络分区注入（toxiproxy / Chaos Mesh），这超出了 side project 测试边界，我坦白没做。

### 9.6 最容易被抓包的三个坑（提前防御）

1. **"并发正确性测试就是 QPS 测试"** → 错，它们是两类完全不同的 benchmark，用不同的函数、不同的并发模式。
2. **"P99 * QPS = 1000ms"** → 错，P99 是尾部，平均延迟是 P50 附近，两者不能直接换算。
3. **"-race 通过就是分布式正确"** → 错，-race 只覆盖单进程内存竞争，分布式正确性要靠跨进程 + 故障注入验证。

## 10. 已知边界与局限

1. **本地单机网络**：所有数字均为本机 TCP，未涉及跨节点延迟。生产 Redis Sentinel 集群下 P99 通常会再叠加几个毫秒的网络 RTT，但量级关系不变。
2. **Redis 单实例**：未跑 Sentinel 故障切换的 P99 影响。代码层 Sentinel 适配已通过 `shared/cache/redis_client.go` 完成，benchmark 不依赖具体拓扑。
3. **Mongo CAS 未端到端**：本次只测 Redis 锁部分。Mongo `{status:pending}` 条件更新已被 `mongodb_filter_test.go` 覆盖正确性。Redis 锁 + Mongo CAS 双保险的端到端压测需要 testcontainers-go，暂不在本次 scope。
4. **HTTP 端到端未做**：本次只测核心函数。HTTP 层多了 JSON 解析 + handler chain 开销，端到端 QPS 会下降；但限流/幂等的相对延迟特征不变。
5. **WSL2 时钟分辨率**：单条延迟 µs 级测量在 WSL2 下精度受限于 `time.Now()`，max 列偶有十几毫秒尾部，应理解为操作系统调度抖动而非 Redis 延迟。
